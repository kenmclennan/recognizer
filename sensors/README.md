# recognizer-sensors

Recognizer's shipped sensors. Each reads the repository's cached scans and its working tree and writes one findings file (`schema/findings.schema.json`); `crap` and `mutation` also write an overlay (`schema/overlay.schema.json`). A sensor is one complete run: `crap` and `mutation` run the repository's tests themselves, so they execute the repository's code in its working tree.

```sh
recognizer-sense-NAME run [--repository P] [--commit C] [--output F] [--settings JSON]
```

`--repository` defaults to `.`, `--commit` to `git rev-parse HEAD`, `--output` to stdout and `--settings` to `{}`. Exit status is `2` for an unknown or missing name, a `--settings` that is not a JSON object or holds a bad or unknown key, a missing repository, no commit and any argument error. `--version` prints the package version, which is also the findings file's `sensor.version`.

A repository registers a shipped sensor in `.recognizer/config.yaml` by name: `sensors: {thresholds: {}}`. `recognizer` expands that to `recognizer-sense-thresholds run --repository {repository} --commit {commit} --output {output} --settings <the mapping as JSON>`.

`brew install kenmclennan/tap/recognizer-sense-NAME` installs one sensor on `PATH`, and the `recognizer-plugins` bundle installs all three; the names are the registry in `src/recognizer_sensors/registry.py`. Contributors run one from a checkout with `uv run --project sensors recognizer-sense-NAME`.

A sensor reports nothing for a file its grammars do not parse: a file with an extension no grammar covers is skipped, and so is a function whose syntax tree has an error node.

## Readiness check and setup guide

```sh
recognizer-sense-NAME check --repository P [--settings JSON] [--suites JSON] [--modules F] [--run] [--work]
recognizer-sense-NAME guide
```

`check` prints one JSON line (valid against `schema/check.schema.json`), `{"gaps": [{"code", "suite", "line"}], "notes": [{"code", "suite", "line"}]}`, and exits `0` whether or not there are gaps (`2` for bad arguments). It needs no commit, writes nothing in the repository and starts no test run. `--run` is valid only with `check`: it also runs each suite that has no gap once and reports `coverage-missing`, `coverage-unreadable` or (a well-formed jacoco report that matches no scanned file, or no scan at all) `coverage-unmatched` when its coverage report is absent, does not parse or matches nothing; a failing suite that leaves a parseable report is not a gap. Under `--run` a suite with no gap whose report covers fewer than all scanned files of its language under its directory also gets a note, code `coverage-partial`, such as `suite core: the coverage report covers 19 of 71 scanned Rust files`; a note is never a gap and changes neither readiness nor the exit status, and an lcov report covering none of the scanned files is `covers 0 of N` rather than `coverage-unmatched`. `--work` (valid only with `check`) asks a sensor that can count what a run would do to add `"work": {"unit", "to_perform", "reusable"}` to the document, counted from its own record with no test and no coverage run; `--modules` narrows it as it does a run, and a sensor that cannot answer (`crap`) prints no `work` key. Mutation counts a function with a site as `reusable` when a record entry matches its body and the support hash and every recorded verdict is reusable by the hashes of its recorded files (a function with no verdict at all costs nothing), and `to_perform` otherwise, so a newly covered site or an uncovered function that has no record entry is predicted as a function to perform; the run's own `work.performed` is the truth. A settings error is one gap, `config`, never exit `2`. `thresholds` has no check: its manifest says `check: false`, and `check` exits `2` with a usage message.

`crap` and `mutation` share one check of the `tests:` suites: with none, `no-test-suites`; per suite, the directory exists (`directory-missing`), then `activate` runs in the user's login shell from the suite's directory (`activate-failed` when it does not, bounded by 60 seconds), then the mandated tools of its language are present: Python `pytest`, `coverage` and `pytest-cov` importable; TypeScript the one runner's packages (`vitest` with `@vitest/coverage-v8` or `@vitest/coverage-istanbul`, or `jest`; both runners in `package.json` is `runner-conflict`); Kotlin an executable `gradlew` and the JaCoCo plugin with its XML report; Rust `cargo llvm-cov` and a `llvm-tools` component in `rustup component list --installed`; C# `coverlet.collector` in every test project. Each gap is one sentence naming the suite, such as `suite api: pytest-cov is not installed in the activated environment`. No install command is offered or run.

`guide` prints the sensor's setup guide as plain text, empty for a sensor with none. The core prints it for `recognizer help sensors <name>`.

## crap

Scores each function or method by change risk: `crap = cc^2 * (1 - coverage)^3 + cc`, as crap4j and unclebob/crapper do (references, never dependencies). `cc` is the cyclomatic complexity from the syntax tree: one plus each `if`, `elif`, loop, `case`/`when`/match arm, `catch`/`except`, conditional expression, `&&`/`||` (`and`/`or` in Python) and, in TypeScript, each `??` and `?.`. Coverage is the share of a function's instrumented lines (merged by path) that were hit.

It runs the test suites listed under `tests:` in `.recognizer/config.yaml` in the same run, each in the user's login shell, so it runs the repository's code in the working tree. `modified` is taken before the tests start. With no `tests:` list it does not run: it exits `2` with `coverage unavailable: no test suites are configured; add a tests list to .recognizer/config.yaml` and leaves a prior overlay untouched. Its readiness check reports `no-test-suites` when the list is absent.

| setting | default | meaning |
| --- | --- | --- |
| `threshold` | `30` | a number above 0; a function above it is a warning |
| `overlay` | `.recognizer/cache/overlays/crap.json` | relative path inside the repository the overlay is written to |

The `tests` list reaches the sensor as `--settings` JSON, put there by `recognizer` from the config's top-level `tests:` key; it is not a setting a user writes under `sensors.crap`, and `test_command` and `coverage` are no longer `crap` settings.

**Test suites.** Each suite has `name`, `language`, `directory`, `command`, an optional `activate` and `env`, and `coverage {path, format}` (`lcov` or `jacoco`); a TypeScript suite also names its `runner`. A suite runs as `$SHELL -ilc 'cd <directory> && <activate> && <command>'` (`/bin/zsh` when `SHELL` is unset) with the suite's `env`, from the repository, one after another in list order, with its output in `.recognizer/cache/coverage/last-run.log`. The sensor adds no flag, plugin, wrapper or environment variable, creates no environment and installs nothing. After a suite ends, its report is the files matching `<directory>/<coverage.path>` modified at or after the moment the suite started; nothing is deleted and an older report never counts. A suite whose language has no scan in the run is skipped. A suite that fails after writing its report keeps its coverage (diagnosis `tests-failed`); a suite that leaves no fresh report, or an empty one, gives `coverage-unavailable` naming the suite; a scanned language with no suite has unknown coverage and a `coverage-unavailable` diagnosis naming the language.

Unknown is never zero: a function whose file has no entry in the report has no `coverage` or `crap` overlay value and warns only when `cc` alone is above the threshold (summary `CRAP at least <cc>`). Findings are warnings with the id `crap:<module>::<function>` and the fix pattern `simplify-or-test`. The sensor also writes the overlay with the metrics `complexity`, `coverage` and `crap`, all at member granularity, keyed `module::function` or `module::Class.method`.

A failing test run does not end C.R.A.P. A suite's report is read even when the suite fails, and the findings document then carries a `diagnosis` with code `tests-failed`, the count of failing tests where the output names them (`failing.count`), at most five names (`failing.names`) and a line such as `3 tests failed, so coverage may read low`. When a suite leaves no fresh report, or its program does not start, C.R.A.P. reports complexity alone (every function has unknown coverage, so findings read `unknown coverage, CRAP at least <cc>` and the overlay holds only `complexity`) and the document carries a `diagnosis` with code `coverage-unavailable` and a line such as `coverage unavailable: the api suite left no coverage report at <path>; see .recognizer/cache/coverage/last-run.log`. Mutation instead refuses: it exits `2` and writes no document, before any mutant, when a suite's coverage run exits non-zero (code `tests-failed`, naming up to five failing tests: `the test suite fails before any mutation: tests/test_orders.py::test_refund and 2 more`) or no coverage can be produced (code `coverage-unavailable`).

A refusal prints exactly two stderr lines: a `recognizer-event` line carrying a `diagnosis` event (`code`, `text` and optional `fix`), then the plain `line`. Every other exit-2 path (bad settings, an unknown sensor) prints one plain line. The combined output of every command is in `.recognizer/cache/coverage/last-run.log`. The commands run in the sensor's own process group, so killing the group ends them.

Every sensor writes `recognizer-event` lines on stderr, always: `crap` a `start` of the functions it measured and a `note` per suite as its coverage run starts, `mutation` a `start` of the functions to mutate and a `progress` per suite (with `step` the suite name when more than one runs), `thresholds` a `start` of the modules and one closing `progress`. A diagnosis's `code` is the sensor's own short string, and the optional boolean `unmeasured` says the sensor finished without measuring what it was asked to (for example a language with no test suite), which makes the CLI record the run as failed. A diagnosis without it, such as `tests-failed`, does not.

## duplication

There is no `duplication` sensor here any more. The duplication check is part of the structure sensor in `check/` (`check/src/duplication/`, settings under `sensors.structure.duplication`) and runs with every `recognizer scan`; `check/README.md` describes it. This package keeps `functions.py`, `identity.py` and `parsing.py` for C.R.A.P. and Mutation, and `sensors/tests/test_function_identities.py` pins their function identities to the goldens the TypeScript port is tested against.

## mutation

Mutates each covered function and runs the repository's tests against every mutant, as unclebob/mutator and clj-mutate do (references, never dependencies), then warns on each function with a surviving mutant, naming each mutation and its line (`line 2 >= to >`), with the fix pattern `strengthen-tests`. One run does it all: the coverage run, the mutants, and the writes.

Mutation reads the `tests` list the core hands it from the config's top-level `tests:` key, as C.R.A.P. does, and runs every command it starts in the user's login shell (`$SHELL -ilc 'cd <directory> && <activate> && <command>'`) with the suite's `env`, inside a copy of the repository. It builds no environment and installs nothing: each language mandates dev-only tools that the repository installs itself (`pytest` with `coverage` and `pytest-cov`; `vitest` with `@vitest/coverage-v8` or `@vitest/coverage-istanbul`, or `jest`; the Gradle wrapper with the JaCoCo plugin and its XML report; `cargo-llvm-cov` with the `llvm-tools` component of rustup; `coverlet.collector` in each C# test project). A missing tool fails the run with the tool's own output in `.recognizer/cache/coverage/last-run.log`. With no `tests:` list it exits `2` with the C.R.A.P. sentence, and its readiness check reports `no-test-suites`. A file belongs to the suite of its language whose `directory` is the longest prefix of its path; a file under no suite is not mutated and has no overlay value, and a scanned language with no suite prints one stderr line and is not measured. Two suites of one language and directory are a settings error.

| setting | default | meaning |
| --- | --- | --- |
| `tests` | none | the suites, handed over by the core; never written under `sensors.mutation` |
| `carry` | none | repository-relative folders, with no trailing slash, that a copy takes although git does not list them (a venv, `node_modules`, build output); each entry names the exact folder, never a name matched at any depth, and nothing is carried by name when it is absent |
| `timeout_factor` | `10` | a mutant's timeout is `max(2, timeout_factor * baseline seconds)` of the baseline of the command that mutant runs; a timed-out run is killed |
| `max_workers` | the smaller of the core count and the available memory divided by one measured run's peak, at least 1 | integer >= 1, mutants run at once; an explicit value wins and reads no memory |
| `overlay` | `.recognizer/cache/overlays/mutation.json` | relative path the overlay is written to |
| `survivors` | `.recognizer/cache/mutation/survivors.json` | relative path the survivors file is written to |
| `record` | `.recognizer/cache/mutation/record.json` | relative path the mutation record is written to |
| `incremental` | `true` | `false` ignores the record and mutates every function; the record is still written |
| `max_minutes` | none | number above 0; no function starts once this many minutes have passed since the first mutant was handed to a worker (the coverage run is not counted) |

Before any mutant the sensor makes one Warm-up copy under `.recognizer/cache/mutation/work/` and runs each suite's own `command` in it, in list order, with the flag that records per-test contexts added for Python (`--cov-context=test`) and a trx logger for C#. A suite that exits non-zero refuses the run, with a stderr line beside the refusal naming `carry` when a folder the suite needs was not carried. A Python suite's `command` must end in the `pytest` invocation so the flag can be appended. An activated venv's editable install points at the original checkout, so a copy could import unmutated source: when the Python suite's coverage report names a source file inside the original repository but outside the Warm-up copy, the sensor stops before any mutant with `coverage unavailable: the <suite> suite imported <path> from outside its repository copy ...`; set `PYTHONPATH` in the suite's `env` to a path inside the repository (resolved inside the copy). A Python suite must also record per-test contexts: when the Warm-up's coverage data holds none (`coverage run -m pytest` without `dynamic_context = test_function` in the repository's own coverage configuration), the sensor refuses the suite with code `no-test-contexts`, naming `pytest --cov=PACKAGE` and `dynamic_context = test_function` as the two fixes, and `recognizer sensors check` reports the same gap for Mutation only when the suite's command and coverage configuration prove it. A suite whose coverage data records contexts but none resolves to a test file (every line would run the whole suite) is refused the same way with code `unmatched-test-contexts`, naming the suite and an example context. The sensor never edits the config, the venv or the copy to fix it, and it cannot see an editable or path-linked dependency in another language.

The operators, one replacement each: `true`/`false` (`True`/`False` in Python), `==`/`!=`, `<`/`<=`, `>`/`>=`, `+`/`-`, `*`/`/`, `&&`/`||` (`and`/`or` and removing `not` in Python), and in TypeScript `===`/`!==` and `??` to `&&` (C# has no `??` site). Strings, comments, generics, unary minus, Rust dereference and a C# `#if` condition yield none, and neither does an uncovered line.

A failing coverage run or baseline writes nothing and exits `2` with the one-line sentences listed under `crap` (the baseline's output tail goes to `last-run.log`). A mutant is killed by a non-zero exit, a failure to start or a timeout, and survives on exit `0`. The sensor writes the survivors file and the record, then the overlay, then the findings. The overlay holds `killed`, `survived` and `uncovered` counts and `score = killed / (killed + survived)` (absent when nothing ran) per function, keyed `module::function`; a function with unknown coverage is absent. It removes a stale `.recognizer/cache/overlays/mutate.json` when it writes its overlay. Copies live under `.recognizer/cache/mutation/work/` and are removed as each mutant finishes; a run killed with `SIGKILL` leaves its copies behind. A run with the whole suite per mutant takes the suite's duration times the covered-site count over `max_workers`; with test selection each mutant takes only the duration of the test files that executed its line.

A timed-out mutant is a kill: it counts in `killed` and the score, is listed under `timeouts` in the survivors file and never under `survivors`.

**Test selection.** The coverage run also records which tests executed each line, and a mutant runs only the tests that executed the line its site is covered by (the greatest recorded line from the function's start up to the site), using only the mandated tools. Python runs `pytest -rfE <node ids>` on the tests named by the per-test contexts; the per-test contexts are read from the Warm-up copy's coverage data with coverage.py's data API, one source file at a time, each node id kept whole (a trailing `|run`, `|setup` or `|teardown` removed, and a `@...` suffix that follows a parametrised `]` removed), a line whose names are not all existing node ids falling back to the test files named by dropping everything after `|` or `::` (a selection of more than 5000 node ids, or an id starting with `-`, also uses those files; the 50-file rule applies only to file selection; data recorded with `dynamic_context = test_function` holds dotted function names, resolved to the test file by path or a unique suffix, and a line the empty context also ran gets no selection), and a line whose names are not all existing files runs the whole suite. TypeScript has no warm-up: each mutant runs the suite's `runner` selection, `npx --no -- vitest related <file> --run` or `npx --no -- jest --findRelatedTests <file>`, with `--bail=1` or `--bail` once the baseline has passed and `--maxWorkers` when several mutants run at once (the cap applies to these selected commands only). `vitest related` exits `0` when no test imports the file, so the first mutant of each file is preceded by one unmutated baseline run of its selected command, and a baseline whose output says `No affected test files found` (or that fails, as `jest` does) makes that file run the whole suite, with one stderr line naming the file. `npx --no` fails instead of downloading anything. Kotlin runs `./gradlew test --no-daemon --tests <class>` for the classes of the covering test files (grouped per Gradle project; `--no-daemon` on every Gradle command, so no daemon is left behind, and copies share the user's normal Gradle home); the pass reads the test classes the Warm-up copy's whole run listed under `build/test-results/test`, maps each to the one test file declaring it (by `package` line and top-level `class` or `object`), and adds one `./gradlew test --no-daemon --rerun --tests <classes> jacocoTestReport` run per test file; a class with no single test file or one failing run drops Kotlin selection for the run. C# runs `dotnet test --filter` with one clause per class (each ending in a dot, so a class never matches a longer name); the pass adds a trx logger to the whole run to list the test classes (the `**/TestResults/results_*.trx` files modified since it started; none found drops selection), maps each to the one `.cs` file declaring it (nested classes with `+`), and adds one `dotnet test --filter <classes>` run per test file; a class with no single test file, one failing run or a run that executed other classes than its filter names drops C# selection for the run. Rust runs `cargo test -p <package> --lib --bin <name> --test <name>` for the cargo test targets that executed the line (doctests are not run by a selected command); the pass reads the targets of the default workspace members from `cargo metadata --no-deps`, names each by its repository-relative source path, groups the unit tests inside source files as one unit per lib or bin target and hashes each group's test items as its in-file test hash (an in-file test edit reruns the sites its unit group covers), and adds one `cargo llvm-cov -p <package> --lib|--bin|--test <name>` run per target; a failed `cargo metadata`, a target outside the repository or named twice, or one failing run drops Rust selection for the run. Kotlin, Rust and C# select only when the language has exactly one suite and its directory is `.`; otherwise each mutant runs the whole suite with one stderr line (`<language> has N suites` or `<language> runs from <directory>`). A selection of more than 50 files, a selection of more than half the suite (the distinct test files across all recorded lines; it takes no baseline of its own) or a file name starting with `-` runs the whole suite. A whole-suite run, a fallback included, runs the suite's own `command` in its directory with its `activate` and `env`, plus only the fail-fast flag (`-x` for pytest, `--bail=1` or `--bail` for TypeScript, `--fail-fast` after the Gradle test task and a directly following `--no-daemon`; none for Rust and C#), so a suite scoped to `tests/unit` never runs outside it; a mutant's timeout ends its process group and counts as a timeout even when a process outside the group holds the output open. A selected command whose baseline fails falls back to the whole suite with one stderr line; a failing whole-suite baseline exits `2`. A mutant that only an unattributed side effect (a session fixture credited to the first file that used it, or an earlier test in the same file that a node selection omits) would have killed can survive; set `incremental: false` for a full verdict.

**Work in the findings.** A Mutation findings document carries `work: {unit: "functions", performed, reused}`: `performed` counts the functions of the run's ticked suites and scope with at least one site run to completion, `reused` those whose every verdict was reused, and a carried function is in neither. Every item of `suites` carries `ran`, true for a suite this run ticked and false for one filled from the stored record, so a suite left `partial` by an earlier run does not mark a later run that ticked only other suites as incomplete.

**Mutation record.** Beside the survivors file the run writes the record (version 3, tables plus ids; a record written with `selection: 2` is ignored, so the first run after the upgrade re-measures every site): top-level `files` holds each distinct `[path, hash]` pair once and `sets` each distinct set of `files` indices once, and per function, the sha256 of its body, one verdict per mutation site (`killed`, `survived`, `timeout`, or `null` for an uncovered site) and, per covered site, an index into `sets` for the test files that ran it (`ran`) and, for a kill, an index for the test files the runner reported failing (`killer`), each file with its hash in `files`; plus `support`, the hash of the shared fixture files (every test file that is neither a test entry nor a `conftest.py`), the sha256 of the record key (`{"suites": <the suites as parsed, in order>, "selection": 3}`, so a change to a suite's `env` or command changes it and `max_workers` does not), the commit as provenance and the identities the last run skipped. Each site is judged on its own: a killed or timed-out site is reused while its function's body hash and every file in its `killer` map, counting the `conftest.py` files on their paths, are unchanged by hash; a surviving site is rerun when a covering test file is new or changed; a covered site with no verdict is run for the first time. A change to a shared support file voids all reuse. A site with no covering test files (TypeScript, or dropped selection) records `ran: null` and is reused only while the hash of all test files is unchanged. Python mutants run with `-rfE` and `killer` is read from the `FAILED` and `ERROR` lines, falling back to `ran` when they are missing or name an unknown path. The same rule applies with and without a module scope: a function outside the scope is carried only when every covered site passes it, and otherwise has no result. A function that only moved keeps its verdicts and reports its new lines. A missing, unreadable or other-version record, or changed suites, means a full run. Known limit: a change to a callee or other production code, with the function's body and test files unchanged, leaves a stale verdict the rule cannot see, as does a test file the convention in `mutation/test_files.py` does not recognise; set `incremental: false` for a full re-verdict.

**Excluded files.** A function whose file has no entry in the merged coverage mapping of its owning suite (a JaCoCo exclude, an lcov report with no `SF:` record for it) is not tested and is recorded as excluded, never as a verdict. The findings document gains `excluded`: `{"functions": <n>, "modules": [<sorted distinct module ids>]}`, written only when `n > 0`, and each such module with no other function in the run's targets is listed in `inputs`, so freshness reads it as measured until its file changes. The survivors file gains a top-level `excluded` list, always present, sorted by identity, of `{"identity", "file", "reason": "not-in-coverage-report"}`. The run prints `recognizer-sensors: mutation: <n> functions in <m> modules not tested because their files are not in the coverage report` when `n > 0`. An excluded function is absent from the overlay, `counts`, `partial` and the record; a file present in the report with no instrumented line in a function's range is not excluded.

**Budget.** With `max_minutes` set, work is queued by function: the functions the last run skipped first, then the rest, each in identity order. A function is wholly reused, wholly mutated or skipped; one already running when the budget ends finishes, so a run can overshoot by up to one function per worker. A skipped function is absent from the overlay (unknown, never healthy), listed in the survivors file's `skipped` with reason `uncovered-by-budget`, and `complete` is `false`. The survivors file also carries `reused`, the number of reused functions, and `unmeasured`: `{"budget": <functions in skipped>, "no-covering-test": <functions with known coverage and mutation sites, none covered>}`. Every run prints `recognizer-sensors: mutation: <r> of <n> functions reused, <m> mutated, <k> skipped (uncovered-by-budget)` on stderr, then a line with the functions without a covering test and how many mutants ran a selection or the whole suite, and exits `0`. The coverage run is outside the budget, so a run can exceed `max_minutes` by its duration.

## thresholds

Reads every current overlay in `.recognizer/cache/overlays/` and writes one finding for each module or member whose value for a configured metric crosses its line. It measures nothing. The settings are a mapping from metric name to a line: `{above: N}` or `{below: N}` with an optional `severity` of `warning` (default) or `violation`, or the string `off` to switch a metric's line off.

| metric       | default line |
| ------------ | ------------ |
| `complexity` | above 10     |
| `coverage`   | below 0.6    |

There is no default for `crap` or `survived`: the `crap` and `mutation` sensors judge those, and a user may still name them. An entry replaces a metric's default whole. An `above` line fires only when the value is greater than the line and a `below` line only when it is less, so a value exactly on a line is never a finding. A finding has the id `thresholds:<metric>:<key>` (the overlay's own key), the kind `thresholds.<metric>`, the principle `code-coverage-guidelines` for `coverage` at `below: 0.6` and `cyclomatic-complexity-limit` for `complexity` at `above: 10`, each with its `citation`, and the metric's name with no `citation` for any other metric or line, the new `metric` field, and `evidence.measures` `{value, line}` with `evidence.producer` naming the overlay's producer. A violation ratchets in the baseline by its id.

An overlay of another commit, or an unreadable one, is skipped with a line on stderr. The first overlay by file name that declares a metric supplies all of its values. A key matching no scanned module is counted and skipped; a metric you named that no current overlay declares prints a line. `recognizer scan --sense` runs sensors in the config's order, so list `thresholds` after `crap` to judge that run's overlay.
