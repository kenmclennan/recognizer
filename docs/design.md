# Recognizer design

Temporary: this document holds the design while it is being decided and built, and is deleted once the code and its own docs carry it.

## What it is

Recognizer scans a codebase into a language-neutral model of its modules and dependencies, and shows that model in a native viewer. The picture is derived from the code and never drawn by hand. The same scan is a machine-readable model other tools read without the viewer, such as lightcycle's codebase audit, which measures change with it and builds ratchets from it.

## Decided

### Granularity

- A box per module. A module's classes, functions and constants are shown in the inspector, never as boxes.
- a Kotlin module is a source file, as for every other language. Packages remain the unit of name resolution, because code in the same package needs no import, and package frames come from the folder tree. Test code stays apart from main through the scanner's skip list.
- a C# module is a source file too: a file holding several types is one box, its types its members. Namespaces are the unit of name resolution, and a module's build module is its nearest `.csproj`.

### Languages

- Python, TypeScript, Kotlin, Rust and C#. More languages come later; this set covers the codebases recognizer is built for, including Kotlin Micronaut services, the Rust side of Tauri apps and .NET services. C# is the only .NET language scanned: a repository's `.fs` and `.vb` files are left out, and the scan says how many.
- A repository holding several languages is scanned in each of them: one scan document per language, never merged, so nothing connects the languages where one calls into another (a webview's `invoke` into a Tauri command, a service calling another over HTTP).
- One TypeScript scanner covers Node back ends and React front ends. Framework meaning (component, hook, route) belongs in the policy and overlays, not the scanner.

### Scanners

- Each language has a standalone command-line scanner that emits the same JSON scan document, so audits and CI can scan without the viewer.
- `recognizer scan <repository>` is the one front door: it detects the repository's languages, runs each language's scanner and writes one scan document per language to `.recognizer/cache/`. Scans are never merged; no edge crosses languages.
- Python uses its own `ast` module. TypeScript uses the TypeScript compiler API, so module resolution (tsconfig paths, workspace packages) is right. Kotlin uses tree-sitter-kotlin and C# uses tree-sitter-c-sharp, each proved by a spike (below). Rust uses the `syn` parser, in a scanner written in Rust; a Rust module is a source file, and edges come from `use` paths and `mod` declarations resolved through the crate's module tree. Crates reached by a Cargo path dependency inside the repository are resolved in-repo and every other crate is foreign; `pub use` re-exports are followed and recorded in `via`; a trait implementation is an `implements` edge; `exported` is any `pub` form. Detection is by `.rs` file alone.

- **Open source, MIT.** Recognizer, its scanners and its app are MIT-licensed, in one public repository.
- **Released and installed as one toolchain.** The `recognizer` CLI, every scanner and the app are one package, versioned and released together, so they never disagree about the scan's `schema_version`. A single Homebrew cask in the tap (`kenmclennan/homebrew-tap`) installs the app, carries the toolchain inside the app bundle, links `recognizer` and each `recognizer-scan-<language>` onto `PATH`, and declares Homebrew's `node` and `python@3.13` as dependencies. A bare `brew upgrade` or `brew upgrade --cask` moves everything at once. CI elsewhere uses the release archive the bundle's toolchain is built from. The app has no updater of its own.

- **The Kotlin scanner** is built on tree-sitter-kotlin, shaped like the Python scanner: syntax only, with its own index of the names each package declares. A spike on Android and Micronaut services (nowinandroid, kuvasz, hm-grunndata-register, a hexagonal petclinic) measured edge precision of 0.98 to 1.0 per package, provided the scanner resolves names rather than reading import lines alone. The name index records the declaring file, and the figures are re-measured per file: on the pinned petclinic checkout 308 of 308 edges between scanned files are correct (precision 1.0) over 134 file modules and 587 edges, against 268 edges over 47 package modules before.
  - **Files.** `.kt` files outside `build/`; Gradle `.kts` scripts are not scanned. A module's build module is the nearest folder holding `build.gradle`, `build.gradle.kts` or `pom.xml`.
  - **Edges by name resolution.** Explicit, aliased and nested-member imports; wildcard imports resolved to the names actually used, never to the whole package; same-package references, which need no import, resolved to the file that declares the name, a name the file declares itself making no edge; fully-qualified uses in code. An import makes an edge only when its name is used. Kotlin has no re-exports, so `via` is never set.
  - **Foreign.** A name declared in no scanned Kotlin file is foreign, under its package (the segments before the first capitalised one). Generated code is foreign, whether checked in (jOOQ's Java, for example) or built (R, BuildConfig, kapt and KSP output); the scan records which unresolved imports fell under an in-repo package prefix, so nothing is dropped silently. An in-repo package prefix is, for each build module, the longest common dotted prefix (at least one segment) of the packages its scanned files declare; an import whose package equals the prefix or is below it is listed in `unresolved_imports`.
  - **Members.** Classes, objects, companion objects, data, sealed, enum and value classes are `class`; interfaces and fun interfaces are `interface`; type aliases are `type`; top-level properties and constants are `constant`; functions include extension functions. `exported` is every visibility but `private` (`internal` is used across packages within a build module, so it counts), and each member also records its visibility.
  - **Robustness.** Where the grammar silently misparses a declaration (some annotated declarations come back as expressions), the file is re-parsed in chunks at each top-level declaration and a name index read by pattern backs it up, so no declaration is lost. Identifiers inside short string templates (`"$CONTEXT_PATH/api"`), which the grammar does not expose, are read from the template text.
  - **Calls.** Calls through a receiver whose type is declared (a constructor parameter, a property) and calls of top-level names and objects. A call to a method a Micronaut Data repository inherits (`save`, `findById`) resolves to the repository interface.
  - **Stated limits.** The grammar lags the newest Kotlin syntax, so 1 to 2% of files keep damaged spans whose bodies are not read; edges are by name, so local shadowing is not modelled; return types are absent where a function's body is an expression; calls through local values and chains are not resolved. Dependency injection is seen through constructor types, imports and `implements` edges; runtime choice among several implementations, test HTTP clients bound to controllers only by URL, and beans made by a `@Factory` are not.
  - **Not crossed.** Kotlin calling Java in a mixed repository is not an edge: scans are never merged across languages.
- **The C# scanner** is built on tree-sitter-c-sharp, pinned to a git commit with C# 14 support (`f1c7c1ee21f56a33412c12efb8abe0c483f05f0d`; the PyPI release misreads C# 14 extension blocks as constructors without an error node), shaped like the Kotlin scanner: syntax only, with its own index of the names each namespace declares, and no .NET SDK needed to scan. A spike on dotnet/eShop, ARKlab/Ark.Tools (net10.0, SimpleInjector) and chocolatey/choco found 0.75% of files damaged, 2 of 2,008 losing a type declaration, and 90 of 90 sampled edges correct; its report is `recognizer/research/csharp-spike.md` in `kenmclennan/lightcycle-specs`.
  - **Files.** `.cs` files outside `bin/` and `obj/`, skipping `*.g.cs`, `*.g.i.cs` and `*.Designer.cs`. A project is test code, and is not scanned, when its `.csproj` references `Microsoft.NET.Test.Sdk`, sets `IsTestProject` true, uses `Sdk="MSTest.Sdk"`, or has a package reference whose id starts with xunit, NUnit, MSTest or TUnit or is `Microsoft.AspNetCore.Mvc.Testing`; when the `.csproj` cannot be read, a project named `*.Tests`, `*.UnitTests`, `*.IntegrationTests` or `*.FunctionalTests` is test code. Discovery reads `.sln`, `.slnx`, `.csproj` and `Directory.Build.props`. The scan's `selection` gains an optional `skip_paths` list of repository-relative directories, the test projects the scanner found by reading `.csproj` files, so the app's change view and any reader of the selection treat those files as deliberately unscanned rather than added.
  - **Edges by name resolution.** `using` imports a whole namespace, giving an edge per used name it declares; `using static`, `using Alias = ...`, `global using` anywhere in the project and the `.csproj`'s `ImplicitUsings` and `Using` items; the file's own namespace and its parents need no `using`. A use of a partial type is an edge to every file declaring it. Uses come from constructor parameters (primary constructors included), fields, properties, base lists (`inherits` and `implements`), parameter and return types, object creation, static access, attributes (with the `Attribute` suffix), generic type arguments and `typeof`, so a registration such as `container.Register<IFoo, Foo>()` is an edge from the composition root. A `public` or `protected` type is visible across projects through `ProjectReference`, or a package reference to an in-repo project; an `internal` or unmarked type only within its own project and every project a `<Compile Include ... Link>` shares its file with; a `file` type only in its file. Types nested in a type's other partial files and in its base types resolve.
  - **Extension methods.** Every method of a static class whose first parameter is `this`, and every member of a C# 14 `extension(...)` block, is indexed; a call `x.Name(...)` or `x?.Name(...)` is an edge to the file declaring an extension of that name whose namespace is visible, whose accessibility allows it and whose project the caller reaches. Matching is by name only, so an instance method that wins over a same-named extension still makes the edge.
  - **Foreign.** A name declared in no scanned C# file is foreign. A project's in-repo prefix is its `RootNamespace`, else its `AssemblyName`, else its `.csproj` name, never the common prefix of what its files declare, because projects declare extensions in borrowed namespaces (`Microsoft.Extensions.DependencyInjection`, `Rebus.Config`); a borrowed namespace is still indexed, and a name under it that does not resolve is foreign. A `using` under an in-repo prefix that names no declared namespace marks source-generated code (protobuf, Razor components) and is listed in `unresolved_imports`.
  - **Members.** Classes, sealed, static and partial classes, records, record structs, structs and enums are `class`; interfaces are `interface`; delegates and `using` aliases are not members. `interface`, `abstract class` and `abstract record` count as abstract, every other declared type as concrete. Methods, constructors, local functions and accessors with bodies are functions, with each member's visibility.
  - **Entry points.** A file with top-level statements; a type with `static Main`; a class deriving from `Controller` or `ControllerBase` or marked `[ApiController]`, or deriving from `BackgroundService` or implementing `IHostedService`; a type the framework loads (`[Generator]`, `[DiagnosticAnalyzer]`, `[ExportCodeFixProvider]`, `[ExportCodeRefactoringProvider]`, `[Cmdlet]`, `[DbContext]`, `[Migration]`, or deriving from `Migration`, `ModelSnapshot`, `IIncrementalGenerator`, `ISourceGenerator`, `DiagnosticAnalyzer`, `CodeFixProvider`, `Cmdlet` or `PSCmdlet`); `*.xaml.cs`, `*.razor.cs` and `*.cshtml.cs` code-behind; and a convention root, any type whose base list names an interface or abstract class the repository registers by scanning (`typeof(I).IsAssignableFrom`, `GetTypesToRegister`, an open-generic `Register`, `Collection.Register`, `Collection.Append` or `RegisterDecorator` with an assembly argument, MediatR's handler interfaces where `AddMediatR` appears, FluentValidation's validators where `AddValidatorsFromAssembly` appears). A file declaring no type (`GlobalUsings.cs`, `AssemblyInfo.cs`) is never an orphan.
  - **Constructor injection.** Constructor parameters give ordinary `depends` edges; the scan carries no injection label. A record's positional parameters are data, which matters only if a label is added later.
  - **Markup.** The scanner also reads `.razor`, `.cshtml` and `.xaml` files outside test projects and adds `depends` edges for the C# types they name: `@inject`, `@model` and `@inherits` types, `@using` as scope (with `_Imports.razor` and `_ViewImports.cshtml` applying to their folder and below), Razor component tags in `.razor` files, and XAML elements, `x:Class` and `x:DataType` resolved through `xmlns:` mappings (`clr-namespace:` with or without `;assembly=`, and `using:`). A markup file is not a module and draws no box. Its edges come from its code-behind module (`<path>.cs`), else the nearest module in the same project that declares a type or has top-level statements, found by walking from the file's folder up to the project folder and taking the smallest path in the first folder that holds one; with none, it adds no edge. A name that resolves to no in-repo declaration adds no edge, no foreign name and no unresolved import. `files` lists every markup file read and `selection.extensions` holds `.cs`, `.razor`, `.cshtml` and `.xaml`.
  - **Calls.** A call is written for a method or constructor of a scanned type. A call through a receiver whose type is declared (a parameter of the method, a primary-constructor parameter, a field or a property of the same type) is a `call` to the method of that name on the declared type, found on the type, its partial parts and its base types. A static call `Type.Method(...)` on an in-repo type, written plain or qualified, is a `call` to a method tagged `static`. An extension call `x.Name(...)` or `x?.Name(...)` is a `call` to the method of that name in each extension declaration the existing extension rule reaches, when the receiver is not a declared in-repo type that has the method. A call to an interface or abstract method is followed by a `dispatch` call to each concrete method of the same name on a type that implements or derives from it. Overloads share one member reference, so one call is written per source, line and target.
  - **Stated limits.** The grammar fails on `async` used as an identifier in an expression and on preprocessor directives inside comma lists, initializers, base lists and method chains; a damaged file is reported and keeps the declarations that survive. Extension calls match by name; calls through `var` locals, typed locals, chains, `new` (no `construct` call is written), a call on the enclosing type's own members, delegates and events, and a method inherited from an unscanned base are not written; overloads are not told apart; a local that shadows a field of the same name is not modelled; reflection and convention registration beyond the patterns above, type names inside Razor `@code` and `@{ }` blocks, `@implements`, `@layout`, `@typeparam`, `@attribute` and `@namespace`, XAML type names in attribute values and markup extensions, Razor components declared only in `.razor` files, wildcard `<Compile Include>`, `var` locals and source-generated types make no edge.
  - **Not crossed.** C# calling into F#, VB.NET or native code is not an edge.

### Viewer

A native app: Tauri 2, with the domain, application and drawing code in TypeScript in the webview, and Rust as a narrow boundary for files, running scanners, watching for changes and dialogs.

- **Built from the template.** The app starts from `kenmclennan/tauri-starter`: its `npm run init` is run in a scratch clone (name Recognizer, slug `recognizer`) and the renamed `app/` is copied into `app/` here and added to the root workspaces. Its CI becomes a job filtered on `app/**`. The template's updater and its Check for Updates menu item are not used: the toolchain is released and upgraded as one, through Homebrew (Scanners, above). The design of record for the app's internals (pure modules behind thin adapters, the Rust trust boundary, the terminal command) is the engineering knowledgebase's `desktop-apps/` topic.
- **Opened from the terminal with `recognizer open [folder]`.** A subcommand of the `recognizer` CLI launches the app on a folder, defaulting to the current directory. The app ships no terminal command of its own: the template's command is removed, so `recognizer` stays the one command for scanning, checking and opening.
- **Links open a repository and a view: `recognizer://open?repo=<absolute path>&view=<name>`.** The app registers the `recognizer` URL scheme with the operating system (Tauri's deep-link plugin, with the single-instance plugin so a link reaches the running app), so a link clicked anywhere, in a browser, a chat or a terminal that makes URLs clickable, or run with `open`, opens Recognizer on that folder with that saved view, or brings forward the window already showing it. `view` is optional; without it the folder opens on an empty canvas. `recognizer open` accepts the same link, so a script or a terminal can open one too. An agent that answers a question with a view ends its answer with the view's link. A link can come from anywhere, so it only ever opens: the folder must exist, the view must be a saved view in it, and a link never runs a command, describes, or changes a file. Anything else is refused with a message saying why.
- **It runs `recognizer scan`, never a bundled scanner.** The viewer scans exactly as CI and audits do. Rust runs the command on the folder the window opened through a Rust dialog and reads the result from that repository's `.recognizer/cache/`. An app launched from Finder has no shell `PATH`, so Rust resolves the command through the user's login shell, with an absolute path in the app's config as an override; a missing command is reported with what to install. A scan whose `schema_version` the app does not know is refused.
- **The window scans when it opens, and only then or on request.** Nothing rescans on its own. The footer says what the canvas was drawn from (the commit, when the folder is under git, and how long ago). When the files move on from the scan, the footer says so in amber with a Rescan button beside it: "N files changed since" for edits, or the new branch and commit when HEAD moved. A file counts when its contents now differ from when it was scanned, it is gone, or it is new in a language the scan covers; an edit undone again stops counting. What the scanners skip, files under `.recognizer/` and, under git, gitignored files do not count. A folder that is not under git is fully supported: the footer gives no commit and never reports HEAD moving. Clicking the count lists the files as modified, added or deleted. Rescan (the button, File > Rescan, ⌘R) dims the canvas while it runs and redraws the same view state, so back and forward still work; an open saved view that no longer matches shows its stale panel as on opening. A failed rescan keeps the old canvas and the footer says why.
- **Layout is ELK, drawn as SVG.** elkjs's layered algorithm places the nodes, off the main thread in a web worker; a pure module turns its coordinates into SVG, so the drawing is tested without a window.
- **The viewer needs no policy, and imposes no order the graph lacks.** A ball of mud must look like one. A policy lens is not built until example codebases have been drawn and show what it must express.

### Explorer

The viewer is an explorer, not a picture of the whole graph. Drawing every module at once is unreadable on a real codebase, and a dependency matrix ordered by depth shows little but cycles. The explorer starts from a few modules the user picks and grows by following edges, so the canvas only ever holds what the user asked to see. Clean and uncluttered is the bar: every addition to the screen earns its place, and nothing is shown by default that the user did not ask for.

The window has three areas, and the [glossary](glossary.md) names them. The first version is exactly what this section describes; anything not here is later.

- **The rail** (far left) is a thin strip of icons, one per left-hand panel, as an IDE's activity bar is. Clicking a panel's icon opens it, and clicking the icon of the open panel closes it so the canvas takes the width; one panel is open at a time, and the open panel's icon is marked. The panels, top to bottom, are Files (the tree; its own hide button is gone), Views, Notes, Scan and Findings, in the order they are used: choose a view, annotate it, scan, then read what the scan found. Hovering a rail icon shows the panel's name beside it. Further panels (saved views, history, scan history) are designed before any is built.
- **The tree** (the Files panel) is the repository's folder structure, as an IDE shows it, and is the way in. It opens and closes files, finds them, and jumps to them on the canvas. It carries no figures: each file and folder has a health disc instead, and a folder's disc is the worst inside it. A find field filters by path, and two filters keep only what is on the canvas or only what needs attention, with the folders above them. Its rows are the same as the Dependencies tab's rows (below). Its header names the repository and has an Open in Editor icon for the whole folder (below). Selecting something on the canvas scrolls the tree to it and highlights it, folders included. The tree has no key of its own: the legend names the discs.
- **The canvas** (centre) draws the modules on it inside frames that nest as the folders do. Each frame is one folder, labelled with that folder's own name, with one exception: a folder that holds no file the scanner reads and exactly one subfolder is merged with that subfolder, so a chain of such folders is one frame labelled with the joined path (`src/main/kotlin/com/example`), as an IDE compacts folders. The tree compacts the same chains into one row. A frame shows its health disc and how many of its folder's files are on the canvas out of how many it holds. A folder can be folded into one box, which keeps its disc, and edges to anything inside it are drawn to that box. A box shows its disc, its name and its note mark, nothing else; the counts of what a module uses and is used by live in the selection bar's dependencies button.
- **The inspector** (right) is closed by default, as a narrow rail, and opens only when asked. Its header gives the selection's name on one line, cut with an ellipsis and shown whole on hover, its folder on the line below, and an Open in Editor icon. It has three tabs, all in one underline style: Contents, Dependencies and Findings. Under the name and folder, above the tabs, a module's header carries its responsibility line (below). Contents shows each of its members as a card, in the order they appear in the file. A card has a coloured left edge and a label above saying what it is (Class, Interface, Type, Function or Constant, each in its own colour), the line it starts on, and its code, coloured as an editor colours it: a class's name and bases, then its fields with their types and its methods' signatures, in file order; a function's signature with its parameters' types and its return type; a constant's value. Only what is exported is shown. A Show private switch above the cards also shows what is not exported and private fields and methods, dimmed and marked private; it applies to every module and is remembered. With it off, a class says how many private fields and methods it hides. Contents carries no links to other modules: who builds, calls or uses a member is for the CLI's questions, not the inspector. Hovering a member highlights the edges that carry its name. For a folder, Contents lists its files and subfolders, each with its disc. Findings lists the selection's violations and warnings, each with why. A selected edge shows its evidence.

The controls are on the canvas, not in the sidebars:

- **One selection, one bar.** Clicking a module, or a folder by the name on its frame, selects it. Its small bar appears above it while the pointer is over the selected box or over the bar itself, and hides shortly after the pointer leaves both; right-clicking selects too and opens the same bar at the pointer. The bar is pinned to what opened it: it pans and zooms with the selection, or with that point on the canvas, and leaves the screen with it rather than being held inside the canvas. There is no second menu, and hovering only outlines. A module's bar has dependencies (with the total count of what it uses and what uses it), notes (the speech-bubble icon, lit while the box has a note; it opens the note bubble), findings (with the count of current findings naming the module, coloured as its disc is, and absent when there are none; it opens the inspector on its Findings tab), contents, open in editor and take off. Every button on the bar is an icon, never a word, and every icon in the app has a tooltip naming what it does and its key, such as "Contents (I)". Take off sits last, after a separator, drawn as a box with a minus and titled "Take off the canvas (Backspace)", never as a cross, so it does not read as closing the bar; the bar has no close button, and clicking empty canvas or Escape dismisses it. A folder's bar, for an open folder by its frame's name or a folded folder's box, adds its files, focus, and fold or unfold, which only make sense on a folder; its dependencies and dependents are the edges that cross its boundary. Keys: D opens the Dependencies tab, F focuses, Z folds, I opens contents, Backspace takes off, Escape clears.
- **One row, in the tree and the lists.** Every module row, in the tree and in the Dependencies tab, is a checkbox, then the name, then the health disc. The checkbox says whether the module is on the canvas, and clicking it puts it on or takes it off. Clicking the name of a module not on the canvas ticks it, puts it on and centres the canvas on it; clicking the name of a module already on the canvas centres the canvas on it. A module on the canvas has its name in bold. A folder row's checkbox puts all its files on or takes them all off, and shows a dash when only some are on; a folder's name opens and closes it, as its chevron does. There is no eye and no find. The checkbox is drawn by the app, not the platform's: 14px with rounded corners, filled with the selection colour and a drawn tick when checked, a dash when partly checked, its border lit on hover, with a focus ring for the keyboard.
- **Following edges is picking from a list in the inspector.** The dependencies button shows the total count and opens the inspector on its Dependencies tab, beside the canvas so it never covers it; the button stays lit while the tab shows. The tab has two sections, Uses and Used by, each headed with its count and each collapsible. Each lists the modules grouped by folder, each heading naming the folder's full path. Its rows are the rows above, the file name with its extension as the tree shows it, and nothing at the right: which names are imported is the edge's evidence, not the row's. Nothing is previewed on the canvas.
- **A trail follows dependencies through the inspector.** At the end of each module row in the Dependencies tab, an arrow shows on hover. Following it opens that module's own inspector panel to the right of the current one, and the row stays highlighted as the one followed. The panels form a trail, and each works as the inspector always does: its tabs, its rows ticked to put modules on the canvas. Following a different row in an earlier panel replaces the trail to its right; closing a panel closes it and every panel to its right. With two or more panels on the trail, the two rightmost always show: the shared panel width shrinks, down to the inspector's minimum, before anything folds. A third shows only when it fits at the dragged width. At most three panels show; earlier ones fold into narrow strips on the left, named vertically, and clicking a strip brings it back into view. Breadcrumbs across the top name every module on the trail and the relationship of each step (uses, or used by); clicking one brings its panel into view. A route icon at the breadcrumbs' end, titled "Put the trail on the canvas (P)", puts every module on the trail on the canvas at once. The trail's modules are outlined on the canvas. Selecting a box on the canvas starts a new trail from it. Every panel shares one width, set by dragging the inspector's edge. Keys, when the trail has focus: up and down move through a panel's rows, right follows the focused row, left returns to the previous panel's followed row, Space ticks, Escape closes the last panel, and P puts the trail on the canvas.
- **Focus** narrows the canvas to one folder's files. **Take off** removes a module, or a folder and everything in it: unticking it, or Backspace on the selection.
- **The view bar** (top left) holds back and forward, a views button that drops down the five most recently opened views with an All views link to the Views panel (described under saved views), the open view's name (with the range as a chip beside it when the view is a change view), which is edited in place to rename the view (or, on an untitled view, to name and save it), save, which asks for a name and a description the first time, and copy link, which copies the saved view's `recognizer://` link (above) to hand to an agent or a colleague. The app always opens on an empty canvas; a saved view comes back only when it is opened. A count in the window's footer, beside the app's version, says how many of the repository's modules are on the canvas; nothing sits over the canvas's top right. Zoom, fit, clear and the legend sit at the bottom right.
- **Both side panels resize.** The tree and the inspector are each resized by dragging their inner edge, between a minimum and a maximum width, and the app remembers the widths across windows and launches.
- **Open and Open Recent.** File > Open… (⌘O) shows the folder dialog whatever is in front, including when no window is open, and opens the chosen folder in the focused window when that window has no folder yet, otherwise in a new window. File > Open Recent lists the last ten folders opened, most recent first, each by its folder name (with its parent folder in brackets when two names collide), with Clear Menu at the end; choosing one opens it as Open does, and a folder that no longer exists is dropped from the list and refused with the usual dialog. The list lives in the app's own config folder, never in a repository.
- **Open in Editor.** File > Open in Editor (⌘⇧E) opens the selected module's file, and File > Open Folder in Editor (⌘⇧O) opens the repository, both in the one editor named in Settings: blank for the system's default, an app's name, or a shell command. The bar, the inspector's header and the tree's header have the same as icons.
- **Settings.** Recognizer > Settings… (⌘,) opens a settings window, as Yori's does. It holds the app's own preferences, never a repository's: the editor. A repository the app has not run on opens its Scan panel with nothing ticked, and after that the repository remembers its own ticks, below. The `recognizer` command is found on the login shell's PATH and is not configurable; when it is missing the app says to install it. A repository's tooling settings stay in its committed config.
- **Zoom and pan follow the device.** On a trackpad, pinch zooms and two fingers pan; with a mouse, the wheel zooms around the pointer and dragging pans. The device is told apart from each event, never from a setting. Zoom is limited to between 10% and 250%.
- **Scan panel.** Behind the Scan rail icon, in place of a Sensors panel: one scan, three phases. The head shows the last scan's commit and age. Extract is first: the languages, the module and edge counts, and whether the next scan will extract ("current", or "files changed since" with the commit); it has no tick, because extraction runs exactly when the files changed since the scan, a scanner's version changed or there is no scan, and `--extract` forces it. Describe is a phase with a tick: the counts of current, out of date and missing lines and the registered describer. Sensors is a phase with a tick: the built-in structure sensor first, "every scan", with its violations and warnings as its chip, then one row per registered sensor with its own tick and its status, ran (with when), stale (its file is from an earlier commit), failed (the reason on hover) or not run. One Scan button names what it will run ("scans current, describe, 3 sensors") and runs it; Stop replaces it while a scan runs. The ticks are remembered per repository, and a window opened on that repository scans on open with the same phases; a repository the app has not scanned before takes the Settings defaults. The footer walks the phases: "Extracting" or "Scans current", "Describing n of N", "Sensors n of N", with Stop, which ends the phase in flight and keeps what was written. Extraction lands first and the canvas is usable while the rest runs; sensor rows go stale when the commit moves and return as each reports, and findings files, discs and the Findings panel update as each lands. A failed sensor or describer is counted once in the footer with Show, which opens the panel on the failed row or the inspector on the failed module, and Open log, which opens the run's record; the rail icon carries a dot while a sensor is failed. While a view is open an "Only this view" switch, captioned with the view's name and module count, limits Descriptions to the view's stale modules and Mutation to the functions of the view's modules; C.R.A.P. and Duplication still run on the whole repository, and the switch is locked during a run and remembered with the ticks. A ticked Descriptions or Mutation row shows the size of the work before a run, which follows the switch. A scoped Mutation run keeps the earlier results for functions outside the scope. Nothing runs on open beyond what the repository remembers, and the Scan button is the only other trigger.
- **Findings panel.** Behind the Findings rail icon, whose badge counts the current findings, amber while every one is a warning and red once a violation is among them. The panel has the heading "Findings" and one muted line ("2 violations, 104 warnings"), then one collapsible group per finding kind, collapsed until clicked, in a fixed order: policy violation first, then the structure kinds, the shipped sensors' kinds, one group per agent report under its name and any other kind under its own. A group row is a chevron, a severity dot (red when it holds a violation), the name and the count; nothing else is numbered. Each finding is a card: the subject in bold (the module's file name, or the function's name), its folder muted beneath it and one plain sentence built from the evidence; text wraps and is never cut. There are no filters: the groups are the filter. When a registered sensor is not current, one line under the heading names it with a link to Sensors. Nothing here is drawn by hand: the cards are the findings files, as the discs are.
- **A finding in focus lights the canvas and selects nothing.** Clicking a card, in the panel or in the inspector's Findings tab, opens it inline and focuses it: its modules and edges light (the offending edge in red, a cycle's or hub's edges in amber) and the rest dims, with no selection, no inspector, no box added and no centring. The open card lists a row per module involved (a member finding lists the function), then one `a.py -> b.py` row per edge. Clicking the open card again, pressing Escape, or selecting any box outside the finding's evidence clears the focus; selecting a box inside it keeps it. One card is open at a time. J and K walk the cards in panel order, opening the group they land in.
- **Evidence off the view is offered, never drawn.** A row whose module has no box on the view says "Add to view" at its right, which adds that one box and nothing else; a module inside a collapsed folder counts as on the view. Nothing is drawn on the canvas for a module the view does not hold.
- **Health discs** are green for fine, amber for a warning, red for a violation, and a hollow grey ring for not measured. They come from the findings every sensor wrote for the current scan; without a policy nothing is red. A module with no findings is green when at least one findings file at the scan's commit covers it (a sensor ran over it), and grey when none does: before the first scan, or when the sensors failed or are stale. A folder shows the worst disc inside it.

Every edge on the canvas can show its evidence: the quoted import line, the names imported, and the route the names took through re-exporting files. Edges are hairlines under the boxes, so the modules dominate; the selection's own edges are highlighted and the rest dimmed. Boxes and frames unrelated to the selection fade to 60% so their names stay readable; unrelated edges fade further, to 35%. Hovering an edge names what it carries, and clicking it shows its evidence. Edges are drawn by kind: an ordinary dependency; an import of a private name (dashed), which is usually a defect; an inferred dependency (dotted, and switchable off), from the scan's inferred edges; and `implements` and `inherits` with a hollow arrowhead, so an adapter fulfilling a port does not read as depending on it. A legend on screen names every edge style, every disc, and what a frame's figure counts, and holds the switch for inferred edges; nothing is explained only in prose.

- **View state is a record.** Everything that decides what the user sees (the modules on the canvas, what is folded, selected and focused) is one view state. Each change makes a new one, so back and forward through them is the undo. View states live only as long as the window: history is never saved, and what lasts is a saved view (below). An agent reads what a window shows through `recognizer window` (Working with agents, below), never from a file.
- **An agent answers a question with a view.** This is a core feature, not an add-on. The user asks how something works ("which modules are involved in creating an item?"); the agent works it out from the scan, the code or both, and answers with a saved view the user opens and explores from. The user can save their own view and hand it back with a question about it, and the loop repeats. The agent traces a feature through the member calls in the scan, so it need not read the source to answer; traces are for the agent and are never drawn on the canvas. The agent builds the view with the CLI's view commands, never by writing the file by hand.

The design beyond the first version is found by prototyping on example codebases: lightcycle first, then Saga, Yori and a known mess. A prototype is a throwaway sketch, never the app's code.

### Saved views

A saved view is how a view lasts: a file in the scanned repository at `.recognizer/views/<name>.json`, committed like the policy, so a team shares views and they review in pull requests. It holds:

- **A description**: one or two sentences saying what the view shows ("how a work item reaches the store"). The app asks for it as Description, with the hint "What it shows". It is required. It tells someone opening a committed view what they are looking at, and it is what lets an agent repair the view when the code has moved on.
- **The commit it was saved at**, so the view can say what changed since.
- **A git range, for a change view**: a base and a head (`main..feature/discounts`), given with `views new <name> --change <base>..<head>`. A view with a range is a change view: when it opens, recognizer diffs the range afresh, so the view follows the branch, puts every module the diff touches on the canvas beside the view's own picks, and marks each box added, modified or removed, a removed module drawn dashed from the base's scan; a legend names the three at the canvas's bottom right, the view bar shows the range beside the name, and a view whose head git no longer knows is stale. The branch carries its view file, so a pull request's view is reviewed with the pull request. This is the one view the open 'Structural change' question needed.
- **Steps**: what put each module on the canvas, replayed against the current scan every time the view opens. There are two kinds. A **pick** names one module by its path; everything the user adds in the app (from the tree, the Dependencies tab, or a folder row's checkbox) is recorded as picks, always. A **rule** names a relationship: everything in a folder, or what a module uses or is used by, optionally within a folder. Rules are written by agents through the CLI where a rule is what is meant. Fold and focus are steps too. Taking a module off removes its pick, or, when a rule put it there, records that it is left out.

No layout is stored: the canvas lays a view out as it lays out any set of modules. Selection is not stored.

**Views are few, and nothing deletes one on its own.** The view bar's views button drops down the five most recently opened views, each with its description and kind, and, when the repository has more, an All views link at the bottom that opens the Views panel. The Views panel, behind a rail icon between Files and Notes, holds the full list: the live views first, each with its description, its kind and its note count, then the done ones under a Stale heading, each saying why: a change view whose head has merged into its base or whose branch no longer exists, or any view with a pick that no longer resolves. Each stale row has Delete, which removes the file as any other change to the repository, and `recognizer views check` names the same views for an agent, so the list stays short without curation and without anything disappearing by itself.

**A view is never shown stale.** A rule cannot go stale: it re-evaluates, gaining new files and losing deleted ones. A pick can name a module that no longer exists. When a view opens, recognizer compares the scan at the view's commit with the current one around the view, and the canvas shows only what exists now, and one message in the message tray says what changed. Each pair of view commit and scan commit is compared once per window, so scanning again at the same commit never repeats the message:

- **Missing**: a picked module that is gone, with its new path when git records a rename.
- **Changed relations**: edges between the view's modules that were removed or added.
- **Newly relevant**: modules that now use or are used by the view's modules and did not at its commit, never added for the user.

The message carries one action, Update, which drops what is missing, takes the renames and saves the view at the current commit; ignoring or clearing the message leaves the view as it is. Nothing removed is drawn: the code as it is now is the only picture.

`recognizer views check` lists every step in every view that names a path which no longer exists, and exits non-zero when there is one; a repository's CI runs it beside `recognizer check`, so a change that breaks a view says so in its own pull request. `recognizer views check --fix` rewrites picks whose files git records as renamed.

#### Working with agents

The user works with an agent beside the app, in a terminal (Claude Code), not inside it: an in-app agent would be a thin layer over the same CLI, decided later. The work runs both ways. The user asks the agent to show them something ("how is an order placed?"), to extend what they are looking at, or to explain it; and the two design changes together, which the agent expresses as a proposed change the user views as a diff (Open, "Structural change").

**The CLI is the agent's only interface.** An agent never reads or writes anything under `.recognizer/`: scans, views, responsibilities, config and the app's state are the tool's to manage, and every question and change goes through `recognizer`. Every command prints plain text by default and JSON with `--json`, and reads the cached scan when it is current and scans first otherwise.

- **Questions of the scan**: `recognizer uses <module>`, `recognizer used-by <module>`, `recognizer callers <module> <name>` and `recognizer path <from> <to>`, with modules named by their repository-relative paths; `recognizer find <text>` for modules by path and members by name; `recognizer show <module>` for what Contents shows (members and signatures, visibility, lines, the responsibility line and its findings); `recognizer modules` to list and filter modules (by folder, by findings, by how much they use or are used, sorted); and `recognizer check [<module>...]` for violations and warnings against the repository's current scan. `check --scan <file>` remains only for CI and fixtures, to replay a scan produced elsewhere; agents never use it.
- **Views**: `recognizer views new <name> --description <text>` (or `--from-window <id>`, which saves what a window shows as a new view), then `add`, `rule`, `fold`, `focus` and `remove`, each adding or removing one step; `show <name>` prints the steps and the modules they resolve to now, so an agent checks its work without the app; `list`, `check` and `rm`; and `note <name> <module-or-folder> <text>` and `note <name> <module-or-folder> --remove`, which set the one note on a module or folder in the view (writing again replaces it) or take it off. An agent never writes a view file by hand.
- **Windows**: `recognizer windows` lists the app's open windows (an id, the folder, the open view, the selection); `recognizer window [<id>]` prints what that window shows (its modules, folds, focus, selection, trail and inspector tab), the id optional when one window is open. `recognizer window <id> add|remove|fold|focus|select|trail|open-view|clear ...` drives that window directly, for when the user is hands off. The CLI reaches the running app through a local socket readable only by the user, which answers each command with done or refused and why.

**Two ways to answer.** Mostly the agent answers through saved views: it builds or extends a view and ends its answer with the view's `recognizer://` link, or extends the view a window already has open, which redraws in place because the app watches `.recognizer/views/`. When the user is hands off, the agent may drive a window instead. Either way every change is an ordinary view-state change, so back and forward undo it.

**The way into an unfamiliar repository is a question to the agent.** The app offers no overview, ranking, name search or path of its own: a folded top level only reads on a small, clean tree and is one box or a hairball on anything else; the modules everything leans on are what the hub warning and the package metrics already name; a name is the IDE's to find; and a route is `recognizer path`, or the Dependencies trail. A person who does not know the repository asks, and the agent answers with a view and its link, as above. The empty canvas keeps its two lines.

**Agent changes are marked.** A change made through `recognizer window` carries who made it (`--by <name>`): the footer shows one line, such as "Claude added 4 modules · Undo", that fades after a few seconds, with Undo stepping back; and the agent's entries in back and forward are labelled as the agent's, so the user sees where their own exploring ends.

**Notes: one comment per box, kept with the view.** Anyone can annotate a view, the user in the app as well as an agent through the CLI. A module or a folder carries at most one note per view, and the note records who last wrote it; writing again replaces the text, so there are no threads, replies or tints by author. Notes belong to the view, not the module, so one module can carry different notes in different views, and they are committed with the view. On the canvas a noted box carries one small outlined speech-bubble mark after its name, and a noted folder the same mark at its frame's corner; nothing else marks a note; the mark sits at the box's right end, centred on its row, and the box is wide enough to hold it. The note is read and written in a speech bubble beside the box, to its right with the tail pointing at the mark, or to its left when there is no room, and at a frame's corner for a folder: the text, who last wrote it, Edit and Remove; clicking the text edits it in place and Save writes the view file as the user; on a box with no note the bubble opens ready to write. A note in focus is a module selection with its bubble open, as a finding in focus is: selecting the noted box keeps it, selecting any other box or pressing Escape clears it. The bubble opens three ways and is the same bubble: clicking the mark, the bar's notes button (the same speech-bubble icon as the mark and the rail), and N on a selected box or folder; the inspector has no notes tab, since the bubble is the one place a note is read or written. Remove is undoable from the footer, as canvas changes are. Only the focused bubble is drawn, so the canvas stays clean. The Notes panel in the left column, behind the rail's speech-bubble icon, is the overview and the order: one row per noted box or folder, a row focuses its note, and it holds no composer. A note whose box is not on the canvas stays in the panel, greyed, until the box returns. The file holds no positions and no timestamps, since the layout places the note and git holds the history.

**A view's notes have one order.** A view's notes are an ordered list, and the order is the view's story: a proposed change, a pull request, or how a feature works, told box by box. The Notes panel lists the notes numbered in that order, each row with a full-height drag handle, and dragging a row reorders the view; a new note lands at the end; the CLI writes the same order with `views note <view> <module> --after <module>`. The numbers sit in the marks on the canvas. The bubble gains Previous and Next (the arrow keys too) and says which note of how many it is; stepping keeps the bubble where it is and pans the canvas so the current box slides in beside it, because a reader's eye should stay on the text. Opening a view from its link lands on the first note with its bubble open.

**Every run leaves a record an agent can read.** Each run of a registered command, by the CLI or by the app through it, writes one record under `.recognizer/cache/log/`: what ran (scan or describe), when, who asked, the command line with its placeholders filled, and for each phase of a scan and each module or sensor within it the exit status, the time taken and the stderr. A scan is one record with a section per phase it ran. The cache is never committed and keeps the last fifty runs. `recognizer log` lists the recent runs, `recognizer log --last` prints the latest in full and `recognizer log <run>` one by id, each with `--json`; the guide points an agent there for any failure, so no agent reads the files by hand. In the app, a failed describe or sensor run offers Open log, which opens that record in the editor. A sensor's command has sixty seconds; one still running then is killed and recorded as failed with the reason timed out, in the CLI and in the app alike. A shipped sensor that runs the tests (`crap`, `mutation`) has no ceiling, because running the tests takes as long as it takes; the app's Stop is the way to end one.

**The help is the manual, and the guide is in the tool.** Using the CLI must not need a skill installed. `recognizer --help` is short: every command with one line. `recognizer help <command>` and `<command> --help` are complete: arguments, what is printed with and without `--json`, exit codes, and one or two real examples. The help is generated from the same command table the CLI dispatches from, so it cannot drift from the commands. `recognizer help agents` is the agent's guide: how to answer each kind of request, which commands to use, and that `.recognizer/` is off limits; it ships and versions with the tool. `recognizer agents install` installs a Claude Code skill that only points at that guide, and a Claude Code permission rule denying reading and editing `**/.recognizer/**`, so the rule is enforced rather than asked for. The help is accepted when an agent given only the help output builds a described view correctly.

### A module's responsibility

Each module has a generated one-line statement of what it is for, shown in the inspector's header above the tabs.

- **Who writes it.** A repository registers a describer in `.recognizer/config.yaml`: the command that writes a line, such as a model's CLI with a fixed prompt, and a version naming that prompt. Recognizer runs it and stays independent of any model. It gives the describer the module's outline from the scan (its members and signatures, what it uses and what uses it) and its source, and takes back one line. The line says what the module does from its code, never from a docstring or a comment.
- **When.** Never on its own, because every line is a model call. `recognizer describe` describes every module whose line is missing or out of date and leaves the rest; `recognizer describe <module>...` describes the named ones; `--all` describes everything. A person, a scheduled CI run or an agent runs it. Extraction never describes, so it stays fast and repeatable; describing is the second phase of a scan, run only when asked for with `--describe` or the Scan panel's tick, which is the same deliberate choice made once per repository.
- **Where.** Committed, at `.recognizer/responsibilities.json`: each module's id mapped to its line, the hash of the module's source it was written from, and the describer and version that wrote it. One run pays for each line and everyone shares it, lines are reviewed in pull requests like any other text, and a fresh clone has them at once.
- **Only regenerated when needed.** A line is current while the module's source hash and the describer and version both match. Editing the module, or changing the describer or its version, makes its line out of date; a change in another module does not, because a module's responsibility is its own. `describe` redoes exactly the out-of-date lines.
- **In the app.** The inspector's header shows the current line under the module's name, above the tabs, and hovering a box on the canvas shows the same line with the note's first words beneath it. The inspector shows the sentence alone, with no tag and no button; describing runs from the Scan panel's Descriptions row. When the repository's scan includes the Describe phase, extraction finishes and the canvas is usable first, then the modules whose line is missing or out of date are described in the background, the footer shows how many are done of how many with a Stop that keeps what was written, and hover text and inspector headers fill in as each line lands. Failures are counted once in the footer; Show opens the inspector on the failed module with the describer's reason, and Open log opens that run's record. When every module failed the same way, the footer says why once instead of counting. The tree never changes for descriptions. The app never describes unless the phase is ticked.

### Repository layout

One repository with a directory per part, so every scanner is tested against the same schema and fixtures in one CI run:

check/                CLI and library: recognizer check, the structure sensor
scanners/python/      CLI: recognizer-scan-python
scanners/typescript/  CLI: recognizer-scan-typescript
scanners/kotlin/      CLI: recognizer-scan-kotlin

scanners/rust/        CLI: recognizer-scan-rust
app/                  the Tauri viewer

### Files in a scanned repository

Everything the repository's owners write is committed under `.recognizer/`; anything derived is cached and gitignored.

| What | Where | Committed |
| --- | --- | --- |
| Policy: levels, components, foreign libraries, ignores | `.recognizer/policy.*` | yes |
| Proposed structures | `.recognizer/proposals/` | yes |
| Ratchet baselines | `.recognizer/baselines/` | yes |
| Saved views | `.recognizer/views/` | yes |
| Scan results | `.recognizer/cache/` | no |
| Findings, one file per sensor | `.recognizer/cache/findings/` | no |
| Tooling configuration: registered sensors and the describer | `.recognizer/config.yaml` | yes |
| Module responsibilities | `.recognizer/responsibilities.json` | yes |
| Health overlays (complexity, coverage, mutation) | `.recognizer/cache/overlays/` | no, unless a project opts in to committing a mutation snapshot keyed by commit |

Scans are not stored for change detection: comparing two commits means scanning both.

### Policy

The one file a repository's owners write, at `.recognizer/policy.yaml`. YAML, because people write it and comments matter. Components are assigned by path, so the same policy shape works in every language.

```yaml
levels: # optional; inner first; a component may depend on itself or any inner one
  - domain
  - ports
  - application
  - adapters
  - entry

components: # which paths belong to which component
  domain: lightcycle/domain/**
  ports: lightcycle/ports/**
  application: lightcycle/application/**
  adapters: lightcycle/adapters/**
  entry: [lightcycle/container.py, lightcycle/cli.py]

forbid: # rules the other forms cannot express
  - lightcycle/adapters/* -> lightcycle/adapters/*
  - "* -> lightcycle/adapters/tui/**"

foreign: # group external libraries
  stdlib: [os, subprocess, sqlite3]

ignore: [tests/**, "**/fixtures/**"]
```

- **The dependency rule comes from `levels` and `uses`.** An edge between two components in `levels` from inner to outer is a violation: drawn red, and counted by the ratchet. `uses` maps a component to the components it may depend on, and permits an edge the order forbids; an edge between two different components that neither form permits is a violation.
- **`forbid` covers what the other forms cannot express**, such as adapters calling each other.
- **There is no allow list.** A way to mark an edge as acceptable becomes a place for violations to hide. An existing violation goes in the ratchet baseline (`.recognizer/baselines/`), where it is counted and may only shrink, never into the policy.
- **The level order is one rule form, not the only one.** The general form is named components with the dependencies each may have (Principles: every dependence is justified by purpose). `levels` and `uses` are both optional and may be combined: a policy with `levels` only is the level order, with `uses` only is an explicit dependency table, and with neither checks only `forbid`. Starter policies for each form live in `policies/`.

### Scan document

Each scanner emits one JSON document per language, with `schema_version` (an integer, bumped only on a breaking change; a consumer refuses a version it does not know), the scanner's name and version, the commit scanned, whether the working tree had uncommitted changes outside `.recognizer/` (`modified`: `true`, `false`, or `null` when the folder is not under git, because nothing is known), the files the scanner read, the rule it used to choose them, and four lists. Version 4 added the last three of those.

- **`files`**: every file the scanner read, sorted by `path` (repository-relative, forward slashes, the same form as a module `id`), each with a `hash`, the SHA-256 of its bytes in lowercase hex. A file with no members is still listed. The CLI's freshness rule and the viewer's changed-since rule both read it, so neither keeps its own copy of what a scanner skips.
- **`selection`**: the scanner's own rule as data, so a consumer can decide whether a path it has not seen would have been read: `extensions`, `skip_directory_names`, `skip_directory_prefixes`, `skip_directory_suffixes`, `skip_directories_containing` (a directory holding a file of that name is skipped) and `skip_file_globs` (`*` is any run of characters and nothing else) and the optional `skip_paths` (repository-relative directories the scanner skipped by reading project files, such as C# test projects; a path under one is unscanned, not added). Each scanner builds it from the constants its discovery uses.

The four lists are:

- **`modules`**: one per box. `id` is the repository-relative path with forward slashes and no leading `./`. `language` sits on the module, not the document. `kind` is `module`, `package` or `interface` (a module whose exports are only abstractions). `members` lists the classes and functions it contains: `name`, `kind` (`class`, `function`, `interface`, `type`, `constant`), `line`, `exported` (the language's own declaration of its public surface: in Python, membership of `__all__` when the module defines one and otherwise a name without a leading underscore, which also marks a class's private fields and methods; in TypeScript, `export`; in Kotlin and Rust, their visibility modifiers), and, for a Kotlin member, `visibility` (`public`, `protected`, `internal` or `private`; `exported` is false exactly when it is `private`; the other scanners omit it, which means not recorded), and the outline the inspector shows: a class's bases, its fields with their types, lines and privacy, and its methods; a function's or method's parameters with their types and its return type; a constant's value, shortened.
- **`edges`**: module to module, `from` and `to` by module id, `kind` is `depends`, `inherits` or `implements`, and `line` is where in `from` it comes from, so a violation is clickable; for an edge a C# markup file produces it is the line in the markup file that names the type. `inherits` and `implements` also carry the two member names (`member`, `to_member`) for the viewer's drill-down.
  - **A `depends` edge points at the module that defines what is used.** It lists the imported `names`, and each name is followed through re-exporting files (a Python `__init__.py`, a TypeScript `index.ts`) to the module that defines it, which is `to`; the files it passed through are `via`, in order. An import of names from two defining modules is two edges. Without this, every user of a package's re-exports appears to depend on the whole package, and the real dependents of a module are hidden.
  - **An `inferred` edge is a dependency the imports do not show.** Where a parameter has no type (a constructor's collaborator, a function's argument), the scanner collects the methods called on it and finds the classes that define all of them, inherited methods included. When few classes match, preferring abstract ones (a Protocol, an ABC, an interface), it emits a `depends` edge to the defining module with `inferred` holding the evidence: the parameter, the methods called, the matched class and its known implementations. Too many matches, or only generic method names, emit nothing. An inferred edge is always drawn and reported as inferred.
- **`calls`**: member to member, by `module::Qualified.name`, with `line` and `how`: `call`, `construct`, `inferred` (the receiver's class found as for an inferred edge) or `dispatch` (an abstract method to the concrete methods that implement it). A call through a port is followed by dispatch to the adapter, so a member's callers include those that reach it through an abstraction. Calls are what an agent traces a feature with, and what the inspector's callers come from.
- **`unresolved_imports`**: optional, written by the Kotlin scanner (always, empty when nothing qualifies). Each item is `from` (a module id), `import` (the import path as written, without its alias; a wildcard keeps its `.*`) and `line`: an import whose name is declared in no scanned file and whose package is equal to or below an in-repo package prefix, whether or not it is used. A scanner that does not record them omits the key, which means not recorded.
- **`foreign`**: external libraries, each a node with id `foreign:<name>`, which edges point at; `name` is what the policy's `foreign` groups match on.

The document is facts about the code only: no policy, layout, colours or violation flags. `check` computes violations from the scan and the policy. A repository with more than one language gets one scan per language; merging them is the consumer's job.

{
  "schema_version": 6,
  "scanner": { "name": "recognizer-scan-python", "version": "0.1.0" },
  "commit": "a1b2c3d",
  "modified": false,
  "files": [
    { "path": "shop/order.py", "hash": "<64 lowercase hex characters>" }
  ],
  "selection": {
    "extensions": [".py"],
    "skip_directory_names": [
      "__pycache__",
      "tests",
      "dist",
      "build",
      "node_modules",
      "site-packages"
    ],

### Toolchains and CI

Each part carries only its own toolchain; no part needs more than one language.

- `scanners/python/`: its own `pyproject.toml`, hatchling build, `requires-python >= 3.11`, uv for the dev venv and lockfile, ruff and pytest. Installable with `uvx` or `pipx`, so an audit needs no checkout.
- `scanners/typescript/` and `app/`: npm workspaces at the repository root, Node 22 in CI with `engines >= 22`, TypeScript 5.9, vitest, biome for lint and format. Prettier (`--prose-wrap=never`) and markdownlint-cli2 at the root for markdown only.
- `app/`: `app/src-tauri` with Tauri 2, Rust stable, edition 2021, `@tauri-apps/cli` in the workspace. CI installs the webkit2gtk system libraries and caches the Rust build.
- `schema/`: JSON Schema 2020-12. No separate validator job: each scanner's tests validate its fixture output against the schema (`jsonschema` in Python, `ajv` in TypeScript), so a schema edit is checked by every scanner.
- `scanners/kotlin/`: Python, uv, py-tree-sitter with the tree-sitter-kotlin grammar, laid out as the Python scanner is.
- `scanners/csharp/`: Python, uv, py-tree-sitter with the tree-sitter-c-sharp grammar built from its pinned commit, laid out as the Kotlin scanner is. Scanning needs no .NET SDK; the C.R.A.P. and mutation sensors need one on the machine that runs them, because they run `dotnet test`, with coverlet's collector writing LCOV per test project, its absolute paths mapped to repository paths and the reports merged. A test project without `coverlet.collector` fails with a message naming it.
- `scanners/rust/`: a standalone Cargo package (not in a workspace), Rust stable, edition 2021, `syn` with proc-macro2's `span-locations`; `cargo fmt`, `clippy` and `cargo test --locked` in its own workflow.

CI is one workflow file per directory, filtered on that directory's path plus `schema/**` and `fixtures/**`: a schema or fixture change runs every scanner, a scanner change runs only itself.

### Sensors

A scanner extracts structure and judges nothing. A sensor judges: it reads the structure, and whatever else it registers for, and writes findings. The viewer and the CLI read findings and know nothing about which sensor wrote them. Recognizer owns the findings format and the registration, as it owns the overlay format, and ships one sensor of its own.

- **What a sensor reads.** The repository's scans from the cache, the policy, the overlays in the cache, and the repository itself, including its git history. A sensor never builds, tests or runs the code it judges; a sensor that needs a measurement taken by running something measures it itself, and a sensor that reads another sensor's overlay reports nothing for the ids the overlay lacks. Because a sensor only reads, every sensor runs after every scan, in the CLI and in the app alike.
- **The structure sensor** ships with recognizer, as the library the viewer imports and the sensor `recognizer check` runs in-process. It reports the policy's violations and the warnings the Principles table derives from the graph alone, and computes the graph metrics. The warnings today are cycles, hubs (a hub is the god module: fan-in and fan-out both at or above `hub_threshold`), folder cycles (two folders that import each other through any of their modules), orphans (a module nothing imports that is not an entry point: a policy entry, a test file, an index-like file, a module its scanner marks as run rather than imported (Python: a package's `__main__.py` or a module with a top-level `__name__` guard), or a path the globs in `warnings.orphan.entry_points` name, filled by the repository from its manifests, which the sensor never reads), policy drift (a policy entry naming a path the scan did not find, and a scanned folder no policy layer covers), stable dependencies (a folder depends on a folder less stable than itself) stable abstractions (a folder farther than `distance_threshold` from the main sequence, named as in the pain zone or the useless zone) and unused exports (a member whose exported flag is true that no edge from another module names; off by default, because a library's exports exist for outside callers); it also computes the folder metrics (per folder: afferent and efferent coupling, instability, abstractness and distance, after Martin's package design principles); to come: untested modules (a module no test file imports, by the language's test-file convention). Each is a switch under `warnings`, on by default, with its threshold beside it. It is on unless the config turns it off, and its settings are `hub_threshold` (an integer of at least 1, default 10), `distance_threshold` (a number from 0 to 1, default 0.3) and a switch per warning under `warnings` (`cycle`, `hub`, `folder_cycle`, `orphan`, `policy_drift`, `stable_dependencies` and `stable_abstractions`, on by default, and `unused_exports`, off by default; `orphan` may instead be `{ entry_points: [<glob>, ...] }`).
- **Shipped sensors.** Beyond the structure sensor, recognizer ships its own sensors in the toolchain, in `sensors/`, beside the scanners and released with them, so the app, the CLI and the sensors never disagree about the findings format. They are written by this project, with the published tools that pioneered each judgement as references, never as dependencies: a sensor's behaviour must not change because an upstream project did. One command, `recognizer-sensors <name>`, runs any of them with the same placeholders a registered command takes, and the `sensors/` package is Python with py-tree-sitter and pinned grammars for every scanned language, laid out as the Kotlin scanner is, so one parser serves them all. A shipped sensor reports nothing for a language it cannot parse. The set, in the order they are built:
  - **Duplication**: near-identical functions, within and across modules. Each function's syntax tree is normalised (local names, literals and field names replaced; calls, operators and shape kept) into a set of structural fingerprints, and pairs are scored by Jaccard similarity over those sets, as Martin's dryer does; a pair above the threshold (0.82) with at least the minimum size is a warning on both modules, naming both functions with their line ranges as evidence. Reads the files only.
  - **CRAP**: Savoia and Evans's change-risk metric per function, `cc² × (1 − coverage)³ + cc`, as crap4j and Martin's crapper compute it. The sensor computes cyclomatic complexity from the tree itself and reads coverage from an LCOV file the registration names, written by the repository's own test run; it runs no tests. A function at 30 or above is a warning on its module, naming the function, its complexity and its coverage; a module with no coverage data has it reported as unknown, never as zero. The per-function numbers are also written as an overlay (complexity, coverage and crap at member granularity), so the viewer can paint them.
  - **Mutation**: one sensor that measures and judges in a single run. It runs the repository's tests under coverage itself, mutates each covered function (the Martin and clj-mutate operator set: boolean, comparison, arithmetic and logical swaps, skipping strings and comments), runs the test command against each mutant in a private copy, and writes an overlay of killed, survived and uncovered counts and the score per function, a survivors file, and a warning for each function with survivors, naming each surviving mutation and its line; a mutant that fails to compile counts as killed, and one that outlasts ten times the baseline run counts as killed by timeout. A rerun reuses the verdicts of a function whose body, covered sites and test command are unchanged (a changed test file forces a full run), an optional `max_minutes` budget leaves later functions unmeasured, and the app ticks a test-running sensor for one Scan only.
  - **Thresholds**: the judgement for any overlay metric. `sensors.thresholds` in the config names a metric, a line (`above` or `below`) and a severity (`warning`, the default, or `violation`), and the sensor writes one finding per module or member that crosses it, the threshold as its evidence and the metric named so the viewer can show it; the well-known metric names have defaults (complexity above 10, coverage below 0.6) and a metric a shipped sensor already judges (crap, survived) has none, so the CRAP and mutation sensors keep their own lines and the thresholds sensor covers the rest. A threshold violation ratchets in the baseline like any other.
- **Registration.** A repository registers further sensors in `.recognizer/config.yaml` under `sensors`, each with a name and the command that writes its findings, run from the repository root with `{repository}`, `{commit}` and `{output}` filled in, as an overlay's command is. The structure sensor is configured under the same key by its name, and `off` removes it. A sensor's settings are its own flags on its command line; the structure sensor's are keys under its entry. The findings document records the settings it was written with, so a report never needs the config to be read.
- **Running.** `recognizer scan` is one pipeline in three phases: extraction, which runs only when the files changed since the last scan, a scanner's version changed or there is no scan (`--extract` forces it); describing (`--describe`); and the registered sensors (`--sense all` or `--sense <name>,...`). The structure sensor runs with every scan whatever the flags, in the CLI and in the app, and the app runs it again when `policy.yaml` or `config.yaml` changes, without a rescan. A registered sensor runs only when asked, because its command is the repository's and running it is a deliberate act; the app's Scan panel is where that choice is made and remembered per repository. `recognizer check` runs the structure sensor, reads every current findings file and reports: it is the one command CI runs, after `recognizer scan --sense all` when CI wants the registered sensors too, and its exit code, baseline flags and output are as before. A sensor whose command fails or whose file does not match the format is reported by name, leaves no findings behind and fails the scan (exit 1): a skipped sensor would otherwise read as no violations. The app never runs a registered sensor on its own; it reads the files a scan left, stale-marked when their commit is not the scan's, and lists every sensor in the Scan panel and the footer as ran, stale, failed or not run.
- **An agent's review is reported, not run.** The findings a code review finds, interaction problems across modules, bugs, performance and security, come from reading the codebase as a whole, so recognizer never runs a reviewer per module or ships a review prompt. Instead any review an agent runs, a workplace skill in a Claude session included, reports its findings into recognizer unchanged: the session is told to report, the agent reads the guide, and hands over findings in the findings form with `recognizer report --as <name>`, from a file or stdin. The command validates the form, stamps the commit it was made at and the time, and writes the findings file under that name as if a sensor named it had run; the principle is whatever the review names, and the viewer treats the findings like any sensor's: the Findings panel groups them by principle, the disc takes the worst, the inspector card shows the summary, the reason and the lines, and a violation can be accepted into the baseline. A report has no command and no row to tick: the Scan panel's Sensors block lists it after the registered sensors as reported, with when and at which commit, and a Clear; a scan never runs or removes it. Once the scan has moved past the report's commit it is not current, named in the Findings panel's not-current line like a stale sensor, and nothing deletes it on its own: the next report under the same name replaces it. `recognizer check` reads a report like any current findings file and ignores a stale one.
- **The file.** One JSON file per sensor at `.recognizer/cache/findings/<name>.json`: `findings_version`, the `sensor` (name and version), `commit`, `modified`, the `settings` the sensor ran with, and `findings`; a shipped sensor writes version 2, which adds `inputs` (module id to the scan's file hash, for each module it measured) and, for a sensor that depends on test files, `tests` (a sha256 over the test files' paths and hashes). Each finding has a stable `id` (the same evidence gives the same id across runs, so the baseline can hold it), its `kind`, a `severity` of `violation` or `warning`, the `principle` it offends, a one-line `summary`, its `evidence` by scan id (the `modules`, and where they apply the `edges` with their lines and the `members`), and a `fix_pattern` where one is named. The structure sensor's ids are `rule-violation:<edge kind>:<from>-><to>` (the baseline identity as one string), `cycle:<sorted modules joined by ",">`, `hub:<module>`, `folder_cycle:<folder A>,<folder B>`, `orphan:<module>`, `policy_drift:entry:<glob>`, `policy_drift:folder:<folder>`, `stable_dependencies:<source folder>-><target folder>`, `stable_abstractions:<folder>` and `unused_exports:<module>`; a hub id omits the numbers so a threshold change that keeps the module a hub keeps the id. A violation is a verdict and fails a run through the ratchet; a warning is a candidate and never does. Metrics are not findings: the structure sensor writes them, folder metrics included, in the check report as it does today.
- **Freshness.** A findings file names the commit of the scan it read; one whose commit differs from the current scan is not shown, and its discs are not measured. A sensor run on a modified tree says so.
- **The baseline** ratchets violations across every sensor, keyed by finding id, at `.recognizer/baselines/violations.json` as before; the structure sensor's violation ids are the identities the baseline holds today, so an existing baseline keeps its meaning. A baseline entry is `{from, to, kind}` for a structure violation or `{id}` for a violation from any other sensor; the entries of the first form come first.
- **In the viewer and for agents.** The health discs, the inspector's Findings tab and the findings panel to come read every current findings file and show a finding with its summary, principle and evidence, never a number alone. `recognizer show` and `recognizer modules --findings` read the same files, and `recognizer check` is how an agent refreshes them.

### Principles

Hexagonal, clean and onion architecture are each one arrangement of the same few principles, drawn from Martin, Fowler, Evans, Parnas and Jackson. Recognizer works from the principles, never from a named architecture: a structural warning is a principle violation, reported as a candidate with its evidence attached, never as a verdict. The scan supplies the facts; the policy declares the intent the facts cannot carry.

| Principle | Warning | Needs from the policy |
| --- | --- | --- |
| Dependencies point toward stability | an edge from a more stable component to a less stable one; a component whose measured instability disagrees with its declared place | which components are meant to be stable |
| Depend on abstractions across a boundary | a concrete cross-boundary edge; a stable component that is mostly concrete | component boundaries |
| Policy code is isolated from mechanism | IO, environment, time or framework reached from policy code | which components hold policy, which foreign groups are mechanism |
| No cycles | a dependency cycle | nothing |
| Things that change together live together | co-change across a component boundary (from the git overlay) | component boundaries |
| Every dependence is justified by purpose | an edge no declared relationship requires | permitted dependencies between components |
| Each rule has one home | structural duplication (from the duplication overlay) | nothing |
| Interfaces are narrow and explicit | a hub with high fan-in and fan-out; a wide exported surface | nothing; candidates only |

Metrics derived from the scan graph alone (fan-in, fan-out, cycles, instability, abstractness, distance from the main sequence, and the same per folder as folder metrics) are structural facts and are computed by the structure sensor. Anything measured by running something (tests, mutation, duplication, git history) is measured by a sensor, which writes it as an overlay, and a sensor that judges it reads the overlay.

A named architecture is a policy template: a starter `.recognizer/policy.yaml` under `policies/` in this repository, copied into a scanned repository and edited there. Recognizer has no setting that names an architecture and never reads anything but the policy in front of it.

### Violations and warnings

Every sensor's findings are one of two kinds, and `recognizer check` reports both in one run:

- **Violations** are the policy's verdicts: an edge that breaks a rule the policy declares. The baseline ratchets them and CI fails on growth. Only violations affect the exit code.
- **Warnings** are heuristics: a threshold or pattern tied to one principle in the table above, reported as a candidate with its evidence. A warning is never baselined and never fails a run. Its thresholds are the sensor's settings, recorded in its findings file and printed in the output. A warning confirmed often enough is promoted to a rule in the policy; a violation baselined and never shrinking is a question about the policy.

Every warning carries what a coach needs and never the number alone: the principle it suspects, the evidence (the modules, edges and members that triggered it) and a stable fix-pattern identifier. A bare metric invites gaming the number rather than fixing the design; habit-hooks' pre-registered evaluation measured a genuine fix in under six percent of trials from a bare complexity message and over eighty percent from a coaching message naming the cue and the action. The coaching text itself lives outside recognizer: a habit-hooks plugin wrapping `recognizer check`, or a guidance entry keyed on the fix-pattern id, is a consumer of the format in the same loose relationship as an overlay converter. The plugin is a spike once warnings exist.

The baseline is keyed by finding id across the whole repository. A later item adds a change scope to `check`, reporting only what the modules touched on a branch introduce, which is what an agent loop acts on.

### Overlays

An overlay is the file a sensor writes for the measurements it takes. The `recognizer` command never measures: each sensor measures what it needs, as `recognizer scan` runs each language's scanner, and recognizer owns the overlay format, never a metric's meaning. The toolchain's shipped sensors each measure what they need and judge it in one run (Sensors, below); a repository registers no measurer, and a config that carries an `overlays` key is refused. Converters from other tools' native reports are separate tools with no dependency on recognizer beyond the format.

- **The file.** One JSON file per overlay at `.recognizer/cache/overlays/<name>.json`: `overlay_version`, `commit`, `modified` (true when the working tree had uncommitted changes), `producer` (name and version), `metrics`, and `values`; a shipped sensor writes version 2, which adds `inputs` and `tests` as in the findings file. Each metric declares its `name`, its `type` (`ratio`, `count`, `number` or `boolean`), its `granularity` (`module` or `member`), and which direction is bad (`bad: high` or `bad: low`). `values` maps each metric name to an object keyed by the scan's own ids: a module's id, or for a member the module's id, `::`, and the member's name, with a method as `Class.method`. A converter matches the scan's ids; the viewer never guesses. Well-known metric names have documented shapes but are not the only ones allowed.
- **Freshness.** An overlay names the commit it measured; one whose commit differs from the scan's is drawn as missing, and one from a modified tree says so. A module or member with no value is unknown. Missing data is unknown, never healthy.
- **Metrics in the viewer.** Overlays are numbers, and the canvas shows none until asked. Metrics, in the canvas controls before Legend (Legend is always last), opens a list of every metric of the current overlays, grouped by overlay with its producer and freshness; a metric from an overlay whose commit is not the scan's is listed stale and cannot be shown, and one from a modified tree says so. Any number of metrics are ticked. Each ticked metric adds a thin bar with its value to every box, in the order ticked; a member-granularity metric shows the box's worst member; hovering a bar names the metric, its value and the worst member; a module the overlay did not measure shows a dashed empty bar, unknown and never healthy; a folder box has no overlay value, so it carries the same bars in that unknown form; a boolean metric draws a track full for yes and empty for no, and its bad end says which is red. The list says which bar is which, its range and which end is bad; there is no key on the canvas. The disc never changes for a metric: it is the findings' alone. The Metrics list controls the canvas and nothing else: the inspector always shows every current metric, as a small table at the foot of each Contents member card and nothing in its header: a header row of short metric names (cc, cov, CRAP, mut, surv, otherwise the metric's name) and one row per function, a class card listing its methods by short name and a function card its one row, values right-aligned and coloured as the bars are, a dash for a member the overlay did not measure. Leading to the bad ones is the findings' job, through the thresholds sensor (Sensors).

How overlays are painted is decided under Overlays in the viewer.
