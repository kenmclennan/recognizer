# Glossary

The words recognizer's code, docs and interface use. A term is added here before it is used, and a term used differently from its entry is a defect in one or the other.

## The code being scanned

| Term | Meaning |
| --- | --- |
| Repository | The codebase being scanned: one git repository, possibly in several languages. |
| Module | One box: a source file. Identified by its repository-relative path. |
| Markup file | A `.razor`, `.cshtml` or `.xaml` file the C# scanner reads. It is not a module and has no box; the types it names become `depends` edges from its code-behind module, or from the nearest module that declares a type. |
| Crate | A Cargo package's library or binary target. The Rust scanner finds crates from `Cargo.toml` files, starts each module tree at the crate's root file and treats a crate in the repository, reached by a path dependency, as in-repo and any other as foreign. |
| Folder | A directory of the repository, as the tree shows it. Not a component: a folder is where files are, not what they are for. |
| Member | A class, function, interface, type or constant defined in a module. |
| Call | A member using another member: calling it, constructing it, or reaching it through an abstraction by dispatch. |
| Outline | What a member contains, read from its declaration: a class's bases, fields, methods and tags, a function's parameters and return type, a constant's value. |
| Class tag | One of `dataclass`, `frozen`, `final`, `runtime_checkable` or `abstract` on a class or interface, read from its decorators or modifiers and shown in Contents beside the class name. `abstract` is also set on a Kotlin `abstract class` and on a TypeScript type alias that can be implemented. |
| Abstract member | An exported member that can stand in for an implementation: an interface, an abstract class, or a type alias that can be implemented (a function or constructor type, or an object type declaring a method or call signature), as each scanner records it. Data shapes, literal and union types, mapped and utility types, constants, enums and ordinary classes are not. |
| Visibility | A Kotlin or C# member's declared access modifier: `public`, `protected`, `internal` or `private` (a C# `file` type is recorded as `private`). A member is exported unless it is private. |
| Unresolved import | A Kotlin import, or a C# `using`, whose name is declared in no scanned file but whose package or namespace is under an in-repo prefix, such as generated code. Recorded in the scan so it is never dropped silently. |
| Input file globs | The optional `selection` list of basename globs for the non-source files a scanner reads or probes wherever they sit, such as `package.json` or `build.gradle.kts`. The change view reports a new file whose name matches as added. |
| Absent paths | The optional `selection` list of repository-relative paths a scanner tried to read or probe and found missing, such as a Python repository's `setup.cfg`. The change view reports one that appears as added. |
| Skip paths | The optional `selection` list of repository-relative directories a scanner skipped for a reason a glob cannot express, such as a C# test project found by reading its `.csproj`. The change view treats files under them as unscanned, not added. |
| Dispatch | A call from an abstract or interface method to each concrete method that implements it, so a caller that reaches a port also reaches its adapter. |
| Trace | The calls followed from one member, which is how an agent finds what a feature touches. Never drawn on the canvas. |
| Name | A member's name as another module imports it. |
| Foreign library | Code outside the repository that a module depends on, such as `sqlite3`. |
| Source root | A directory under the repository that Python imports are resolved from, such as `src` in a src layout. The Python scanner reads the ones a repository declares, then the repository root; module ids stay repository-relative paths. |
| Script folder | A directory that holds no `__init__.py`. Python puts a running script's own directory on the import path, so the Python scanner resolves an import of a file beside a module in a script folder when no source root matches; a module inside a package never gets this. |
| Re-export | A module that makes another module's names importable from itself, such as a Python `__init__.py` or a TypeScript `index.ts`. |
| Dependency | An edge from a module to the module that defines a name it uses. |
| Declaration | A `mod x;` the Rust scanner records as a `declares` edge. It makes the child reached for the orphan check and is not a dependency. |
| Dependent | A module on the other end of a dependency: the one that uses. |
| Route | The re-exports a name passed through on its way from its defining module to the module that imports it. Stored as `via`. |
| Generic method | A method name too common to identify a class, such as `get`. The scanners ignore an untyped parameter whose called methods are all generic. |
| Inferred dependency | A dependency found from the methods called on an untyped parameter, not from an import. Always shown as inferred. |
| Composition root | The module that builds the object graph and wires adapters into what uses them; it reaches nearly everything. |

## Architecture

| Term | Meaning |
| --- | --- |
| Component | A named set of modules, declared in a policy by path. |
| Stratum | A horizontal layer of responsibility, such as domain, application or adapters. |
| Slice | A vertical cut through the strata that makes one use case or feature work, from the thing that drives it to the things it drives. |
| Policy | The one file a repository's owners write to declare components and the dependencies they may have. |
| Violation | An edge that breaks a rule the policy declares. Baselined; the only finding that fails a run. |
| Warning | A heuristic over the graph, tied to a principle and carrying its evidence. Never baselined, never fails a run. |
| Baseline | The recorded violations a repository has accepted for now; it may only shrink. |
| Scratch folder | A rebuildable folder under `.recognizer/cache/` (the Mutation work folder `mutation/work`, which holds the Warm-up copy and every Mutant copy). Results (overlays, findings, coverage, logs, Mutation's `survivors.json` and `record.json`, scans) are never scratch and stay backed up. |
| Overlay | Measurements a sensor writes (coverage, churn, mutation), as one file per overlay to `.recognizer/cache/overlays/` and painted onto modules and members. |
| Inputs | The `inputs` key of an overlay or findings file: each module the sensor measured, mapped to the file hash the scan recorded for it. Never recomputed from disk. |
| Tests hash | The `tests` key of an overlay or findings file from a sensor that depends on tests: a sha256 over every test file's path and hash, and over a hash of each test item inside Rust source files and of each file they declare, and each file those reach through `mod`, sorted by path. |
| Current result | A result (an overlay value or a finding) whose measured modules still have the hash `inputs` records and, for a sensor that depends on tests, whose `tests` matches the repository's present test files. Anything else is out of date and shown nowhere. |
| Result row | One result's line in the Scan panel's list: Structure (always run, not tickable), Descriptions, or one sensor. Every row is in one of five freshness states, with the same icon and wording in the list, the summary and the Findings line: current (with when), out of date (N modules), never run, failed (with when and a log link) or running (with done of total). |
| Incremental | The default mode of the Scan panel's mode toggle (Incremental or Full). The primary button names the work ("Update N modules", "Run `<names>`" or a disabled "Up to date"), and a run does only the out-of-date and missing work and keeps every current result. When no ticked row has work but some unticked rows are not current, the button is a disabled "Nothing ticked to run" and a hint names those rows; a click never ticks a row. |
| Full | The other mode of the Scan panel's mode toggle. The primary button reads "Rescan N modules"; that click reruns every ticked sensor over the scope, describes every module (`--describe=all`) and replaces the sensors' results; Mutation still reuses a verdict whose function body and covering tests are unchanged. The toggle only changes the primary's label and never runs anything; it is disabled while a scan runs. |
| Freshness model | The one module (`app/src/freshness-model.ts`) that computes every result row's state, the changed modules (the ones Structure reports changed), the modules an update brings current, the modules a sensor has no result for, the Scan panel's summary and primary button, the Findings panel's line, the footer's progress text and which canvas boxes read "changed". The Scan panel, the Findings panel, the canvas and the footer read it, so they cannot disagree; it only reads and never starts a run. |
| Excluded function | A function the Mutation sensor did not test because its file has no entry in the coverage report. It is counted in the findings document's `excluded` and listed with its module in `inputs`, so freshness treats the module as measured. |
| Unowned function | A function the Mutation sensor did not test because no configured suite's directory and language cover its file. It is counted in the findings document's `unowned` and listed with its module in `inputs`. |
| Metrics list | The canvas control, before Legend, that lists every metric of the current overlays and ticks the ones shown as bars on the boxes; it controls the canvas only. |
| Metric bar | A row on a module box, one per ticked metric the module has a value for, in tick order: a short label, a track, a fill in the tone colour and the figure; a member-granularity metric shows the box's worst member; hover names it. A folder box and a module the overlay did not measure show no row. |
| Thresholds sensor | The shipped sensor that turns any overlay metric over a configured line into a finding, a warning or a violation as `sensors.thresholds` says. |
| Report | A findings file an agent hands to recognizer with `recognizer report --as <name>` after a review it ran itself; listed with the sensors but never run by a scan, stale once the scan passes its commit, replaced only by the next report under the same name. |
| Responsibility | A module's generated one-line statement of what it is for, committed in `.recognizer/responsibilities.json` and current while its source and describer are unchanged. |
| Describer | The command a repository registers in its config to write responsibilities. |
| Describer registration | The `describer` key of the Config: the command to run, with `{repository}`, `{module}`, `{model}` and `{request}` filled in, and a version naming its prompt, recorded bare: the model is not part of it. A Config without one falls back to the Describer in effect. |
| Describing settings | The model, the Batch size and the Confirmation threshold, global to the user, held under `describing` in the app's `config.json`, seeded as `haiku`, 4 and 5 and edited in Settings; a scan from the app and one from a terminal read the same values. |
| Describe projection | The estimate printed before the describe phase starts any call: the number of modules, the input tokens (3 characters per token plus a fixed 900 per request), and the API-equivalent dollar cost at the selected model's price, unknown for a model naming no known family. It is never a share of a subscription limit. |
| Confirmation threshold | The `confirm_above_usd` Describing setting, in US dollars, API-equivalent, seeded 5. A scan started from the app asks before describing when the Describe projection is above it or its price is unknown; equal does not ask, and the app's answer reaches the scan through the Describe answer file, not stdin. The CLI never asks. |
| Describe answer | The file `.recognizer/cache/scan-running.answer.json` beside the run record, written by the app to answer the scan's describe confirmation and read by the scan that asked: `version`, the `run_id` it answers and `describe` true or false. There is one per run, the scan removes it after reading it, and a scan ignores one whose `run_id` is not its own. |
| Describe stop | The describe phase ending early with every line already written kept: on a provider usage or rate limit (describer exit status 75), or, as a fallback for a limit the describer does not recognise, when a whole Batch size of describer calls (at least 2) fail in a row. The modules not described stay missing or out of date, so the next scan describes them. |
| Batch size | How many modules are described at once; the describe phase keeps that many describer runs going. |
| Describer in effect | The Config's describer when it has one, otherwise the shipped `recognizer-describe-claude` with its prompt version, as `recognizer describe --describer` reports. |
| Current line | A Responsibility whose source hash, describer and version all match the module and the Describer in effect today; the model that wrote it is not compared. |
| Out of date | A Responsibility that is not a Current line: its module's source (the files the scan recorded for it), the describer command or the version has changed since it was written. |
| Unchecked | The status of a Responsibility that exists but whose Current line test cannot run, because no Describer registration exists or the module's source cannot be read. |
| Overlay registration | An entry of the Config's `overlays` key: an overlay's name, the command to run with `{repository}`, `{commit}` and `{output}` filled in, its Metric declarations and, optionally, `runs_tests: true` when it runs the repository's tests. |
| Sensor | A program that reads the scans, the policy, the overlays or the repository and writes a findings file; it never runs the code it judges. Recognizer ships the structure sensor and a repository registers others. |
| Sensor registration | An entry of the Config's `sensors` key: a sensor's name and the command to run with `{repository}`, `{commit}` and `{output}` filled in, or for the structure sensor its settings, or `off`. |
| Sensor progress | The message a sensor prints while it runs, which the CLI passes through `--json` and the app shows on the progress line. |
| Hub | A module that at least `hub_threshold` modules import and that itself imports at least `hub_threshold` modules. Its finding lists each importer with the names it takes (`used_by`) and the hub's size, so the reader sees what the importers use. |
| Orphan | A module no scanned module imports that is not an entry point; reported as an `orphan` warning. A module only test files import is still an orphan and is reported with its test importers. |
| Test import | A record of a test file importing a scanned module, written by a scanner from the test files it skips as `test_imports` (`from` the test file, `to` the module, `names` when known); the `orphan` and the `unused_exports` finding read it, and a test file is never a module. |
| Entry point | A module that need not be imported: one a policy entry names literally, a test file by convention, an index-like file (`index`, `__init__`, `main`, `mod`, `lib`) or one matched by a glob in `warnings.orphan.entry_points`, or a module its scanner marks as run rather than imported (Python: a package's `__main__.py`, a module with a top-level `__name__` guard or a module a `pyproject.toml` console script names; TypeScript: a file a `package.json` names in `main`, `bin`, `exports` (including a `*` pattern of a non-private package) or `scripts`, a `*.config.*` file, a file an HTML `<script src>` loads, or a file starting with a shebang; Rust: a Cargo target root, a file reached only through a module declaration gated by `#[cfg(test)]` or any `cfg` predicate that requires `test`, such as `cfg(all(test, unix))`, or a file whose own inner attribute is such a gate, as the [Rust scanner README](../scanners/rust/README.md) states; Kotlin: a file with a top-level `fun main`). |
| Actual file | A Kotlin file with a top-level `actual` declaration whose package and name an `expect` declaration in another file of the same build module also holds; its module carries `actual_of`, the ids of those expect files, and `recognizer check` counts it as reached whenever one of them is reached. |
| Policy drift | A policy entry that matches no scanned module, or a scanned folder no policy component covers; reported as a `policy_drift` warning. |
| Folder metrics | Per folder that holds scanned modules, Martin's package numbers computed from the scan and the policy alone: afferent coupling (modules outside that import modules inside), efferent coupling (modules inside that import project modules outside; imports of modules outside the scanned project count for neither coupling), instability, abstractness (the share of exported members that are abstract members) and distance. Written in the check report's `folder_metrics`, never as findings. |
| Main sequence | The line where a folder's abstractness plus its instability is 1. Distance is how far a folder is from it: `abs(abstractness + instability - 1)`. |
| Structure sensor | Recognizer's own sensor: the policy's violations, the warnings derived from the graph alone (cycles, hubs, orphans, policy drift, stable dependencies and, off by default, unused exports) and the graph and folder metrics. Its settings are the hub threshold, the instability gap, the composition roots and a switch per warning. On unless the Config turns it off. |
| Shipped sensor | A sensor recognizer writes and releases with the toolchain in `sensors/`, run by `recognizer-sensors <name>` and by `recognizer scan --sense <name>` whether or not the config registers it; a config entry carries settings only. One run measures what it needs and judges it: duplication, CRAP, mutation and thresholds. |
| CRAP sensor | The shipped sensor that runs the Test suites configured under `tests:` in `.recognizer/config.yaml` (never a built-in command or a `test_command`), scores each function `cc^2 * (1 - coverage)^3 + cc` from its cyclomatic complexity and the coverage of its lines, warns at or above `threshold` (30 by default) with the fix pattern `simplify-or-test`, and writes the per-function numbers as an overlay in the same run; a function with unknown coverage is never scored as zero. A failing test suite does not end the run: the results are kept and the document carries a Diagnosis of `tests-failed`, and when no coverage can be produced the sensor reports complexity alone with a Diagnosis of `coverage-unavailable`. |
| Diagnosis | The one object (`code`, `line`, optional `fix`, optional `failing` with `count` and at most five `names`) that says why a sensor could not do everything it was asked to. `code` is `tool-missing`, `tests-failed` or `coverage-unavailable`; `line` is the complete one-line sentence with the fix in it. A completed C.R.A.P. run carries it in the findings document, a Refusal carries it on the `recognizer-reason` stderr line, and the run log entry records it. |
| Preflight | The check `recognizer scan` makes after the scan marker is held and before the describe and sense phases, that everything the ticked sensors and the describer need is in place. It has two stages: an early stage before extraction (a commit, the describer and its arguments, `recognizer-sensors`) and a project stage after it, which is each ticked sensor's Readiness check. It runs no tests, spends nothing and installs nothing. Any Gap means nothing runs, and the scan exits `4`. |
| Readiness check | A sensor's own answer to whether it can run: `recognizer-sensors <name> --check`, which prints the gaps it finds as plain sentences and exits `0` either way. `recognizer sensors check [name]` asks each sensor that is not off and relays what they say, exit `1` while any gap remains; `--run` also runs each test suite once. The core knows nothing of tests, languages or tools, and nothing is installed or fixed: a person or an agent installs what is missing and checks again. |
| Readiness note | A sensor's remark from a readiness check that is not a Gap: it never blocks a scan, never changes `ready` and never changes the exit code. Today it names how many scanned files a ready suite's coverage report covers (`coverage-partial`), shown by `recognizer sensors check --run`. |
| Setup guide | The text a sensor supplies for setting it up (`recognizer-sensors <name> --guide`, printed by `recognizer help sensors <name>`): the tools it requires, how to find how the developers run their tests, how to write the suites, and to re-run the readiness check until it is clean, never installing anything without the human's say-so. |
| Gap | One missing or unusable thing a ticked sensor or the describer needs, as the Preflight reports it: an `id`, the `line` that says what is missing (for a sensor, its own sentence), the sensors it `needs`, the `project` it is in, and a `fix` (its text, command, folder, environment and whether it is `repository` or `outside`). The Scan panel shows a gap's line and the sensors it needs, never a fix; for a sensor's gap it adds one help line pointing at that sensor's setup guide. |
| Refusal | The end of a sensor run that cannot proceed for a toolchain cause (a red suite before Mutation, no coverage for Mutation, a test program that does not start): the sensor writes no document, exits `2`, and prints the `recognizer-reason` line with its Diagnosis, then the plain `line`. |
| Cyclomatic complexity | One plus the branch points in a function's own body (conditions, loops, match arms, catches, the boolean operators "and" and "or", and in TypeScript the nullish and optional-chain operators), counted from the syntax tree. |
| Duplication sensor | The first shipped sensor: it reports each duplication family, and so each pair, of functions in the same language whose structural fingerprints are alike (Jaccard similarity at or above `threshold`, 0.82 by default) as one `duplication` warning on every member's module, with the fix pattern `extract-shared-function`. A pair needs its shorter member at `max(min_lines, pair_min_lines)` lines (`pair_min_lines` 6 by default); a family keeps the `min_lines` floor of 4. |
| Duplication family | A set of functions linked by over-threshold pairs (the connected component of the pair graph), reported as one finding listing every member; its similarity is the lowest linking pair's, and a plain pair is a family of two. A family of three or more methods in one file under one qualified-name prefix reads "N methods of Class share one structure". |
| Lines duplicated | The sum of a duplication finding's members' line counts, the figure duplication findings are ranked by, largest first, in `recognizer check` and in the Findings panel. |
| Structural fingerprint | The set of SHA-1 hashes of every subtree, cut at depth 3, of a function's normalised syntax tree (local names, parameter names, field names and literals replaced by kind tokens; call names, operators and shape kept); two functions are compared by the Jaccard similarity of their sets. |
| Mutation record | The file beside the survivors file in which the Mutation sensor keeps, per function, a hash of its body and, per mutation site, the verdict, the test files that ran it and its Killer, each with its hash, with a hash of the Test suites and of the Test support files; a rerun reuses each site on its own while its function's body and the files that bear on it are unchanged, and runs the rest. |
| Killer | The test files the runner reported failing for a mutant that was killed, with the `conftest.py` files on their paths; a killed site is reused while the hash of every Killer file is unchanged. |
| Test support files | The test files that are neither a test entry nor a `conftest.py`, such as helpers and data under a test directory; the Mutation record keeps one hash of them, and any change to it voids all reuse because the sensor cannot say which tests use them. |
| Budget | A Mutation sensor's `max_minutes` ceiling, counted from the first mutant (the coverage pass is outside it): no function starts once it is spent, and a function left unstarted is skipped, absent from the overlay and listed in the survivors file as `uncovered-by-budget`; the next run queues it first. |
| Stopped run | The Mutation run Stop ended: it keeps every function whose mutants all finished, lists the rest as skipped in the record and the survivors file, and says so in its findings document through the root key `stopped`, which the Scan panel reads as `stopped, <n> of <m> functions measured`. Its record keeps the previous verdicts of the functions it did not reach, wherever their keys still match. |
| Partial result | A Mutation run that measured fewer functions than it considered, from a Budget or a Stop, recorded in its findings document under the root key `partial` and shown in the Metrics panel as `Partial: <n> of <m> functions measured`. A complete findings document of a sensor that counts functions carries `counts: {measured, total}`, and a run's record keeps the verdicts of functions it did not reach, whether a stop or a Budget ended it. |
| Checkpoint | A write of everything a sensor has settled so far (overlay, findings document and any record it resumes from) while it still runs. The findings document is marked `partial`, so a run that fails, times out or is stopped keeps it as its visible result and the next run resumes from it. A checkpoint never replaces a complete output that measured more functions, whichever commit that output is for, by `counts`, `stopped` or `partial`; an equal count replaces it, and an output with no count is not protected. |
| In-file test hash | The digest of a Rust lib or bin target's unit tests - the test items - `#[test]` or an item gated by a `cfg` predicate that requires `test`, as the [Rust scanner README](../scanners/rust/README.md) defines a test gate - found by walking its module tree from the root file - which the Mutation sensor joins to the killer and ran sets, so an edit to an in-file test reruns the sites that target's unit group covers; the walk follows `#[path]`, and a module with no file takes a digest of every `.rs` file under the root file's directory instead. |
| Test selection | The Mutation sensor's choice, per mutant, to run only the tests that cover its site instead of the whole suite, with only the tools each language mandates: Python runs the test files whose per-test contexts executed the line; TypeScript runs the runner's own related-files selection (`vitest related` or `jest --findRelatedTests`); Kotlin, C# and Rust run the test classes or targets a per-class or per-target Warm-up copy run attributed to the line. A selection of more than half the suite runs the whole suite instead, and a language with several suites or a suite outside the repository root runs the whole suite. |
| Test suite | An entry of the Config's `tests` list: its name, language, directory, command, optional activation and environment, and the coverage report it leaves. The CRAP sensor runs each one in the user's login shell from its directory and reads the report it names. |
| Mutation sensor | The shipped sensor that runs the tests under coverage, mutates the covered functions, runs the tests against each Mutant and warns, per function with a Survivor, with the fix pattern `strengthen-tests`; in the same run it writes the overlay of killed, survived and uncovered counts and a score, the survivors file and the Mutation record, reusing an unchanged function's verdicts and stopping at a Budget. |
| Mutant | A single token of a covered function replaced by its one counterpart (`>=` by `>`, `and` by `or`, `true` by `false`), written into a Mutant copy and run through the Test suite's login shell. A failing, unstartable or timed-out run kills it. |
| Mutant copy | The per-worker copy of the repository, made of the git-listed files and the folders on the Carry list, reset to its tracked state before each Mutant. It lives in the Scratch folder until the run ends or it is retired after a timeout or a failed reset. |
| Carry list | The `carry` setting under `sensors.mutation`: the exact untracked repository folders (such as `frontend/node_modules`) a copy takes, with no built-in list; a folder not listed is not in the copy. |
| Warm-up copy | The one copy of the repository the Mutation sensor runs each configured Test suite in before any Mutant, to read its coverage and its per-test contexts; the warm-up also measures the Run memory. |
| Run memory | The peak resident memory of the process tree of one test run, measured during the warm-up and used to size the default worker count. |
| Survivor | A Mutant whose test run passed: the tests did not notice the change. |
| Producer | The tool that wrote an Overlay file, named with its version in the file's `producer`. |
| Metric declaration | A metric's `name`, `type`, `granularity` and `bad` direction, registered in the Config and repeated in the Overlay file. |
| Config | A repository's committed `.recognizer/config.yaml`, which registers its overlays and holds its other recognizer tooling settings. The policy is separate. |
| Config key | A dotted path that addresses one scalar or one list of scalars in the Config, as `recognizer config` takes it: `sensors.mutation.max_minutes`, or `tests.<name>.command` for the list entry whose `name` is `<name>`. |
| Key schema | The document an owner publishes listing the Config keys it owns, described by `schema/config-keys.schema.json` and merged by `recognizer config` and `recognizer help config`. |
| Command table | `COMMANDS` in `check/src/commands.ts`: the one list `recognizer` dispatches from and generates its help from. |
| Freshness | Whether the cached scans can be used: they were taken at the current commit from a clean working tree, and the scanned files still hash the same. Otherwise `recognizer scan` runs first. |
| Scanner | A language's standalone command that emits a scan. |
| Toolchain | The `recognizer` command, the scanners and the app, versioned and installed together. Out of step: a tool the app is about to run reports a version other than the app's own; the app refuses the scan and names both versions and the fix. |
| Bundled toolchain | The folder inside the app, `Contents/Resources/toolchain/commands`, holding one entry per shipped command; a packaged app runs its tools from it by absolute path and never through `PATH`. |
| Nothing ran | A scan that exited without error but ran none of a phase the user asked for (describe, measure or sense), reported with the reason instead of shown as finished. The reason is derived from the run record's `ran` and `commit`, whoever started the scan; a record whose `ran` is null (no summary was written) is a failure, never Nothing ran. |
| Scan | The document a scanner emits: modules, edges and foreign nodes for one language, the files it read and the selection it used. |
| Scanned file | A file a scanner read, recorded in the scan's `files` with the SHA-256 of its bytes. The files include the manifests, pages and configs read to decide modules, edges or entry points, not only source. |
| Selection | A scanner's rule for choosing files, recorded in the scan as data: extensions, skipped directories and skipped file globs, and the non-source files it reads by name or path. A consumer applies it to a path the scan has not seen. |
| Baseline | What the viewer holds of a scan's files: each file's recorded hash and the scan's selection, including its input file globs and absent paths, with the commit and branch taken just before the scan. Changed since compares the folder against it. |
| Changed since | The viewer's report of what differs from the scan on screen: an edited, added or deleted file the scanners read, or a moved commit or branch. An edit undone again does not count. |
| Rescan | Running the scan again on request, from the Scan panel, File > Rescan or Cmd-R. It keeps the view state, and a run whose structure is unchanged updates the open view without rebuilding it; nothing rescans on its own. |
| Update in place | Handing a run's new sensor results, findings and notices to the open explorer without rebuilding it, so the canvas, camera, selection, inspector and left panel stay as they were. It applies when the scan's modules and scan documents are unchanged; a structural change rebuilds the explorer and carries the camera. |
| Cache | A repository's gitignored `.recognizer/cache/`, where scans and overlays are written. |

## The viewer

| Term | Meaning |
| --- | --- |
| Tree | The left area: the repository's folders and files, each with its health disc. The way in. |
| Canvas | The centre area: the modules the user has opened, inside their frames, and the edges between them. |
| Inspector | The right area, closed by default: what is in the selection, its findings, or an edge's evidence. |
| Frame | The box on the canvas for exactly one folder, which may be a compacted folder, labelled with its joined path, holding that folder's open modules and the frames of its open subfolders. |
| Compacted folder | A chain of folders that hold no scanned file and exactly one subfolder, merged with the folder that ends the chain and identified by that deepest path; it is one frame on the canvas and one row in the tree, labelled with the joined path. |
| Open | On the canvas. A module is opened from the tree or by following an edge, and closed the same way. |
| Selection | The one module, folder or edge the user has picked, highlighted in the tree and shown in the inspector. |
| Selection bar | The small bar of icon actions shown above the selection while the pointer is over it; right-clicking opens the same bar. |
| Settings | The app's own preferences (the editor), set in its settings window; distinct from a repository's Config. |
| Describe phase | The second phase of a scan, run when ticked: the modules whose line is missing or out of date are described; progress shows in the footer's scan line and the result is a message in the message tray. |
| Run log | The record of one run of a registered command (scan or describe, and measure in records written before measurers were retired; a scan record holds its extract, describe and sense phases) under `.recognizer/cache/log/`, read with `recognizer log`; the last fifty are kept. |
| Scan marker | The file `.recognizer/cache/scan-running.json` with its `scan-running.progress.jsonl` of event lines beside it: together the run record of the current Scan run. The pair is replaced by the next run rather than removed at its end, and a `checking` or `running` record is stale only while its process is not alive (a reader then shows it `stopped`); an unreadable or older-version file is not live. At its end the record also carries `commit` (the commit the scan used, or null when the folder has none) and `ran` (the phases that held at least one entry, null when the scan wrote no summary), which is what a reader needs to tell what ran. While a record is live a second scan refuses with exit code 3. The record is version 4: `failure.reason` is the failure text for every scan, bounded at 8192 characters (the last 8192 are kept), written by the CLI whoever started the scan, from the failed entry or from the error the scan threw. |
| Scan run | One scan of a repository, from its start to its end. There is one current run per repository, read from the run record (the Scan marker) whoever started it, the app or `recognizer scan` on the command line. Its phases are `checking` (the Preflight), `refused` (with its Gaps) or `running`, then `finished`, `failed` or `stopped`. Only `recognizer scan` writes the record; the app reads it. |
| Editor | The program Open in Editor launches, named in Settings as blank (the system default), an app's name or a shell command; a shell command may use `{file}` and `{line}` placeholders, for example `code -g {file}:{line}`, to open at a line. |
| Picker | The inspector's Dependencies tab: its Uses and Used by sections list what the selection uses and what uses it, grouped by folder, to put on the canvas. |
| Eye | The 16px icon at the right end of a module or folder row that shows whether the module is on the canvas and puts it on or takes it off (half for a folder with only some files on); it does nothing else. |
| Trail | The inspector panels opened by following modules through their Dependencies, one to the right of the next, with breadcrumbs naming each step. |
| Strip | A narrow vertical column naming a trail panel that is folded out of view, to the left of the shown panels or, once an earlier one is brought back, to their right. Clicking it brings the panel back. |
| Breadcrumbs | The row above a trail's panels naming each module in the trail and each step's relationship (uses or used by), with the route icon that puts the whole trail on the canvas at its end. |
| Fold | Drawing an open folder as one box, which keeps its health disc and takes the edges to anything inside it. |
| Contents | A module's members as cards in file order, or a folder's files. |
| Card | A member shown in Contents with its label, line and code. |
| Function length | The span from a function or method's first line to its last, shown on its inspector card as `N lines` with a bar scaled to the module's largest, banded neutral at 20 lines or fewer, long (amber) from 21 to 50 and red over 50. An indicator, not a finding: each codebase's own linters own code-quality rules. |
| Show private | The remembered switch that adds non-exported members and private fields and methods to Contents. |
| Health disc | A dot on each file, folder and box: green fine, amber a warning, red a violation, a grey ring not measured. A folder shows the worst inside it. |
| Finding | A violation or warning a sensor wrote for the current scan: a stable id, a kind, a principle, a one-line summary, its evidence by scan id and, where one is named, a fix pattern. Attached to the modules in its evidence; a health disc shows the summary. |
| Needs attention | The tree filter that keeps only modules with an amber or red disc. |
| Focus | Narrowing the canvas to one folder's files. |
| Legend | The panel on the canvas, opened from its bottom-right controls, that names every edge style, every disc and what a frame's figure counts, and holds the inferred-edges switch. |
| Box | What the canvas draws for a module, or for a folded folder: its disc, its name and, when it has a note, its note mark. |
| Box description | The small panel that fades in directly under a hovered canvas box, as wide as the box, showing the module's one-line description from the describer; a box with no description shows none. |
| Private-name import | An import of a name the target module does not export. Drawn dashed. |
| Evidence | Why an edge exists: the quoted source line, the names, the route, or what an inferred edge was inferred from. |
| View state | Everything that decides what the user sees, as one record. Each change makes a new one; it lasts only as long as the window. |
| History | The sequence of view states the user has moved through in a window; back and forward walk it. It is never saved. |
| Rail | The thin strip of icons at the window's far left, one per left-hand panel; an icon opens its panel, or closes it when it is open. |
| Files panel | The rail's panel holding the tree. |
| Saved view | A named view committed at `.recognizer/views/<name>.json`: its title, its description, the commit it was saved at, its steps and its notes. |
| Modified view | A saved view whose canvas contents differ from its saved file, shown by the muted "modified" beside its name; panning and zooming do not count. |
| Revert | The view bar's button that restores a modified saved view's saved contents and camera, with Undo, or only the camera when that is all that moved. |
| Unsaved-changes dialog | The dialog, centred over the window on a dimmed backdrop, that asks whether to save a modified view before Clear or opening another view closes it. |
| View title | The optional heading text of a saved view, separate from its name. |
| View details card | The card under the view bar, or in place of a Views panel row, that edits a view's name, title and description together, with Cancel and Save. |
| View heading | The title and description of a saved view, drawn centred above the diagram and moving with it. |
| Change view | A saved view that holds a git range (base..head), re-diffed when it opens; the diff's modules are on the canvas marked added, modified or removed. |
| Plan | A saved view marked `plan: true` that shows what is intended before the code exists: its modules may carry a proposed change, and it has no change range. A view is never both a plan and a change view. |
| Proposed change | What a plan says will happen to one module: new, changes, moves, moves and changes, or removed. It is the view file's `proposed` entry, the `--change` kind on `views add` and `views change`, and a coloured border on the canvas. It is not the range of a change view. |
| Planned module | A module a plan names with a proposed change of new, moves or moves and changes that the scan does not hold. It has a box, takes a note and never makes the view stale. |
| Ghost box | The dashed box a plan draws at the old path of a moved module, reading "moving to" the new folder, with a dashed arrow to the module's new box. It is not a module: it takes no note and cannot be selected. |
| Member reference | How a plan names one member: `module#Name` for a function, class or other top-level member, or `module#Class.method` for a method. The module is everything before the last `#`. It is the argument of `views add`, `views change` and `views remove` and, split into `module` and `member`, a `proposed` entry in the view file. |
| Member mark | The coloured band and icon on the right edge of a member's row in the inspector's Contents: a plus for new or added, a triangle outline for changes or modified, a minus for removed. A plan's marks come from its member entries, a change view's from its git range. Marks never show on the canvas. |
| Stale view | A saved view the list shows under Stale with Delete: a change view whose head is merged or whose branch is gone, or any view with a pick that no longer resolves. |
| Views panel | The left-column panel, behind the rail icon between Files and Notes, that lists every saved view: live ones, then stale ones, each with Edit and Delete (stale ones only Delete); opened from the view bar's All views link. |
| Note | The one text a person or an agent attaches to a module or folder in a saved view, with the name of who last wrote it; writing again replaces it. |
| Notes panel | The left-column panel, behind the rail's speech-bubble icon, that lists every noted box and folder in the view, numbered and in reading order with a drag handle on each row, and focuses the selected note; the overview, with no composer. |
| Note bubble | The speech bubble hanging from a box's or folder's note mark that holds its one note, who last wrote it, Edit and Remove, and its number, "n of N", and Previous and Next that pan the canvas to the next box with the bubble kept where it is; the place notes are read and written, opened from the mark, the bar's notes button or N. |
| Note mark | The small outlined speech-bubble icon after a noted box's name or at a noted frame's corner; clicking it opens the bubble. |
| Note focus | A module selection with its note bubble open; kept while the noted box stays selected, cleared by any other selection or Escape. |
| Scan panel | The left-column panel, behind the Scan rail icon, that shows one list of Scan rows and one Scan button, with the ticks a repository remembers. |
| Scan row | One entry of the Scan panel's list: a checkbox, a name and a state in words (not yet run, a count with an age, running, waiting, or failed). |
| Scope (Only this view) | The Scan panel's switch, shown only while a view is open and remembered with the row ticks. When it is on, a run describes only the view's stale modules and mutates only the functions of the view's modules; C.R.A.P. and Duplication still cover the whole repository; in a plain run the Mutation list is the union of the out-of-date and missing modules. `recognizer scan --modules <file>` takes the module ids as a JSON array and applies the same scope. |
| Suite tick | A checkbox beside one Test suite under C.R.A.P. or Mutation in the Scan panel, remembered per repository and per sensor. A scan runs only the ticked suites of an armed sensor and keeps every other suite's last result; a suite new to the Config starts ticked. The sensor's own tick is tri-state (off, some, all) and still clears after every scan. |
| Suite fold | The chevron under C.R.A.P. and Mutation in the Scan panel that lists every Test suite with its Suite tick, result and short age. It is closed by default, whether it is open is remembered per repository, and a closed fold's row summarises the ticked suites. |
| Suite record | The file `.recognizer/cache/suites/<sensor>.json` in which C.R.A.P. and Mutation keep, per Test suite, when it last ran, its status, its counts, the hashes of the sources and tests it ran over and, for C.R.A.P., its coverage part. Only the sensors read it; a partial run composes the sensor's whole result from it. |
| Phase | One of the parts of a scan: extraction (when the files changed), describing (when ticked), measuring (CLI only, when asked for) and the sensors (when ticked). |
| Findings panel | The left-column panel, behind the Findings rail icon: a heading with one muted count line, then one collapsible group per finding kind, each holding cards. |
| Finding group | One collapsible kind in the Findings panel, named by the kind, a report or an unknown kind: a chevron, a severity dot, the name, an info icon when the group has help, and its count. Collapsed until clicked. |
| Finding group name | The plain name a built-in finding group shows, beside the finding kind it holds: `rule-violation` Breaks the policy, `cycle` Import cycle, `hub` Hub, `orphan` Orphan, `policy_drift` Policy out of step, `stable_dependencies` Depends on less stable code, `unused_exports` Unused exports, `duplication` Duplicated code, `crap` C.R.A.P., `mutation` Mutations, `thresholds` Over a limit. The names and the group help live in `app/src/finding-groups.json`, the one file the panel reads. |
| Group help | The two plain sentences a finding group can carry, "What it means" and "What to do", shown in a tip when the info icon beside the group name is hovered or focused. A reported group and an unknown kind have none and show no icon. |
| Finding card | A finding in the panel or in the inspector's Findings tab: the subject in bold, its folder muted beneath it and one plain sentence; opened inline to a row per module, member or edge involved, with Add to view on a row whose module is off the view. |
| Finding focus | One finding card open: the evidence lit on the canvas and the rest dimmed, with no selection and no box added. Cleared by Escape, by clicking the open card, or by selecting a box outside the evidence. |
| Description | A saved view's required one- or two-sentence statement of what it shows. |
| Step | One entry in a saved view, replayed on opening: a pick, a rule, a fold, a focus, or a module left out. |
| Pick | A step naming one module by path. Everything the user adds in the app is recorded as picks. |
| Rule | A step naming a relationship (a folder's files, what a module uses or is used by), re-evaluated on every opening. |
| View drift | What the tray message about a saved view reports when the view is compared with the current scan: a pick that is missing, changed relations, or newly relevant modules. |
| Left out | A step recording that a rule put a module on a view and the user took it off. A pick is never removed by a left-out; only modules a rule contributed are. |
| Resolution | A view's steps evaluated against a scan: the modules, folds and focus they give, and the steps that name a path that is gone. |
| Link | A `recognizer://open?repo=<absolute path>[&view=<name>]` address of a repository and, optionally, one of its saved views. Opening one opens the folder and the view, or focuses the window already showing the folder; it never runs a command, scans, describes or writes. |
| Window id | The `w-<n>` label the app gives a window, which `recognizer windows` lists and `recognizer window <id>` takes. |
| App socket | The per-user local socket, `app.sock` in the app's config folder, through which the `recognizer` command reads the running app. |
| Agent change | A view-state change made through `recognizer window <id> <verb>`, carrying `--by`. It is one ordinary history step, so one Back undoes it. |
| Message | A kind (warning, error, done or info), one sentence, a time and at most one action (Upgrade, Show or Undo), held in the message tray. |
| Message tray | The popover the footer's bell opens: per window, in memory only, newest message first, with a badge on the bell counting the unread. |
| Toast | A new message shown above the bell for 3.5 seconds, then only in the message tray. |
| Mark | Who made a history entry and what the change was, kept beside it so Back and Forward can name the agent's entries as the agent's. |
| View bar | The control group at the canvas's top left: back and forward over the history, the open view's name with the saved views to open, Save and Copy link. |
| Agent guide | The text `recognizer help agents` prints: how an agent answers show-me, extend, explain and drive requests, which commands to use and that `.recognizer/` is off limits. Its command section is generated from the command table. |
| Agent install | What `recognizer agents install` writes into the user's Claude folder: a skill that only points at the agent guide, and a permission rule denying Read and Edit of `**/.recognizer/**`. `uninstall` reverses it. |
