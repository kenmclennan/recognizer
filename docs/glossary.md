# Glossary

The words recognizer's code, docs and interface use. A term is added here before it is used, and a term used differently from its entry is a defect in one or the other.

## The code being scanned

| Term | Meaning |
| --- | --- |
| Repository | The codebase being scanned: one git repository, possibly in several languages. |
| File | One box: a source file, identified by its repository-relative path. The JSON keys and schema names `modules` and `module`, and code identifiers, keep the word module. |
| Sealed hierarchy | A type tagged `sealed` and its direct subtypes (the files whose `inherits` or `implements` edges name it): one unit for the cycle check, because the language keeps the subtypes beside the base and the base names them. Edges inside one never make a cycle, and a cycle through one is reported without them. |
| Markup file | A `.razor`, `.cshtml` or `.xaml` file the C# scanner reads. It is not a box; the types it names become `depends` edges from its code-behind file, or from the nearest file that declares a type. |
| Crate | A Cargo package's library or binary target. The Rust scanner finds crates from `Cargo.toml` files, starts each file tree at the crate's root file and treats a crate in the repository, reached by a path dependency, as in-repo and any other as foreign. |
| Folder | A directory of the repository, as the tree shows it. Not a component: a folder is where files are, not what they are for. |
| Member | A class, function, interface, type or constant defined in a file. |
| Call | A member using another member: calling it, constructing it, or reaching it through an abstraction by dispatch. |
| Outline | What a member contains, read from its declaration: a class's bases, fields, methods and tags, a function's parameters and return type, a constant's value. |
| Class tag | One of `dataclass`, `frozen`, `final`, `runtime_checkable` or `abstract` on a class or interface, read from its decorators or modifiers and shown in Contents beside the class name. `abstract` is also set on a Kotlin `abstract class` and on a TypeScript type alias that can be implemented. |
| Abstract member | An exported member that can stand in for an implementation: an interface, an abstract class, or a type alias that can be implemented (a function or constructor type, or an object type declaring a method or call signature), as each scanner records it. Data shapes, literal and union types, mapped and utility types, constants, enums and ordinary classes are not. |
| Visibility | A Kotlin or C# member's declared access modifier: `public`, `protected`, `internal` or `private` (a C# `file` type is recorded as `private`). A member is exported unless it is private. |
| Unresolved import | A Kotlin import, or a C# `using`, whose name is declared in no scanned file but whose package or namespace is under an in-repo prefix, such as generated code. Recorded in the scan so it is never dropped silently. |
| Input file globs | The optional `selection` list of basename globs for the non-source files a scanner reads or probes wherever they sit, such as `package.json` or `build.gradle.kts`. The change view reports a new file whose name matches as added. |
| Absent paths | The optional `selection` list of repository-relative paths a scanner tried to read or probe and found missing, such as a Python repository's `setup.cfg`. The change view reports one that appears as added. |
| Skip paths | The optional `selection` list of repository-relative directories a scanner skipped for a reason a glob cannot express, such as a C# test project found by reading its `.csproj`. The change view treats files under them as unscanned, not added. |
| Dispatch | A call from an abstract or interface method to each concrete method that implements it, so a caller that reaches a port also reaches its adapter. |
| Trace | The calls followed from one member, which is how an agent finds what a feature touches. Never drawn on the canvas. |
| Name | A member's name as another file imports it. |
| Foreign library | Code outside the repository that a file depends on, such as `sqlite3`. |
| Source root | A directory under the repository that Python imports are resolved from, such as `src` in a src layout. The Python scanner reads the ones a repository declares, then the repository root; file ids stay repository-relative paths. |
| Script folder | A directory that holds no `__init__.py`. Python puts a running script's own directory on the import path, so the Python scanner resolves an import of a file beside a file in a script folder when no source root matches; a file inside a package never gets this. |
| Re-export | A file that makes another file's names importable from itself, such as a Python `__init__.py` or a TypeScript `index.ts`. |
| Dependency | An edge from a file to the file that defines a name it uses, other than a name it uses only as a supertype; a supertype is an `inherits` or `implements` edge instead. |
| Extraction | One language's scan run: the scanner, commit, dirty state, selection and scanned-files list. It holds what is true of a run and not of a file. |
| Declaration | A `mod x;` the Rust scanner records as a `declares` edge. It makes the child reached for the orphan check and is not a dependency. |
| Dependent | A file on the other end of a dependency: the one that uses. |
| Route | The re-exports a name passed through on its way from its defining file to the file that imports it. Stored as `via`. |
| Generic method | A method name too common to identify a class, such as `get`. The scanners ignore an untyped parameter whose called methods are all generic. |
| Inferred dependency | A dependency found from the methods called on an untyped parameter, not from an import. Always shown as inferred. |
| Composition root | The file that builds the object graph and wires adapters into what uses them; it reaches nearly everything. Each surface has one a behaviour test goes through. |
| Behaviour test | A test that drives a surface through its composition root with fakes only at the outermost ports. |

## Architecture

| Term | Meaning |
| --- | --- |
| Stratum | A horizontal layer of responsibility, such as domain, application or adapters. |
| Slice | A vertical cut through the strata that makes one use case or feature work, from the thing that drives it to the things it drives. |
| Core | The package `@recognizer/core`: the domain, the ports and the use cases, with no knowledge of the CLI, the app, the file system or any process. Adapters depend on it, never the reverse. |
| Use case | One thing a person asks recognizer to do, such as Scan, written once in the core as a flow over ports. |
| Port | An interface a use case uses to reach the world outside core, such as Scan, Scanners, Sensors, Describer, Git, Scan lock, Confirm, Clock or Process. It lives with the subdomain that uses it; an adapter implements it for real and a fake implements it in tests. |
| Entity repository | An interface the domain owns through which one aggregate is stored and read: structure, findings, policy, config, run log or baseline. A filesystem adapter implements it; a fake implements it in tests. |
| Subdomain | One responsibility of the application layer, such as scanning, describing or sensing, with its own use cases and ports in one folder. |
| Running scan | What the Scan port returns: a stream of typed events, a final outcome and `stop()`. |
| Policy | The one file a repository's owners write: the entries to ignore, the entry points and the forbid rules. |
| PolicyRule | A statement the user makes in the policy: one forbid entry, one ignore glob or one entry glob. |
| Violation | A file's imports that break one rule the policy declares, reported as one finding. Baselined per import; the only finding that fails a run. |
| Warning | A heuristic over the graph, tied to a principle and carrying its evidence. Never baselined, never fails a run. The Warning entity is a structural problem worked out by core's analysis from the Dependencies, the rules and the structure settings (a cycle, an orphan, unused exports, private imports, a long function, duplication or complexity); a warning-severity result from a registered sensor is a Finding. |
| Baseline | The recorded violations a repository has accepted for now; it may only shrink. |
| Scratch folder | A rebuildable folder under `.recognizer/cache/` (the Mutation work folder `mutation/work`, which holds the Warm-up copy and every Mutant copy). Results (overlays, findings, coverage, logs, Mutation's `survivors.json` and `record.json`, scans) are never scratch and stay backed up. |
| Overlay | Measurements a sensor reports (coverage, churn, mutation), which core writes as one file per overlay to `.recognizer/cache/overlays/` (or under `.recognizer/cache/commits/<commit>/overlays/` for a commit) and which are painted onto files and members. |
| Inputs | The `inputs` key of an overlay or findings file: each file the sensor measured, mapped to the file hash the scan recorded for it. Never recomputed from disk. |
| Tests hash | The `tests` key of an overlay or findings file from a sensor that depends on tests: a sha256 over every test file's path and hash, and over the entries of each tests report (a scanner's hash of each test input inside source files it owns), sorted by path. |
| Tests report | The answer a scanner gives to its `tests` verb, `{entries}`: the hash of each test input it owns, keyed by repository-relative path, a `#` and a suffix the scanner chooses. The tests hash joins it to the test files' own hashes. A scanner declares that it answers with `reports_tests` in its manifest. |
| Survey answer | The answer a scanner gives to its `survey` verb, `{runners, tools, notes}`: the test runners, coverage tools and survey notes for its own languages, read from the repository's build files, with `{up}` and `{slug}` where a path or command needs the runner's depth and name. The request names the repository root, its file list and the configured suites. A scanner declares that it answers with `setup_survey` in its manifest. |
| Survey order | The `order` in a scanner's `setup_survey` manifest key: a non-negative integer that fixes where its survey answer comes in the Setup survey; ties break by plugin name. |
| Current result | A result (an overlay value or a finding) whose measured files still have the hash `inputs` records and, for a sensor that depends on tests, whose `tests` matches the repository's present test files. Anything else is out of date and shown nowhere. |
| Result row | One result's line in the Scan panel's list: Structural analysis, Descriptions, or one sensor; Structure is not a row, since it always runs. Every row is in one of six freshness states, with the same icon and wording in the list, the summary and the Findings line: current (with when), out of date (N files), never run, checking (a sensor or Descriptions row before the first plan answer arrives, with the summary reading "Checking what is out of date"), failed (with when and a log link) or running (with done of total). |
| Incremental | The default mode of the Scan panel's mode toggle (Incremental or Full). The primary button names the work ("Update N files", "Run `<names>`" or a disabled "Up to date"; a disabled "Checking" shows until the plan answer arrives, and a disabled "Nothing to run" when no sensor is registered), and a run does only the out-of-date and missing work and keeps every current result. When no ticked row has work but some unticked rows are not current, the button is a disabled "Nothing ticked to run" and a hint names those rows; a click never ticks a row. |
| Full | The other mode of the Scan panel's mode toggle. The primary button reads "Rescan N files"; that click reruns every ticked sensor over the scope, describes every file (`--describe=all`) and replaces the sensors' results; Mutation still reuses a verdict whose function body and covering tests are unchanged. The toggle only changes the primary's label and never runs anything; it is disabled while a scan runs. |
| Freshness model | The one file (`packages/app/src/freshness-text.ts`) that computes every result row's state, the changed files (the ones Structure reports changed), the files an update brings current, the files a sensor has no result for, the Scan panel's summary and primary button, the Findings panel's line, the footer's progress text and which canvas boxes read "changed". It reads the out-of-date files per sensor and for descriptions from core's freshness rules, the same ones a Scan plan reads, and keeps the running, failed and current-at states from the window's own run state. The Scan panel, the Findings panel, the canvas and the footer read it, so they cannot disagree; it only reads and never starts a run. |
| Scan plan | What core's `Scan.plan` returns for a request: the phases, files and suites a scan would run, the names the plan dropped because no sensor registers them, the out-of-date files per sensor and for descriptions (the gaps), the sensors never run here, and whether the plan is idle. It has no text; the app builds the button label and the progress sentence from it. Planning reads and writes nothing and starts no scan, describe, sense or test run. |
| Scan estimate | The Scan panel's rounded time figure for a planned run, shown as one line under the primary button and built from per-part figures read from this repository's run records. A part with no usable history, or a Mutation part whose Work the sensor has not answered, is named "no estimate yet" and never given a figure. It is a pre-run figure only: while an app-started scan runs, the run card reads the plugins' Reported estimates instead. |
| Fixed part | The share of a sensor's time that does not scale with what it measures: coverage and the Mutation warm-up. A scan records it as `fixed_ms` on the sensor's entry, and the Scan estimate adds it once, then scales only the rest, by the work a run will do for a sensor that can count it and by file count for one that cannot. |
| Work | A plugin's count of what a run will do or did, in the unit its manifest names. Before a run the `check` verb's `--work` answer is `{ unit, to_perform, reusable }`, counted from the sensor's own record with no test run; a findings document carries `{ unit, performed, reused }` for the run, and a scan's sense entry keeps `{ unit, performed }`. For Mutation the unit is functions: `to_perform` and `performed` are functions with at least one site to run, `reusable` and `reused` functions whose every verdict was kept, and a function carried from a suite not ticked or a file out of scope is in none of them. The Scan estimate scales Mutation by `to_perform` at the pace of past `performed`. |
| Excluded function | A function the Mutation sensor did not test because its file has no entry in the coverage report. It is counted in the findings document's `excluded` and listed with its file in `inputs`, so freshness treats the file as measured. |
| Unowned function | A function the Mutation sensor did not test because no configured suite's directory and language cover its file. It is counted in the findings document's `unowned` and listed with its file in `inputs`. |
| Unknown file | A scanned file whose language no installed scanner publishes a rule for, so its test-file, supertype and private-import findings are unknown, not clean. Core names it from the scan and the scanners' manifests, records it in the structure findings document's `unknown_files`, prints it in the check report, and the app's scan summary shows it. It is never a violation and never a baseline entry. |
| Metrics list | The canvas control, before Legend, that lists every metric of the current overlays and ticks the ones shown as bars on the boxes; it controls the canvas only. |
| Metric bar | A row on a file box, one per ticked metric the file has a value for, in tick order: a short label, a track, a fill in the tone colour and the figure; a member-granularity metric shows the box's worst member; hover names it. A folder box and a file the overlay did not measure show no row. |
| Report | A findings file an agent hands to recognizer with `recognizer report --as <name>` after a review it ran itself; listed with the sensors but never run by a scan, stale once the scan passes its commit, replaced only by the next report under the same name. |
| Responsibility | A file's generated one-line statement of what it is for, committed in `.recognizer/responsibilities.json` and current while its source and describer are unchanged. |
| Describer | The command a repository registers in its config to write responsibilities. |
| Describer registration | The `describer` key of the Config: the command to run, with `{repository}`, `{module}`, `{model}` and `{request}` filled in, a version naming its prompt, recorded bare: the model is not part of it, and optionally a `build` (a command and the repository folder it runs in) that the Preflight names as the fix when the describer's arguments check fails. A Config without one falls back to the Describer in effect. |
| Describing settings | The model, the Batch size and the Confirmation threshold, global to the user, held under `describing` in the app's `config.json`, seeded as `haiku`, 4 and 5 and edited in the Settings modal; a scan from the app and one from a terminal read the same values. |
| Describe projection | The estimate printed before the describe phase starts any call: the number of files, the input tokens (3 characters per token plus a fixed 900 per request), and the API-equivalent dollar cost at the selected model's price, unknown for a model naming no known family. It is never a share of a subscription limit. |
| Confirmation threshold | The `confirm_above_usd` Describing setting, in US dollars, API-equivalent, seeded 5. A scan started from the app asks before describing when the Describe projection is above it or its price is unknown; equal does not ask, and the app's answer reaches the scan through the Describe answer file, not stdin. The CLI never asks. |
| Describe answer | The file `.recognizer/cache/scan-running.answer.json` beside the run record, written by the app to answer the scan's describe confirmation and read by the scan that asked: `version`, the `run_id` it answers and `describe` true or false. There is one per run, the scan removes it after reading it, and a scan ignores one whose `run_id` is not its own. |
| Describe stop | The describe phase ending early with every line already written kept: on a provider usage or rate limit (describer exit status 75), or, as a fallback for a limit the describer does not recognise, when a whole Batch size of describer calls (at least 2) fail in a row. The files not described stay missing or out of date, so the next scan describes them. |
| Describe confirmation | The Run's record of the describe cost question: the ask (the number of files, the model, the input tokens and the price, unknown when the model has no known price) and its answer, `describe` or `skip`, none until the user answers. An ask still unanswered when the Run ends is dropped; an answered one is kept. |
| Describe halt | The Run's record of a Describe stop: its cause (`limit` or `failures`), the reason the describer gave, how many files were described and not described, and the failure threshold. It is set once and ends the describe Plugin run as stopped. |
| Batch size | How many files are described at once; the describe phase keeps that many describer runs going. |
| Describer in effect | The Config's describer, or none when it has none, as `recognizer describe --describer` reports; with none registered, describing refuses and names how to register one. |
| Current line | A Responsibility whose source hash, describer and version all match the file and the Describer in effect today; the model that wrote it is not compared. |
| Out of date | A Responsibility that is not a Current line: its file's source (the files the scan recorded for it), the describer command or the version has changed since it was written. |
| Unchecked | The status of a Responsibility that exists but whose Current line test cannot run, because no Describer registration exists or the file's source cannot be read. |
| Overlay registration | An entry of the Config's `overlays` key: an overlay's name, the command to run with `{repository}`, `{commit}` and `{output}` filled in, its Metric declarations and, optionally, `runs_tests: true` when it runs the repository's tests. |
| Sensor | A program that reads the scans, the policy, the overlays or the repository and writes a findings file; it never runs the code it judges. Recognizer ships structural analysis and a repository registers others. |
| Sensor registration | An entry of the Config's `sensors` key: a sensor's name and the command to run with `{repository}`, `{commit}` and `{output}` filled in, plus an optional `manifest`: the whole command that prints the sensor's manifest, run exactly as written. A sensor with no `manifest` is never asked for one and declares nothing. For structural analysis the entry is its settings, or `off`. |
| `planned_work` | An optional key of a sensor's manifest, `{ "verb": string }`: the sensor answers `check --work` with the work a run would still perform, and the verb is the word the time estimate uses ("mutate"). Absent means the sensor plans no work. |
| `log_path` | An optional key of a sensor's manifest: the repository-relative path of the log its last run wrote, which the app opens from a failed row. Absent means it writes none the app can open. |
| Unlisted metric | A metric entry whose manifest sets `unlisted: true`: the overlay panel does not list it under that sensor's group because another group already shows it. |
| Sensor progress | The message a sensor prints while it runs, which the CLI passes through `--json` and the app shows on the progress line. |
| Orphan | A file no scanned file imports that is not an entry point; reported as an `orphan` warning. A file only test files import is still an orphan and is reported with its test importers. A Kotlin file reached only through a supertype follows the supertype rule: an implementer or subtype of a reached file is reached, and an implementer of a file nothing reached uses is an orphan. |
| Test import | A record of a test file importing a scanned file, written by a scanner from the test files it skips as `test_imports` (`from` the test file, `to` the file, `names` when known); the `orphan` and the `unused_exports` finding read it, and a test file is never a file. |
| Entry annotation | A simple annotation name in the shipped Kotlin list (Micronaut, Spring and Jakarta container annotations such as `Controller`, `Singleton`, `Service`, `Inject`) or in `warnings.orphan.entry_annotations`; a Kotlin file whose top-level class, interface or object carries one is an entry point. |
| Entry point | A file that need not be imported: one the policy `entry` list names or matches by glob, a test file by convention or one matched by a glob in `warnings.orphan.entry_points`, or a file its scanner marks as run rather than imported (Python: a package's `__main__.py`, a file with a top-level `__name__` guard or a file a `pyproject.toml` console script names, a package `__init__.py` when some file under the package is imported from outside it; TypeScript: a file a `package.json` names in `main`, `module`, `browser`, `bin`, `exports` (including a `*` pattern of a non-private package), `scripts` or `zshy`, the `index.js` beside a `package.json` with no `main` and no `exports`, a file a `*.config.*` file names in an `entry` property, a `*.config.*` file, a file an HTML `<script src>` loads, or a file starting with a shebang; Rust: a Cargo target root (the library root included), a file reached only through a file declaration gated by `#[cfg(test)]` or any `cfg` predicate that requires `test`, such as `cfg(all(test, unix))`, or a file whose own inner attribute is such a gate, as the [Rust scanner README](../packages/scanners/rust/README.md) states; Kotlin: a file with a top-level `fun main`, or a file carrying an entry annotation). |
| Actual file | A Kotlin file with a top-level `actual` declaration whose package and name an `expect` declaration in another file of the same build file also holds; its file carries `actual_of`, the ids of those expect files, and `recognizer check` counts it as reached whenever one of them is reached. |
| Policy drift | A policy entry glob that matches no scanned file; reported as a policy problem, never as a finding. |
| Policy problem | A condition of the policy file itself, a policy drift today: reported by `check`, `scan` and the app as a message naming `.recognizer/policy.yaml`, never a finding, never counted as a warning and never changing an exit code. |
| Folder metrics | Per folder that holds scanned files, Martin's package numbers computed from the scan and the policy alone: afferent coupling (files outside that import files inside), efferent coupling (files inside that import project files outside; imports of files outside the scanned project count for neither coupling), instability, abstractness (the share of exported members that are abstract members) and distance. Written in the check report's `folder_metrics`, never as findings. |
| Main sequence | The line where a folder's abstractness plus its instability is 1. Distance is how far a folder is from it: `abs(abstractness + instability - 1)`. |
| Structure | The scan: required, builds the code state and reports no defects. It always runs, so the Scan panel does not list it; its freshness is what changed since the scan. |
| Structural analysis | The optional step that reports defects from the structure, the policy and its limits: cycles, orphans, unused exports, private imports, long functions, policy violations, duplication and cyclomatic complexity. Recognizer's own sensor, on unless the Config turns it off, and a scan can run without it (`recognizer scan --skip-analysis`, or its tick unticked in the Scan panel). Its settings are a switch per warning and the limits of its checks. Its sensor id, config key, findings file and overlay are still `structure`. |
| Official sensor | A sensor this repository writes and releases as a plugin in `packages/sensors/`, run by `recognizer-sense-<name>`. It is discovered on `PATH` and registered like any other sensor, with `recognizer plugin add <name>`: Recognizer knows it only while it is installed, and its display name, description, metrics and findings come from its manifest. One run measures what it needs and judges it: CRAP (which also judges coverage) and mutation. |
| CRAP sensor | The official sensor that runs the Test suites configured under `tests:` in `.recognizer/config.yaml` (never a built-in command or a `test_command`), scores each function `cc^2 * (1 - coverage)^3 + cc` from its cyclomatic complexity and the coverage of its lines, warns above `threshold` (30 by default) with the fix pattern `simplify-or-test`, and writes the per-function numbers as an overlay in the same run; a function with unknown coverage is never scored as zero. A failing test suite does not end the run: the results are kept and the document carries a Diagnosis of `tests-failed`, and when no coverage can be produced the sensor reports complexity alone with a Diagnosis of `coverage-unavailable`. |
| Diagnosis | The one object (`code`, `line`, optional `fix`, optional `suite`, optional `failing` with `count` and at most five `names`, optional `unmeasured`) that says why a plugin could not do everything it was asked to. `code` is the plugin's own short string; Recognizer keeps no list of codes and never decides anything from one. `line` is the complete one-line sentence; `fix` is the instruction where there is one. `unmeasured` says the plugin finished without measuring what it was asked to, and makes its run entry fail. A completed run carries it in the findings document, a Refusal carries it as a `diagnosis` Plugin event, and the run log entry records it. |
| Preflight | The check `recognizer scan` makes after the scan marker is held and before the describe and sense phases, that everything the ticked sensors and the describer need is in place. It has two stages: an early stage before extraction (a commit, the describer and its arguments, each ticked sensor's program) and a project stage after it, which is each ticked sensor's Readiness check. It runs no tests, spends nothing and installs nothing, and runs only Plain activations. Any Gap means nothing runs, and the scan exits `4`. |
| Readiness check | A plugin's own answer to whether it can run, given by its `check` verb (`recognizer-sense-<name> check`), which prints the gaps it finds as plain sentences and exits `0` either way. A check runs only a Plain activation of a suite and notes any other `activate` line as `activate-unchecked`; only `--run` runs it. `recognizer sensors check [name]` asks each sensor that is not off and relays what they say, exit `1` while any gap remains; `--run` also runs each test suite once. The core relays each gap as the sensor wrote it, and nothing is installed or fixed: a person or an agent installs what is missing and checks again. |
| Doctor | `recognizer doctor [REPOSITORY]`: the read-only check of a repository's config, policy, scanners and sensors, in that order, which starts no scanner, describer or test command and writes nothing. It reports Setup problems, exits `0` with none and `1` with some, and is the config upgrade path when a release retires a key. |
| Setup problem | One line of a Doctor report: a `code` (such as `config-retired` or `scanner-missing`), the `subject` it is about, the `title` that names what changed in plain words, the `line` that says what is wrong in full, and a `fix` that is a command when one exists and an instruction otherwise. A skipped area is not a Setup problem. |
| Readiness note | A sensor's remark from a readiness check that is not a Gap: it never blocks a scan, never changes `ready` and never changes the exit code. Today it names how many scanned files a ready suite's coverage report covers (`coverage-partial`), shown by `recognizer sensors check --run`, and a suite whose `activate` is not a Plain activation (`activate-unchecked`), whose tools were not checked. |
| Setup guide | The text a plugin supplies for setting it up, given by its `guide` verb and printed by `recognizer help sensors <name>`: the tools it requires, how to find how the developers run their tests, how to write the suites, and to re-run the readiness check until it is clean, never installing anything without the human's say-so. |
| Gap | One missing or unusable thing a ticked sensor or the describer needs, as the Preflight reports it: an `id`, the `line` that says what is missing (for a sensor, the sentence its `check` verb gave), the sensors it `needs`, the `project` it is in, and a `fix` (its text, command, folder, environment and whether it is `repository` or `outside`). The Scan panel shows a gap's line and the sensors it needs, never a fix; for a sensor's gap it adds one help line pointing at that sensor's setup guide. |
| Refusal | The end of a sensor run that cannot proceed for a toolchain cause (a red suite before Mutation, no coverage for Mutation, a test program that does not start): the sensor writes no document, exits `2`, and prints a `diagnosis` Plugin event with its Diagnosis, then the plain `line`. |
| Coverage limit | The line coverage below which the C.R.A.P. sensor reports a function as a warning, `sensors.crap.coverage_limit`: 0.6 by default (Google's Code Coverage Best Practices), tunable, and `false` switches the finding off. A tuned limit is reported beside the published 0.6. |
| Cyclomatic complexity | One plus the branch points in a function's own body (conditions, loops, match arms, catches, the boolean operators "and" and "or", and in TypeScript the nullish and optional-chain operators), counted from the syntax tree by two parts that agree on every function: the CRAP sensor, which writes it to its overlay, and structural analysis, which reports the functions over the Complexity limit with no test run. |
| Complexity limit | The most branch paths a function may have before the `complexity` finding reports it, `sensors.structure.warnings.complexity.limit`, 10 by default (McCabe). |
| Duplication check | A check inside structural analysis, run with every scan and set under `sensors.structure.duplication`: it reports each duplication family, and so each pair, of functions in the same language whose structural fingerprints are alike (Jaccard similarity at or above `threshold`, 0.82 by default) as one `duplication` warning on every member's file, with the fix pattern `extract-shared-function`. A pair needs its shorter member at `max(min_lines, pair_min_lines)` lines (`pair_min_lines` 6 by default); a family keeps the `min_lines` floor of 4. A function with no body (an interface, abstract, external or expect member) is skipped, and the structural fingerprints and `min_nodes` come from the function body alone, so parameter lists, their annotations, the name and the return type do not count toward similarity. For Kotlin the line floors (`min_lines`, `pair_min_lines`) count the compared span, the body after any scope-call wrapper is looked through, not the whole function with its annotations, and an expression body that is an `object` or a lambda is compared on its inside; other languages count the whole function. |
| Scope-call wrapper | The one Kotlin call a function body consists of, around a trailing lambda: `synchronized`, `use`, `withLock`, `runCatching`, `run`, `with`, `apply`, `also` or `let`, optionally under `return`. The duplication check looks through it, comparing and counting the lambda's statements instead, repeatedly for nested wrappers; a call chained after it, a body of several statements and any other callee are not looked through. |
| Duplication file finding | The one `duplication` warning two or more near-copy files give together: a pair of files qualifies when the functions that copy each other, counted only at the pair floor and across the two files, are at least 2 on each side and at least 0.75 of each file's compared functions; qualifying pairs join into one component and every cross-module pair of copies inside it is absorbed into the finding, whose id starts `duplication:modules:` and names the two lowest files by code point (with a `#` and the file count for three or more), lists each function pair in its summary and takes the lowest absorbed similarity. |
| Duplication family | A set of functions linked by over-threshold pairs (the connected component of the pair graph), reported as one finding listing every member; its similarity is the lowest linking pair's, and a plain pair is a family of two. A family of three or more methods in one file under one qualified-name prefix reads "N methods of Class share one structure". |
| Lines duplicated | The sum of a duplication finding's members' line counts, the figure duplication findings are ranked by, largest first, in `recognizer check` and in the Findings panel. |
| Structural fingerprint | The set of SHA-1 hashes of every subtree, cut at depth 3, of a function's normalised syntax tree (local names, parameter names, field names and literals replaced by kind tokens; call names, operators and shape kept); two functions are compared by the Jaccard similarity of their sets. |
| Mutation record | The file beside the survivors file in which the Mutation sensor keeps, per function, a hash of its body and, per mutation site, the verdict, the test files that ran it and its Killer, each with its hash, with a hash of the Test suites and of the Test support files; a rerun reuses each site on its own while its function's body and the files that bear on it are unchanged, and runs the rest. |
| Killer | The test files the runner reported failing for a mutant that was killed, with the `conftest.py` files on their paths; a killed site is reused while the hash of every Killer file is unchanged. |
| Test support files | The test files that are neither a test entry nor a `conftest.py`, such as helpers and data under a test directory; the Mutation record keeps one hash of them, and any change to it voids all reuse because the sensor cannot say which tests use them. |
| Budget | A Mutation sensor's `max_minutes` ceiling, counted from the first mutant (the coverage pass is outside it): no function starts once it is spent, and a function left unstarted is skipped, absent from the overlay and listed in the survivors file as `uncovered-by-budget`; the next run queues it first. |
| Stopped run | The Mutation run Stop ended: it keeps every function whose mutants all finished, lists the rest as skipped in the record and the survivors file, and says so in its findings document through the root key `stopped`, which the Scan panel reads as `stopped, <n> of <m> functions measured`. Its record keeps the previous verdicts of the functions it did not reach, wherever their keys still match. |
| Partial result | A Mutation run that measured fewer functions than it considered, from a Budget or a Stop, recorded in its findings document under the root key `partial` and shown in the Metrics panel as `Partial: <n> of <m> functions measured`. A complete findings document of a sensor that counts functions carries `counts: {measured, total}`, and a run's record keeps the verdicts of functions it did not reach, whether a stop or a Budget ended it. |
| Checkpoint | The pair of findings document and overlay core writes for what a plugin has settled so far (a `settled` event, with any record the plugin resumes from) while it still runs, or keeps when the run ends early. The findings document is marked `partial` or `stopped`, so a run that fails, times out or is stopped keeps it as its visible result and the next run resumes from it. A checkpoint never replaces a complete output that measured more functions, whichever commit that output is for, by `counts`, `stopped` or `partial`; an equal count replaces it, and an output with no count is not protected. |
| In-file test hash | The digest of a Rust lib or bin target's unit tests - the test items - `#[test]` or an item gated by a `cfg` predicate that requires `test`, as the [Rust scanner README](../packages/scanners/rust/README.md) defines a test gate - found by walking its file tree from the root file - which the Mutation sensor joins to the killer and ran sets, so an edit to an in-file test reruns the sites that target's unit group covers; the walk follows `#[path]`, and a file with no file takes a digest of every `.rs` file under the root file's directory instead. |
| Test selection | The Mutation sensor's choice, per mutant, to run only the tests that cover its site instead of the whole suite, with only the tools each language mandates: Python runs the test node ids whose per-test contexts executed the line; TypeScript runs the runner's own related-files selection (`vitest related` or `jest --findRelatedTests`); Kotlin, C# and Rust run the test classes or targets a per-class or per-target Warm-up copy run attributed to the line. A selection of more than half the suite runs the whole suite instead, and a language with several suites or a suite outside the repository root runs the whole suite. |
| Test suite | An entry of the Config's `tests` list: its name, language, directory, command, optional activation and environment, and the coverage report it leaves. The CRAP sensor runs each one in the user's login shell from its directory and reads the report it names. |
| Mutation sensor | The official sensor that runs the tests under coverage, mutates the covered functions, runs the tests against each Mutant and warns, per function with a Survivor, with the fix pattern `strengthen-tests`; in the same run it writes the overlay of killed, survived and uncovered counts and a score, the survivors file and the Mutation record, reusing an unchanged function's verdicts and stopping at a Budget. |
| Mutant | A single token of a covered function replaced by its one counterpart (`>=` by `>`, `and` by `or`, `true` by `false`), written into a Mutant copy and run through the Test suite's login shell. A failing, unstartable or timed-out run kills it. |
| Mutant copy | The per-worker copy of the repository, made of the git-listed files and the folders on the Carry list, reset to its tracked state before each Mutant. It lives in the Scratch folder until the run ends or it is retired after a timeout or a failed reset. |
| Carry list | The `carry` setting under `sensors.mutation`: the exact untracked repository folders (such as `frontend/node_modules`) a copy takes, with no built-in list; a folder not listed is not in the copy. |
| Warm-up copy | The one copy of the repository the Mutation sensor runs each configured Test suite in before any Mutant, to read its coverage and its per-test contexts; the warm-up also measures the Run memory. |
| Worker Gradle home | The per-worker `GRADLE_USER_HOME` in the Scratch folder that one warm Gradle daemon runs against for a Kotlin Mutation worker's Mutant runs, seeded from the user's Gradle home and removed with the run. |
| Run memory | The peak resident memory of the process tree of one test run, measured during the warm-up and used to size the default worker count. |
| Memory reserve | The fixed amount of memory (2000 MB) Mutation leaves for the desktop when sizing workers on macOS: the sizing reading is free pages plus file-backed pages plus purgeable pages, less this reserve, so the `available` figure in the sizing line is net of it. |
| Survivor | A Mutant whose test run passed: the tests did not notice the change. |
| Producer | The tool that wrote an Overlay file, named with its version in the file's `producer`. |
| Metric declaration | A metric's `name`, `type`, `granularity` and `bad` direction, registered in the Config and repeated in the Overlay file. |
| Config | A repository's committed `.recognizer/config.yaml`, which registers its overlays and holds its other recognizer tooling settings. The policy is separate. |
| Config key | A dotted path that addresses one scalar or one list of scalars in the Config, as `recognizer config` takes it: `sensors.mutation.max_minutes`, or `tests.<name>.command` for the list entry whose `name` is `<name>`. |
| Policy key | A dotted path that addresses one list of strings in the Policy, as `recognizer policy` takes it: `entry`, `forbid` or `ignore`. |
| Forbid rule | A policy entry whose `from` globs may not import its `to` globs, reported as a Violation per importing file. |
| Key schema | The document an owner publishes listing the Config keys it owns, described by `schema/config-keys.schema.json` and merged by `recognizer config` and `recognizer help config`. |
| Command table | `COMMANDS` in `packages/cli/src/commands.ts`: the one list `recognizer` dispatches from and generates its help from. |
| Freshness | Whether the cached scans can be used: they were taken at the current commit from a clean working tree, and the scanned files still hash the same. Otherwise `recognizer scan` runs first. |
| Scanner | A language's standalone command that emits a scan. |
| Toolchain | The `recognizer` command and the app, versioned and installed together. Out of step: `recognizer --version` reports a version other than the app's own; the app refuses the scan and names both versions and the fix. Plugins are not part of it: each is judged by its protocol. |
| Bundled toolchain | The folder inside the app, `Contents/Resources/toolchain/commands`, holding one entry, `recognizer`; a packaged app runs it by absolute path and never through `PATH`. |
| Release unit | A folder built, versioned and released as one archive with its own tag `<unit>-v<version>`, listed in `tools/packaging/units.json`. One unit may carry several formulae when they share a package: the `sensors` unit carries the three sensor formulae. |
| Plain activation | An `activate` line made only of `source <path>/activate` (or `. <path>/activate`), `nvm use [version]`, `sdk env` and `conda activate <name>`, joined by `&&`. A Readiness check runs it; any other `activate` line is not run by a check. |
| Plugin bundle | The formula `recognizer-plugins`, which depends on every official plugin formula and which the cask depends on, so one cask install gives a working set. Adding an official plugin changes the bundle, not the cask. |
| Nothing ran | A scan that exited without error but ran none of a phase the user asked for (describe, measure or sense), reported with the reason instead of shown as finished. The reason is derived from the run record's `ran` and `commit`, whoever started the scan; a record whose `ran` is null (no summary was written) is a failure, never Nothing ran. |
| Scan | The document a scanner emits: files, edges and foreign nodes for one language, the files it read and the selection it used. |
| Scanned file | A file a scanner read, recorded in the scan's `files` with the SHA-256 of its bytes. The files include the manifests, pages and configs read to decide boxes, edges or entry points, not only source, so they are a superset of the boxes. |
| Selection | A scanner's rule for choosing files, recorded in the scan as data: extensions, skipped directories and skipped file globs, and the non-source files it reads by name or path. A consumer applies it to a path the scan has not seen. |
| Baseline | What core holds of a scan's files, per window (the app only asks for the changes): each file's recorded hash and the scan's selection, including its input file globs and absent paths, with the commit and branch taken just before the scan. Changed since compares the folder against it. |
| Changed since | The viewer's report of what differs from the scan on screen: an edited, added or deleted file the scanners read, or a moved commit or branch. An edit undone again does not count. |
| Rescan | Running the scan again on request, from the Scan panel, File > Rescan or Cmd-R. It keeps the view state, and a run whose structure is unchanged updates the open view without rebuilding it; nothing rescans on its own. |
| Update in place | Handing a run's new sensor results, findings and notices to the open explorer without rebuilding it, so the canvas, camera, selection, inspector and left panel stay as they were. It applies when the scan's files and scan documents are unchanged; a structural change rebuilds the explorer and carries the camera. |
| Cache | A repository's gitignored `.recognizer/cache/`, where scans and overlays are written. |

## Plugins

| Term | Meaning |
| --- | --- |
| Plugin | An executable that does one of Recognizer's three kinds of work: a scanner reads a language into a scan, a sensor measures and writes findings and overlays, a describer writes one line per file. It is named `recognizer-scan-<name>`, `recognizer-sense-<name>` or `recognizer-describe-<name>` and speaks to Recognizer through arguments, JSON on stdout and events on stderr. Recognizer's own scanners, sensors and describer are plugins under the same contract. |
| Manifest | The JSON a plugin prints for `<command> manifest`: its kind, name, display name, version, protocol version, install command, whether it has a readiness check, whether a run may take minutes or has a time limit, the words its progress counts in, its settings, and the fields its kind adds (a scanner's languages, a sensor's metrics and finding sentences, a describer's prompt version). |
| Protocol version | The one integer in a manifest's `protocol`, covering the manifest, event, scan, findings and overlay schemas together. The CLI supports the current protocol and the one before it; a plugin outside that range is refused before anything runs. A plugin's own `version` is never compared. |
| Verb | One of the arguments a plugin answers, always as its first argument: `manifest`, `check`, `run` and `guide`, and for a scanner the optional `tests` and `survey`. A plugin does work only when Recognizer calls a verb. A tool whose manifest says `check: false` answers `check` with exit 2, and a tool with no setup help answers `guide` with nothing. The four are answered by every shipped tool, and `recognizer plugin check` calls all four. A scanner answers `tests` when its manifest sets `reports_tests` and `survey` when it sets `setup_survey`. |
| Plugin event | One JSON line a plugin writes on stderr while it runs, prefixed `recognizer-event`: a `start`, a `progress`, a `note`, a `diagnosis`, a `stage`, an `estimate`, a `result` or a `settled`. The CLI reads every one, tags it with the plugin's name and forwards it unchanged on `recognizer scan --json` as a `plugin` line; core carries a sensor's stage and estimate in its Plugin run, and the app reads the footer's scan line and the failure text from the run snapshot. |
| Grace period | The 10 seconds a plugin has to exit after SIGTERM, when the user stops a scan or a run passes its time limit, before it is killed with SIGKILL. The app adds a backstop of 15 seconds from its own SIGTERM. |
| Installed plugin | An executable on `PATH` named `recognizer-scan-<name>`, `recognizer-sense-<name>` or `recognizer-describe-<name>` whose `manifest` verb answers with a valid manifest of that kind and name. `recognizer plugins` lists them; the first match on `PATH` is the one that runs. |
| Install line | The string recorded under `install.<program>` in a repository's `config.yaml`, copied from the plugin's manifest by `recognizer plugin add`, which doctor shows as the fix when the program is not installed on a machine. |
| Registration file | One JSON file, named `<kind>-<name>.json`, that registers a plugin: its `registration_version`, kind, name, the `command` words that start it and the `manifest` words that read its manifest. A file that fails these rules is unreadable and is listed with its reason, never loaded. |
| Plugin registry | The machine-wide set of registration files, read from two folders: the Homebrew folder `/opt/homebrew/share/recognizer/plugins/` and the user folder `~/.config/recognizer/plugins/`. For one kind and name the user file outranks the Homebrew one, and of all describers the newest file is the one in effect. `recognizer plugin register` and `plugin unregister` write and remove user files. |
| Registered plugin | A plugin the plugin registry holds a readable, winning registration file for. A shadowed Homebrew file and a describer that lost to a newer one are not registered plugins. |
| Scanner choice | The `scanners` section of `config.yaml`, which maps a language to the manifest name of the scanner that reads it, and the rule that picks one scanner per language: the one installed scanner that claims it, the one the config names, or a failure when two claim it and the config names none. |
| Plugin template | The files `recognizer plugin init` writes for one kind and language, bundled in the CLI, and conforming as written: it passes `recognizer plugin check` the moment it is written. |
| Plugin environment | The variables a plugin command runs with: the login shell's variables, with the bundled toolchain folder first on `PATH` when the app has one. Core builds it; Rust and the CLI only supply its parts and spawn with it. |
| Language facts | The `language.json` of a template language in the bundle: its `order` in the printed language list, an optional `launch` command that `plugin check` is run with, and an optional `build` line printed before the check line. A folder without one is not offered as a language. |
| Grammar rules | The per-grammar tables a scanner publishes in its manifest under a language's `grammars`: the grammar's name, the extensions parsed with it, and the node types and operators that mark a function, a scope, a branch and a boolean operator, plus the types of a function bound to a name. Structural analysis reads them from the installed scanners instead of holding any language's tables itself. |
| Test file rules | The `test_files` rules a scanner publishes on a language in its manifest: for each rule the extensions it applies to and the directory names, directory suffixes, basename patterns and stem suffixes that mark a path as a test file. A path is a test file when any rule of any installed scanner matches it. Core reads them through `LanguageBehaviour` and holds no language's conventions. |
| Function naming rules | The `function_names` a scanner publishes on a grammar: for a function type whose name is not its plain `name` child, the field it requires, the field or literal it is named from and an optional prefix. Structural analysis applies them generically. |
| Span rule | The `span` a scanner publishes on a grammar whose functions can hold their whole body in one scope-call lambda: the scope-call names and the node types the unwrapping reads. Absent, a function's compared span is its body. |
| Grammar vocabulary | The `vocabulary` a scanner publishes on a grammar, beside its function naming and span rules: the node types and names for comments, literals, calls, identifiers, trivial function shapes and scope names, the node types whose `operator` field counts as a boolean operator, the grammar's field roles and its assignment operators. Structural analysis applies it generically and recognises none of it for a grammar that publishes none. |
| Field role | One of twelve named meanings (such as a function's body, a call's callee or an assignment's right-hand side) for which a scanner publishes, in a grammar's `vocabulary.fields`, the tree-sitter field that holds it. Core reads a role's field from the vocabulary and names no field itself; a role the grammar does not publish is not read. |
| Plugin guide | The author guide `recognizer help plugin-guide` prints: what a plugin is, the verbs, the manifest, versions, events, stopping, installing and the author kit. |
| Unregistered plugin | An installed sensor that the repository's `config.yaml` does not register, which a run needs only when the config has a `tests:` list and no registered sensor runs tests. `recognizer doctor` then reports each installed sensor that runs tests as a problem with `recognizer plugin add <name>`, and registering any one clears them all; `scan --sense <name>` refuses an installed sensor that is not registered with the same command. An installed sensor that is not registered is otherwise normal and never a problem. |

## The viewer

| Term | Meaning |
| --- | --- |
| Tree | The left area: the repository's folders and files, each with its health disc. The way in. |
| Canvas | The centre area: the files the user has opened, inside their frames, and the edges between them. |
| Inspector | The right area, closed by default: what is in the selection, its findings, or an edge's evidence. |
| Frame | The box on the canvas for exactly one folder, which may be a compacted folder, labelled with its joined path, holding that folder's open files and the frames of its open subfolders. |
| Compacted folder | A chain of folders that hold no scanned file and exactly one subfolder, merged with the folder that ends the chain and identified by that deepest path; it is one frame on the canvas and one row in the tree, labelled with the joined path. |
| Open | On the canvas. A file is opened from the tree or by following an edge, and closed the same way. |
| Selection | The one file, folder or edge the user has picked, highlighted in the tree and shown in the inspector. |
| Selection bar | The small bar of icon actions shown above the selection while the pointer is over it; right-clicking opens the same bar. |
| Service | The child process, `recognizer serve`, that serves core's ports to the app over standard input and output; the app's Rust side relays each call and its stream items. |
| Setup | The rail button, between Findings and Settings, and the wizard it opens: Files, Checks, Tests, Policy, Review and Apply, the same on every run. On a configured repository Review leads with doctor's fixes. Opening it runs only the Setup survey and `recognizer doctor`; its badge counts doctor's problems. |
| Survey note | A sentence in the Setup survey about one directory that a test runner or its absence needs the user to know: a Kotlin build with no JaCoCo plugin, a missing Gradle wrapper, or a coverage report path the survey cannot read. The Tests step shows each one. |
| Setup survey | What `recognizer setup survey` finds about a repository without changing it or starting a scanner, describer or test: the files read, the checks, the test runners with their coverage tools, the configured test suites, the survey notes, the mark of each language, check and suite, the folders the policy does not cover, and the fixes doctor names. The same repository gives the same survey. |
| Setup mark | The Set up, New or Gone label Setup shows on a language, a check or a test suite of a configured repository, derived from the config and the repository, never stored. |
| Setup changes | The ordered list of commands that a set of choices makes, built by code in `recognizer setup changes` and shown in Review. Apply runs them all or undoes them all; Run once applies only the Tests step's changes, runs the readiness check and undoes them. |
| Policy recommendation | The optional answer Claude gives for the Policy step: ignore, entry and forbid cards, each with its reason and the files it is based on. A forbid card shows how many imports break it today. Only a card the user accepts becomes policy commands. |
| Settings modal | The large modal over a window, opened from the gear at the bottom of the rail, Recognizer > Settings... and Cmd+,. It lists the panes core publishes in two groups: This Mac (Editor, Describing and Setup, stored per Mac) and This repository (Structural analysis, the installed sensors and Test suites, written to the open repository's Config); with no repository open only This Mac shows. The app holds no field, label or unit of its own. |
| App setting | A value stored per Mac in the app's `config.json`, applying to every repository. |
| Repository listing | The files of a repository that one `RepositoryFiles` call returns, root-relative and `/`-separated, from `git ls-files` (tracked and untracked files git does not ignore) or, when git cannot list, from a walk that skips the skipped folders; `none` when neither works. Three named variants: the source listing (leaves out the top-level `.recognizer` folder, walks when git cannot list), the setup listing (leaves out listed files missing on disk, walks when git cannot list) and the detection listing (never walks, and carries git's warning). |
| Repository setting | A value written to the open repository's Config (`.recognizer/config.yaml`) by the Settings modal, through `recognizer config`. |
| Settings label | The `label`, `labels`, `unit`, `units`, `order` and `section` keys of a manifest's setting that make it a row of the Settings modal: the row's name, the text after its input, its place in the pane and the labelled group of rows it sits under. A setting with neither `label` nor `labels` is not a row, and a plugin with no labelled setting has no pane; `settings_title` names the pane, `display` by default. A `switch` key makes the row a toggle beside its number and names how off is stored: a separate boolean key, the value `false`, or the key absent. |
| Settings pane | One page of the Settings modal: a name, a group and its rows in labelled sections, built by core from its own settings and each installed plugin's manifest and listed core first, then plugins by display name. Test suites is a pane of cards rather than rows. |
| Machine setting | A setting with `scope` `machine`, stored in the app's `config.json` under its dotted key (`describing.model`) rather than in a repository's Config, and set for every repository on this Mac. A reset writes its default; it never removes the key. |
| Limit link | A setting's `limit` key in a sensor manifest: the metric it limits, its direction (`above` or `below`) and, optionally, the setting that holds the severity of a finding past it. The Settings modal shows that severity as a select beside the limit, and the severity sets the tone of the metric's function-card cell: amber for `warning` or no severity, red for `violation`. |
| Tuned figure | A limit, threshold or line that differs from its published figure (the long-function limit, the C.R.A.P. threshold, the complexity or coverage line); a finding on it states the limit in force, and the published figure appears once, in the group's popover and the setting's description. |
| Published default | The `default`, `defaults` or `default_text` a key schema entry publishes; Reset restores it by removing the key, never by writing it. |
| Staged edit | A change the Settings modal holds until Save. |
| Describe phase | The second phase of a scan, run when ticked: the files whose line is missing or out of date are described; progress shows in the footer's scan line and the result is a message in the message tray. |
| Run log | The record of one run of a registered command (scan or describe, and measure in records written before measurers were retired; a scan record holds its extract, describe and sense phases) under `.recognizer/cache/log/`, read with `recognizer log`; the last fifty are kept. A scan that fails before its phases start, on an invalid request, config or scanner setup, leaves no entry; the Scan marker is its record. A scan that is stopped, or whose process is killed outright, ends as `stopped`, exit 1, with `finished` set and the phases recorded so far; its outcome is one of `ok`, `failed`, `running` or `stopped`. A scan that throws after its entry is written closes it as `failed`, exit 1, with the phases recorded so far. A describe that throws after its entry is written closes it the same way, with the entries recorded so far. |
| Scan marker | The file `.recognizer/cache/scan-running.json` with its `scan-running.progress.jsonl` of event lines beside it: together the run record of the current Scan run. The pair is replaced by the next run rather than removed at its end, and a `checking` or `running` record is stale only while its process is not alive (a reader then shows it `stopped`); an unreadable or older-version file is not live. At its end the record also carries `commit` (the commit the scan used, or null when the folder has none) and `ran` (the phases that held at least one entry, null when the scan wrote no summary), which is what a reader needs to tell what ran. While a record is live a second scan refuses with exit code 3. The record is version 5: `failure.reason` is the failure text for every scan, bounded at 8192 characters (the last 8192 are kept), written by the CLI whoever started the scan, from the failed entry or from the error the scan threw. `exit` is the code the command ended with: 143 when stopped, 4 when refused by the preflight, and 2 when the scan threw an error before or between its phases. |
| Attached scan | A scan an open window shows and can stop although an earlier session or the command line started it: opening a repository whose Scan marker is live attaches the window to that run instead of refusing, starts no scan of its own, draws the explorer from the last adopted scan or, with none, a holding view with the run's progress and Stop. Quitting stops it only when the app started it. |
| Scan run | One scan of a repository, from its start to its end. There is one current run per repository, read from the run record (the Scan marker) whoever started it, the app or `recognizer scan` on the command line. Its phases are `checking` (the Preflight), `refused` (with its Gaps) or `running`, then `finished`, `failed` or `stopped`. Only `recognizer scan` writes the record and the app reads it, except that the service rewrites the record of a run whose process was killed outright as `stopped` and finishes that run's log record. |
| Run model | Core's account of one repository's runs and results, held by the service: the Sensor registry, the active Run with its Plugin runs, the Result set and Result freshness. It is built from the scan marker, the progress log, the findings files, the config and the plugin catalog, and it is published as the Repository state. |
| Repository state | The snapshot the service publishes as `repository.state` for one repository: the registry, the run, the results, the freshness and a count of unreadable reports, with a `revision` that rises by one on every change and starts at 1 with each service process. `repository.watch` streams it and `repository.state` returns it once. |
| Plugin run | One plugin's part of a Run: its phase (extract for one language's scanner, describe for the describer, sense for a sensor), its state (queued, running, finished, stopped or failed), its progress, its Stage, its Reported estimate, and, when it failed, its failure reason and diagnosis. The describe Plugin run counts files and keeps a tally: how many were described, how many failed and the first failure. A plugin run starts only after the one before it ended, and its end is set once; ending it clears its estimate and keeps its last stage. |
| Stage | The part of its run a plugin says it is in, reported as a `stage` event with a name, an index counting from 1 and the number of stages. A later stage replaces the earlier one, and a stage never changes the Reported estimate. |
| Reported estimate | A plugin's own estimate of the awake time left for its whole run, reported as an `estimate` event, or none when it cannot say. The extract scanners and the sensors each report one from their own history. Core carries it in the Plugin run and works out the Effective estimate and the Remaining estimate from it; the opening-scan modal shows the running scanner's, and the app derives no estimate of its own. |
| Planned estimate | A sensor's history figure for the run about to start, in milliseconds, taken from the Scan estimate's parts when the user presses Run and handed to the service with `scan.start` as `plannedMs`. A sensor with no usable history has none. The service holds it for that app-started run only, and a run started from the command line never takes it. |
| Effective estimate | The figure core counts for one live sense Plugin run, `{ ms, source }`: its Reported estimate with source `reported` when it has one, a zero included, else its Planned estimate with source `history`, else none. An extract, describe or ended Plugin run has none. |
| Remaining estimate | The run's time left, `{ ms, silent }`, in the Repository state's run. It is the sum of the live sense Plugin runs' Effective estimates, and `ms` is none while any live one has none, with `silent` naming those. It is absent unless the run was started by the app and is running with a live sense Plugin run. The run card rounds it and reads "No estimate yet" when `ms` is none. |
| Scanner history | The file `.recognizer/cache/scan-<language>/history.json` under a scanned repository, where one extract scanner keeps its last five completed runs as `{ key, ms, units }`, with `ms` the run's awake time and `units` its file count. The scanner scales the median `ms` per unit by this run's file count to report its Reported estimate; a scanner with no history reports none. |
| Result set | The results kept per plugin, each at a commit and a modified flag; a commit's results are read from `.recognizer/cache/commits/<commit>/` beside the working tree's. It grows as results are reported and is replaced whole only by a finished run; a result read from a findings file that cannot be read is kept and flagged unreadable, never removed. |
| Reported result | The findings and overlay values a plugin sends in a `result` event as it settles them, a function or a file at a time. Core holds them by finding id and by metric and id, and writes the findings document and the overlay from them; a plugin that reports its results writes neither file. |
| Settled | The `settled` event: the facts of a measurement (modified, settings, inputs, counts and the rest) at a point the plugin can stand behind. It is the plugin's checkpoint, and a later one replaces the facts of an earlier one. |
| Result freshness | Per registered plugin: current, stale with its out-of-date files, never run, or checking. Missing data is unknown, never healthy: when the scan document cannot be read, a plugin with results is stale. |
| Run scope | What a Run measures: the working tree, or one named commit. A commit-scoped run keeps its results beside the working tree's in memory and writes none of them to the findings files. |
| Key placeholder | The `<name>` in a setting key, such as `tests.<name>.command`. The manifest that publishes the key declares it, with a pattern or a list of values. |
| Editor | The program Open in Editor launches, named in Settings as blank (the system default), an app's name or a shell command; a shell command may use `{file}` and `{line}` placeholders, for example `code -g {file}:{line}`, to open at a line. |
| Picker | The inspector's Dependencies tab: its Uses and Used by sections list what the selection uses and what uses it, grouped by folder, to put on the canvas. |
| Eye | The 16px icon at the right end of a file or folder row that shows whether the file is on the canvas and puts it on or takes it off (half for a folder with only some files on); it does nothing else. |
| Trail | The inspector panels opened by following files through their Dependencies, one to the right of the next, with breadcrumbs naming each step. |
| Strip | A narrow vertical column naming a trail panel that is folded out of view, to the left of the shown panels or, once an earlier one is brought back, to their right. Clicking it brings the panel back. |
| Breadcrumbs | The row above a trail's panels naming each file in the trail and each step's relationship (uses or used by), with the route icon that puts the whole trail on the canvas at its end. |
| Fold | Drawing an open folder as one box, which keeps its health disc and takes the edges to anything inside it. |
| Contents | A file's members as cards in file order, or a folder's files. |
| Card | A member shown in Contents with its label, line and code. |
| Function length | The span from a function or method's first line to its last, shown on its inspector card as `N lines` with a bar scaled to the file's largest, banded neutral at 20 lines or fewer, long (amber) from 21 to 50 and red over 50. The red band over 50 is only a visual band. |
| Body length | The lines from a function or method's `body_line` to its last, so a signature is not counted; the measure the `long_function` finding uses when the scan carries `body_line`, the first line of the body. |
| Show private | The remembered switch that adds non-exported members and private fields and methods to Contents. |
| Health disc | A dot on each file, folder and box: green fine, amber a warning, red a violation, a grey ring not measured. A folder shows the worst inside it. |
| Principle | The published principle a finding rests on, named by a stable id from the registry in `packages/cli/src/principles.ts` and shown by its name. |
| Citation | The author, work, year and optional locator a finding carries for its principle, taken from the registry; absent for the repository's own policy rule. |
| Finding | A violation or warning a sensor wrote for the current scan: a stable id, a kind, a principle, a citation where the principle is published, a one-line summary, its evidence by scan id and, where one is named, a fix pattern. Attached to the files in its evidence; a health disc shows the summary. |
| SensorFindings | One sensor's stored findings with the freshness they were measured under: the sensor, the commit, whether the working tree was dirty, its settings, the hashes of the inputs and tests it ran over, and its Findings. One per sensor, kept in `.recognizer/cache/findings/<sensor>.json`. |
| Needs attention | The tree filter that keeps only files with an amber or red disc. |
| Focus | Narrowing the canvas to one folder's files. |
| Legend | The panel on the canvas, opened from its bottom-right controls, that names every edge style, every disc and what a frame's figure counts, and holds the inferred-edges switch. |
| Box | What the canvas draws for a file, or for a folded folder: its disc, its name and, when it has a note, its note mark. |
| Box description | The small panel that fades in directly under a hovered canvas box, as wide as the box, showing the file's one-line description from the describer; a box with no description shows none. |
| Private-name import | An import of a name the target file does not export. Drawn dashed. For a Python file structural analysis also reports it as a `private_imports` finding on the importing file. |
| Evidence | Why an edge exists: the quoted source line, the names, the route, or what an inferred edge was inferred from. |
| View state | Everything that decides what the user sees, as one record. Each change makes a new one; it lasts only as long as the window. |
| History | The sequence of view states the user has moved through in a window; back and forward walk it. It is never saved. |
| Rail | The thin strip of icons at the window's far left, one per left-hand panel; an icon opens its panel, or closes it when it is open. |
| Files panel | The rail's panel holding the tree. |
| Saved view | A named view committed at `.recognizer/views/<name>.json`: its title, its description, the commit it was saved at, its steps and its notes. |
| Modified view | A saved view whose canvas contents differ from its saved file, shown by the muted "modified" beside its name; panning and zooming do not count. |
| Revert | The view bar's button that restores a modified saved view's saved contents and camera, with Undo, or only the camera when that is all that moved. |
| Unsaved-changes dialog | The dialog, centred over the window on a dimmed backdrop, that asks whether to save a modified view before Clear or opening another view closes it. |
| View title | The optional heading text of a saved view, separate from its name. |
| View details card | The card under the view bar, or in place of a Views panel row, that edits a view's name, title and description together, with Cancel and Save. |
| View heading | The title and description of a saved view, drawn centred above the diagram and moving with it. |
| Change view | A saved view that holds a git range (base..head), re-diffed when it opens; the diff's files are on the canvas, drawn from the head scan plus the base scan's removed files, marked added, modified, renamed or removed. A test file is never a box, so it is counted as not on the canvas whatever its status. The view's `change` may carry the name of the pick that opened it. |
| Renamed | The change view's mark for a file git reports as renamed (`R` in `git diff -M --name-status`): one file at its new path, with the old path noted as `from`; the old path has no node. |
| Plan | A saved view marked `plan: true` that shows what is intended before the code exists: its files may carry a proposed change, and it has no change range. A view is never both a plan and a change view. |
| Proposed change | What a plan says will happen to one file: new, changes, moves, moves and changes, or removed. It is the view file's `proposed` entry, the `--change` kind on `views add` and `views change`, and a coloured border on the canvas. It is not the range of a change view. |
| Planned file | A file a plan names with a proposed change of new, moves or moves and changes that the scan does not hold. It has a box, takes a note and never makes the view stale. |
| Ghost box | The dashed box a plan draws at the old path of a moved file, reading "moving to" the new folder, with a dashed arrow to the file's new box. It is not a file: it takes no note and cannot be selected. |
| Member reference | How a plan names one member: `module#Name` for a function, class or other top-level member, or `module#Class.method` for a method. The file is everything before the last `#`. It is the argument of `views add`, `views change` and `views remove` and, split into `module` and `member`, a `proposed` entry in the view file. |
| Member mark | The coloured band and icon on the right edge of a member's row in the inspector's Contents: a plus for new or added, a triangle outline for changes or modified, a minus for removed. A plan's marks come from its member entries, a change view's from its git range, where a renamed file's marks come from its old text at the old path and its new text at the new path. Marks never show on the canvas. |
| Head scan | The scan of a change view's modified files as they are at its head commit, made from git, which supplies the head's members for the inspector whatever branch is checked out. |
| Stale view | A saved view the list shows under Stale with Delete: a change view whose head is merged or whose branch is gone, or any view with a pick that no longer resolves. |
| Views panel | The left-column panel, behind the rail icon between Files and Notes, that lists every saved view: live ones, then stale ones, each with Edit and Delete (stale ones only Delete); opened from the view bar's All views link. |
| Note | The one text a person or an agent attaches to a file or folder in a saved view, with the name of who last wrote it; writing again replaces it. |
| Notes panel | The left-column panel, behind the rail's speech-bubble icon, that lists every noted box and folder in the view, numbered and in reading order with a drag handle on each row, and focuses the selected note; the overview, with no composer. |
| Note bubble | The speech bubble hanging from a box's or folder's note mark that holds its one note, who last wrote it, Edit and Remove, and its number, "n of N", and Previous and Next that pan the canvas to the next box with the bubble kept where it is; the place notes are read and written, opened from the mark, the bar's notes button or N. |
| Note mark | The small outlined speech-bubble icon after a noted box's name or at a noted frame's corner; clicking it opens the bubble. |
| Note focus | A file selection with its note bubble open; kept while the noted box stays selected, cleared by any other selection or Escape. |
| Scan panel | The left-column panel, behind the Scan rail icon, that shows one list of Scan rows and one Scan button, with the ticks a repository remembers. |
| Scan row | One entry of the Scan panel's list: a checkbox, a name and a state in words (not yet run, a count with an age, running, waiting, or failed). |
| Scope (Only this view) | The Scan panel's switch, shown only while a view is open and remembered with the row ticks. When it is on, a run describes only the view's stale files and mutates only the functions of the view's files; C.R.A.P. and the duplication check of structural analysis still cover the whole repository; in a plain run the Mutation list is the union of the out-of-date and missing files. `recognizer scan --modules <file>` takes the file ids as a JSON array and applies the same scope. |
| Suite tick | A checkbox beside one Test suite under C.R.A.P. or Mutation in the Scan panel, remembered per repository and per sensor. A scan runs only the ticked suites of an armed sensor and keeps every other suite's last result; a suite new to the Config starts ticked. | Suite fold | The chevron under C.R.A.P. and Mutation in the Scan panel that lists every Test suite with its Suite tick, result and short age. It is closed by default, whether it is open is remembered per repository, and a closed fold's row summarises the ticked suites. |
| Suite record | The file `.recognizer/cache/suites/<sensor>.json` in which C.R.A.P. and Mutation keep, per Test suite, when it last ran, its status, its counts, the hashes of the sources and tests it ran over and, for C.R.A.P., its coverage part. Only the sensors read it; a partial run composes the sensor's whole result from it. |
| Phase | One of the parts of a scan: extraction (when the files changed), describing (when ticked), measuring (CLI only, when asked for) and the sensors (when ticked). |
| Findings panel | The left-column panel, behind the Findings rail icon: a heading with one muted count line, then one collapsible group per finding kind, each holding cards. |
| Finding group | One collapsible kind in the Findings panel, named by the kind, a report or an unknown kind: a chevron, a severity dot, the name, an info icon when the group has help, and its count. Collapsed until clicked. |
| Finding group name | The plain name a built-in finding group shows, beside the finding kind it holds: `rule-violation` Breaks the policy, `cycle` Import cycle, `orphan` Orphan, `unused_exports` Unused exports, `private_imports` Private imports, `long_function` Long functions, `complexity` Complexity, `duplication` Duplicated code, `crap` C.R.A.P., `coverage` Low coverage, `mutation` Mutations. | Group help | The two plain sentences a finding group can carry, "What it means" and "What to do", shown in a tip when the info icon beside the group name is hovered or focused. A reported group and an unknown kind have none and show no icon. |
| Finding card | A finding in the panel or in the inspector's Findings tab: the subject in bold, its folder muted beneath it and one plain sentence; opened inline to a row per file, member or edge involved, with Add to view on a row whose file is off the view. |
| Finding focus | One finding card open: the evidence lit on the canvas and the rest dimmed, with no selection and no box added. Cleared by Escape, by clicking the open card, or by selecting a box outside the evidence. |
| Description | A saved view's required one- or two-sentence statement of what it shows. |
