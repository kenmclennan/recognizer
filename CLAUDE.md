# Recognizer

Scans codebases into a language-neutral structure model and shows it in a native viewer. [README.md](README.md) says what it is for.

## Design

The design of record is [docs/design.md](docs/design.md). It is temporary: it holds the design while it is decided and built, and is deleted once the code and these docs carry it. Build against it; do not restate it here.

- Its **Decided** section is settled. Do not reopen a decision without Ken.
- Its **Open** section is decided with Ken one question at a time, in the order listed, each recorded under Decided before anything is built on it.
- Its **First build items** section is the build order once the open decisions it names are settled.

The words the code, docs and interface use are defined in [docs/glossary.md](docs/glossary.md); add a term there before using it.

This repo is lightcycle project `kenmclennan/recognizer`, shortcode `REC`; work is filed and built through lightcycle.

## Layout

One repository, a directory per part:

- `schema/` - the JSON Schemas and example files for the scan document, the saved view file, `config.yaml`, `responsibilities.json`, the overlay file (`overlay.schema.json`) and the findings document (`findings.schema.json`, with examples in `findings-examples/`) and the run log record (`log.schema.json`, with examples in `log-examples/`)
- `scripts/` - the toolchain archive builder (`build-toolchain.mjs`), the lockfile closure it vendors (`toolchain-closure.mjs`), the archive check (`verify-toolchain.mjs`) and the Homebrew renderer (`render-homebrew.mjs`), the install guard that opens both gates (`require-install.mjs`), the temp-directory leak guard that wraps each suite (`assert-clean-tmpdir.mjs`: runs it with `TMPDIR` on a fresh folder and fails if anything is left) and the shared test helper that removes temp folders after each file (`temp-dirs.mjs`, `vitest-remove-temp-dirs.mjs`), with their tests; the archive holds the CLI, the TypeScript, Python, Kotlin and Rust scanners (the Rust one a prebuilt arm64 binary, the Kotlin one with a vendored wheelhouse) and the claude describer
- `check/` - the `recognizer` CLI, dispatched and documented from one command table (`commands.ts`, `help.ts`): `check` reports violations, baseline growth, graph metrics and warnings, for the repository's current scan (scanning first when stale; `check [<module>...]` narrows the report) or, with `--scan`, for a scan file; `find`, `show` and `modules` read the scan (`read-commands.ts`; `findings.ts` holds `findingsByModuleFrom` and is exported from the library, `member-tokens.ts` the one signature token model, exported from the library); `scan` is one pipeline in three phases (`scan-phases.ts` holds the pure decision, flag parsing and event lines): extraction only when the scans are not current or with `--extract`, then the structure sensor, then `--describe[=all]` (the shared `describeModules` in `describe-modules.ts`) and `--sense all|<names>` (the shared `runSensors` in `run-sensors.ts`), printing one JSON line per event with `--json`; `uses`, `used-by`, `callers` and `path` answer questions from a fresh scan (`freshness.ts`); `open` starts the viewer on a folder or a `recognizer://` link (`open-command.ts`; `link.ts` parses and checks links, shares `fixtures/links/syntax.json` with `app/src-tauri/src/link.rs`, and is exported from the library); `views` builds, shows and checks the saved view files at `.recognizer/views/<name>.json` (`notes-order.ts` is the pure order model for notes - append, place, move, reorder, number, drop index - exported from the library; `views.ts` validates and resolves them, holds the version 4 `notes` list and `ordered` flag (absent for a walkthrough, `false` for a lens) with `isOrdered` and the one `serialiseView` both the CLI and the app write through, at most one note per module or folder path with the last kept and one warning from `noteWarnings` when a file holds several, with `migrateView` and `viewNotes`, and is exported from the library, `views-command.ts` is the CLI); `config-parse.ts` expands a command-less `sensors` entry named for a shipped sensor (`duplication: {threshold: 0.9}`) to the `recognizer-sensors` command through `shipped-sensors.ts` (`expandShortForms`, `SHIPPED_SENSORS`), so every consumer sees an ordinary registration; `measure` runs the overlays a repository registers in `.recognizer/config.yaml` and writes `.recognizer/cache/overlays/<name>.json` (`measure-command.ts`; `overlays.ts` holds `validateOverlay` and is exported from the library), `scan --sense` runs the sensors a repository registers under `sensors` in `.recognizer/config.yaml` and `check` runs the built-in structure sensor (`structure-sensor.ts`, no IO, exported from the library, with the folder-cycle, orphan, policy-drift, stable-dependencies and stable-abstractions warnings in `structure-warnings.ts`, the per-folder package metrics behind the last two in `folder-metrics.ts` and the entry-point rule in `entry-points.ts`; `structure-run.ts` writes its findings file for both `check` and `scan`) and reads every findings file, each sensor writing `.recognizer/cache/findings/<name>.json` (`findings-files.ts` holds the path, the atomic write and the reader, `findings-document.ts` the types and `validateFindings`, `registered-command.ts` the command runner `measure` shares, `load-findings.ts` the `loadFindings` that `show` and `modules --findings` read through), and `windows` and `window` read the running app's open windows over its local socket, `window <id> add|remove|fold|focus|select|trail|open-view|clear ... [--by <name>]` changes one (the `drive` request, answered done or refused), and `views new --from-window` saves one as a view (`window-commands.ts`; the one seam is `Io.request`), `help agents` prints the guide an agent follows (`agent-guide.ts`, its command section generated from the table) and `agents install|uninstall` writes or removes the Claude Code skill and the deny rule on `**/.recognizer/**` in `~/.claude` (`agents-command.ts`), and `describe` runs the describer a repository registers in `.recognizer/config.yaml` (`config.ts`) for every module whose line in `.recognizer/responsibilities.json` is missing or out of date, and `describe --check` reads the lines without running it (`describe-command.ts`; `responsibilities.ts` holds the file's types, `validateResponsibilities` and `lineStatus` and is exported from the library); `scan` (one record with a `phases` array), `describe` and `measure` each leave one record in `.recognizer/cache/log/` (the last fifty, written by the pure `run-log.ts` through `Io.now()`, validated by `log-document.ts`), read with `log [<id>] [--last] [--kind ...]` (`log-command.ts`). The neighbour, caller and path logic the app also uses lives in `neighbours.ts`, `callers.ts` and `paths.ts` and is exported from the library ([check/README.md](check/README.md))
- `packaging/homebrew/` - the formula and cask templates the release renders into the tap
- `THIRD-PARTY-NOTICES.md` - generated by `app/scripts/third-party-notices.mjs` from `package-lock.json` (npm production packages) and the app's and the Rust scanner's Cargo manifests (the Rust crates, via `cargo metadata`; `rust-notices.mjs` fails on a crate outside the accepted licence list); shipped in the app bundle and the toolchain archive
- `policies/` - starter policies a scanned repository copies into `.recognizer/policy.yaml`
- `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/` - one standalone CLI per language (`recognizer-scan-rust` is Rust on `syn`, one module per `.rs` file, with its own `cargo test` workflow); the Kotlin scanner is Python on py-tree-sitter, one module per package directory, and its real-content test needs `RECOGNIZER_KOTLIN_PETCLINIC` (the pinned petclinic checkout; CI sets it and `RECOGNIZER_REQUIRE_REAL_CONTENT=1`)
- `sensors/` - the shipped sensors, one Python package (`recognizer-sensors`, hatchling and uv as `scanners/kotlin/`, py-tree-sitter with the TypeScript, Python, Kotlin and Rust grammars pinned in `pyproject.toml`): `recognizer-sensors <name> [--repository P] [--commit C] [--output F] [--settings JSON]` writes one findings file, exit 2 on an unknown name or bad arguments; `registry.py` holds the names and each sensor's `run`, which returns an `Outcome` (findings and an optional overlay the CLI writes before the findings file) (equal to `fixtures/sensors/shipped.json`, which `check/src/shipped-sensors.ts` `SHIPPED_SENSORS` also reads), `duplication/` the duplication sensor (normalised syntax tree, depth-3 structural fingerprints, Jaccard score, defaults `threshold` 0.82, `min_lines` 4, `min_nodes` 20), `crap/` the CRAP sensor (cyclomatic complexity per function from the tree, per-line coverage from the LCOV file the `coverage` setting names, `crap = cc^2 * (1 - coverage)^3 + cc`; settings `threshold` 30, `coverage` `coverage/lcov.info`, `overlay` `.recognizer/cache/overlays/crap.json`; it writes that overlay beside its findings file), `mutate/` the mutation measurer (a measurer, not a sensor: `MEASURERS` in `registry.py`; `recognizer-sensors mutate` reads the CRAP overlay and the LCOV file, applies the operator table in `sites.py` to covered functions, runs the required `test_command` once per mutant in a private copy under `.recognizer/cache/mutation/work/` with `runner.py` and writes the `killed`, `survived`, `uncovered` and `score` overlay plus a second output, the survivors file `.recognizer/cache/mutation/survivors.json`; its metric declarations are in `fixtures/sensors/measurers.json`, which `check/src/shipped-sensors.ts` `SHIPPED_MEASURERS` reads and `expandMeasurerShortForms` expands for `overlays: {mutate: {test_command: [...]}}`), `mutation/` the mutation sensor (reads that overlay and the survivors file, one warning per function with a survivor, nothing when either is missing or stale), `unused_exports/` the unused-exports sensor (reads the scans' members and edges, one warning per module listing the exports no other module's edge names; `entry_points.py` ports the structure sensor's entry-point rules and `fixtures/sensors/entry-points.json` checks both; its `entry_points` default is the orphan globs, copied in by `expandConfig` in `check/src/config-parse.ts`), `functions.py` and `identity.py` shared by the CRAP and duplication sensors and the measurer; its tests are pytest in `sensors/tests/` and `check/test/sensors.integration.test.ts` (runs `recognizer scan --sense duplication` over `fixtures/duplication/sample` and `--sense crap` over `fixtures/crap/sample`); the measurer's fixture is `fixtures/mutate/sample` (a weak, a strong and a slow test script), and CI is `sensors.yml`; it ships in the toolchain archive beside the scanners
- `describers/claude/` - the reference describer: `recognizer-describe-claude <request-file>` sends the request `recognizer describe` writes to `claude -p` with the fixed prompt in `prompt.md` and prints one line; its version is derived from the prompt file and registered in `.recognizer/config.yaml`
- `app/` - the Tauri viewer, built from `kenmclennan/tauri-starter` ([app/README.md](app/README.md))
- `fixtures/` - small sample codebases per language, each with its expected scan; `fixtures/window-socket/` holds the request and response pairs the Rust socket tests and the CLI tests share

`schema/`, `check/`, `policies/`, `sensors/`, `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/`, `describers/claude/`, `app/` and `fixtures/` exist.

## Rules

- **The scan document is the contract.** Every scanner emits exactly the schema; nothing language-specific leaks into the document, the policy or the viewer. Every scanner is tested against the shared fixtures.
- **Recognizer knows no architecture.** Every architectural meaning - component names, which dependencies are permitted, any preset - lives in a repository's policy. A named architecture is a template under `policies/`, copied into a repository and edited there. Hexagonal vocabulary appears only in fixtures, examples and templates. Warnings are principle violations, reported by `recognizer check` as candidates with evidence, never verdicts; each names its principle, its evidence and a stable fix-pattern id, and the coaching text an agent reads lives outside recognizer.
- **Recognizer never measures.** Metrics that need something run (tests, mutation, duplication, git history) arrive as overlays, produced by tools a repository registers in `.recognizer/config.yaml`; recognizer runs them and owns the overlay format and the registration, never a metric's meaning.
- **Derived, never authored.** Nothing on the real diagram is drawn by hand. A proposed structure is a separate artifact, always labelled as not in the code.
- **No allow list.** The policy cannot mark a violating edge as acceptable. Existing violations live in a baseline that may only shrink.
- **Missing data is unknown, never healthy.**
- **Prior art is for approach only.** Robert C. Martin's [uml-viewer](https://github.com/unclebob/uml-viewer) states no licence: copy or port none of its code. Its published rules (what counts as an edge, what to skip, how interfaces are marked) may be followed.
- **Scanned repositories own their `.recognizer/` folder.** Policy, tooling configuration (`config.yaml`), saved views, module responsibilities (`responsibilities.json`), proposals and baselines are committed there; scans, overlays, findings and run logs go in `.recognizer/cache/` (`log/` holds the run records), which is gitignored.

## Worktrees

A fresh worktree has no `node_modules`. Run `npm ci` at the repository root before typecheck, tests or any `npm run` script; the root install covers every workspace. `npm run check` and `npm run check:app` start with `scripts/require-install.mjs`, which exits 1 with "run npm ci at the repository root" when `node_modules` is missing, older than `package-lock.json` or lacks a workspace. Run app tools through their npm scripts, whose `pre*` hooks rebuild `check/dist`; a direct `tsc` or `vitest` call needs `npm run build -w recognizer` first.

## Gate risks

- A test that needs a temp folder makes it with `makeTempDir` from `scripts/temp-dirs.mjs` (look tests use `look-page.ts`), so it is removed after the file; every suite runs under `scripts/assert-clean-tmpdir.mjs`, which fails on anything left in `TMPDIR`.
- Biome formats and lints code (`npm run lint -w @recognizer/app`, `lint:fix` to apply). Prettier is for Markdown only; never run it over code or the whole repository.
- The `*-look.test.ts` files drive a headless Chrome and take about a minute each. While iterating, run only the file you are changing (`npm run test -w @recognizer/app -- src/<name>.test.ts`); run the full suite before you finish.
- The Rust scanner's real-content test (`scanners/rust/tests/real_content.rs`) pins the app crate's own shape from `fixtures/rust/recognizer-baseline.json`: adding, removing or re-wiring a Rust module under `app/src-tauri` changes its module, file or edge counts and fails `check:app` (its `check:rust` step runs `cargo test --locked` in `scanners/rust`, as does the app workflow) and the scanner-rust workflow. After any such change run `cargo test --locked` in `scanners/rust` and update the baseline and the test's counts in the same commit.
- Window geometry and native dialog presentation cannot be seen from the pool: a look test runs in headless Chrome, not in the Tauri window, so it cannot prove a window's size, a sheet's placement or a clipped button. A test about size asserts the inner size the Rust builder sets, never a figure derived from the outer size or a title bar; everything else visible only in the running app is the driver's check at review, named as such in the brief, and a worker says so in its closing note rather than treating the look test as proof.
- The full `npm run check:app` takes about 5-6 minutes. Run it once, at the end, from the repo root, with the longest timeout; a timeout is not a failure, so do not re-run it.

## CI

Every pull-request and push workflow runs on a GitHub-hosted runner; the repository is public, so those minutes are free. `app` and the `toolchain` job of `check` (which builds the macOS arm64 archive) run on `macos-15`; `check`'s `test` job, `markdown`, `describer-claude`, `sensors` and the four `scanner-*` workflows run on `ubuntu-latest`, so a test in them must not assume a Mac path or tool. A hosted runner has only what the image and the workflow's own setup steps provide (Node from `actions/setup-node`, `uv` from `astral-sh/setup-uv`): no `recognizer-scan-*` binary is on the PATH, so a test that runs a real scan must build or install the scanner it needs inside the workflow, or it fails only on CI. Only `release.yml` runs on the self-hosted runner on Ken's Mac (`runs-on: [self-hosted, macOS, ARM64]`), which has the local toolchain. No workflow uses `Swatinem/rust-cache`: on the self-hosted runner its cleanup prunes `~/.cargo/bin` and deletes `rustup`, which takes `cargo` and `rustc` with it.

## Code style

- No code comments and no docstrings; behaviour is legible from names and tests.
- Blank lines group related statements; whitespace around multi-line statements.
- Markdown: hyphens not emdashes, one line per paragraph, formatted with `prettier --prose-wrap=never` and linted with markdownlint (line length is off, `.markdownlint.json`).
- Keep this file current as the code changes, in the same change.
