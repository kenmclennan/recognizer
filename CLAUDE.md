# Recognizer

Scans codebases into a language-neutral structure model and shows it in a native viewer. [README.md](README.md) says what it is for.

## Design

The design of record is [docs/design.md](docs/design.md). It is temporary: it holds the design while it is decided and built, and is deleted once the code and these docs carry it. Build against it; do not restate it here.

- Its **Decided** section is settled. Do not reopen a decision without Ken.
- Its **Open** section is decided with Ken one question at a time, in the order listed, each recorded under Decided before anything is built on it.
- Its **First build items** section is the build order once the open decisions it names are settled.

The words the code, docs and interface use are defined in [docs/glossary.md](docs/glossary.md); add a term there before using it.

This repo is lightcycle project `kenmclennan/recognizer`, shortcode `REC`; work is filed and built through lightcycle.

## Layout

One repository, a directory per part:

- `schema/` - the JSON Schemas and example files for the scan document, the saved view file, `config.yaml`, `responsibilities.json`, the overlay file (`overlay.schema.json`) and the findings document (`findings.schema.json`, with examples in `findings-examples/`)
- `scripts/` - the toolchain archive builder (`build-toolchain.mjs`), the lockfile closure it vendors (`toolchain-closure.mjs`), the archive check (`verify-toolchain.mjs`) and the Homebrew renderer (`render-homebrew.mjs`), the install guard that opens both gates (`require-install.mjs`), the temp-directory leak guard that wraps each suite (`assert-clean-tmpdir.mjs`: runs it with `TMPDIR` on a fresh folder and fails if anything is left) and the shared test helper that removes temp folders after each file (`temp-dirs.mjs`, `vitest-remove-temp-dirs.mjs`), with their tests; the archive holds the CLI, the TypeScript, Python, Kotlin and Rust scanners (the Rust one a prebuilt arm64 binary, the Kotlin one with a vendored wheelhouse) and the claude describer
- `check/` - the `recognizer` CLI, dispatched and documented from one command table (`commands.ts`, `help.ts`): `check` reports violations, baseline growth, graph metrics and warnings, for the repository's current scan (scanning first when stale; `check [<module>...]` narrows the report) or, with `--scan`, for a scan file; `find`, `show` and `modules` read the scan (`read-commands.ts`; `findings.ts` holds `findingsByModuleFrom` and is exported from the library, `member-tokens.ts` the one signature token model, exported from the library); `scan` detects languages, runs each scanner and writes the cache; `uses`, `used-by`, `callers` and `path` answer questions from a fresh scan (`freshness.ts`); `open` starts the viewer on a folder or a `recognizer://` link (`open-command.ts`; `link.ts` parses and checks links, shares `fixtures/links/syntax.json` with `app/src-tauri/src/link.rs`, and is exported from the library); `views` builds, shows and checks the saved view files at `.recognizer/views/<name>.json` (`views.ts` validates and resolves them, holds the version 3 `notes` list with `migrateView` and `viewNotes`, and is exported from the library, `views-command.ts` is the CLI); `measure` runs the overlays a repository registers in `.recognizer/config.yaml` and writes `.recognizer/cache/overlays/<name>.json` (`measure-command.ts`; `overlays.ts` holds `validateOverlay` and is exported from the library), `sense` runs the sensors a repository registers under `sensors` in `.recognizer/config.yaml` (`sense-command.ts`) and `check` runs the built-in structure sensor (`structure-sensor.ts`, no IO, exported from the library) and reads every findings file, each sensor writing `.recognizer/cache/findings/<name>.json` (`findings-files.ts` holds the path, the atomic write and the reader, `findings-document.ts` the types and `validateFindings`, `registered-command.ts` the command runner `measure` shares, `load-findings.ts` the `loadFindings` that `show` and `modules --findings` read through), and `windows` and `window` read the running app's open windows over its local socket, `window <id> add|remove|fold|focus|select|trail|open-view|clear ... [--by <name>]` changes one (the `drive` request, answered done or refused), and `views new --from-window` saves one as a view (`window-commands.ts`; the one seam is `Io.request`), `help agents` prints the guide an agent follows (`agent-guide.ts`, its command section generated from the table) and `agents install|uninstall` writes or removes the Claude Code skill and the deny rule on `**/.recognizer/**` in `~/.claude` (`agents-command.ts`), and `describe` runs the describer a repository registers in `.recognizer/config.yaml` (`config.ts`) for every module whose line in `.recognizer/responsibilities.json` is missing or out of date, and `describe --check` reads the lines without running it (`describe-command.ts`; `responsibilities.ts` holds the file's types, `validateResponsibilities` and `lineStatus` and is exported from the library). The neighbour, caller and path logic the app also uses lives in `neighbours.ts`, `callers.ts` and `paths.ts` and is exported from the library ([check/README.md](check/README.md))
- `packaging/homebrew/` - the formula and cask templates the release renders into the tap
- `THIRD-PARTY-NOTICES.md` - generated by `app/scripts/third-party-notices.mjs` from `package-lock.json` (npm production packages) and the app's and the Rust scanner's Cargo manifests (the Rust crates, via `cargo metadata`; `rust-notices.mjs` fails on a crate outside the accepted licence list); shipped in the app bundle and the toolchain archive
- `policies/` - starter policies a scanned repository copies into `.recognizer/policy.yaml`
- `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/` - one standalone CLI per language (`recognizer-scan-rust` is Rust on `syn`, one module per `.rs` file, with its own `cargo test` workflow); the Kotlin scanner is Python on py-tree-sitter, one module per package directory, and its real-content test needs `RECOGNIZER_KOTLIN_PETCLINIC` (the pinned petclinic checkout; CI sets it and `RECOGNIZER_REQUIRE_REAL_CONTENT=1`)
- `describers/claude/` - the reference describer: `recognizer-describe-claude <request-file>` sends the request `recognizer describe` writes to `claude -p` with the fixed prompt in `prompt.md` and prints one line; its version is derived from the prompt file and registered in `.recognizer/config.yaml`
- `app/` - the Tauri viewer, built from `kenmclennan/tauri-starter` ([app/README.md](app/README.md))
- `fixtures/` - small sample codebases per language, each with its expected scan; `fixtures/window-socket/` holds the request and response pairs the Rust socket tests and the CLI tests share

`schema/`, `check/`, `policies/`, `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/`, `describers/claude/`, `app/` and `fixtures/` exist.

`app/` is the npm workspace `@recognizer/app`: Vite, TypeScript and plain DOM in `app/src/`, and the Rust crate `recognizer_app` in `app/src-tauri/`. It imports `check` as a library (`recognizer`, built to `check/dist` by the `pre*` scripts). Its rules:

- Logic goes in pure modules with unit tests (`scan-loading`, `folder-compaction`, `tree-model`, `tree-filter`, `health`, `open-modules`, `canvas-state`, `canvas-graph`, `canvas-layout`, `canvas-scene`, `canvas-keys`, `notes-order`, `bar-hover`, `edge-evidence`, `inspector-model`, `show-private`, `editor-open`, `picker-model`, `row-model`, `panel-widths`, `view-steps`, `view-file`, `stale-report`, `view-history`, `window-state`, `viewport`, `wheel-device`, `layout-source`, `tools-notice`, `footer-scan`, `rescanner`, `trail-model`, `responsibility-model`, `busy-gate`, `view-notes`, `view-link`, `window-drive`, `agent-line`, `sensor-run`); views and sources (`*-view.ts`, `*-source.ts`) stay thin, the ELK layout runs in the `layout.worker.ts` web worker, and `main.ts` is the composition root. Rust stays the narrow boundary for the dialog, the app's settings (`settings.rs`: the `editor` key of `config.json`, leaving any other key as it is, read and written for the Settings window `settings.html`, which `settings-view.ts` builds), launching the editor (`editor.rs`: system default, an app's name or a shell command), the changed-since rule (`changes.rs`: the baseline built from the cached scans' recorded files, hashes and selection, the comparison and the 2-second poller behind `changes-changed`), running `recognizer scan`, asking the installed command for its version (`recognizer_version`, behind the footer's out-of-step notice), reading the cache and launch arguments, the module responsibility lines (`responsibilities.rs`: `read_responsibilities` reads `.recognizer/responsibilities.json` and `config.yaml` with the SHA-256 of each module's source, `describe_module` runs `recognizer describe <module> --json` for one module, and the `responsibilities-changed` watcher), the sensors (`sensors.rs`: `write_structure` writes or removes `.recognizer/cache/findings/structure.json`, `read_findings` reads every findings file, `remove_findings` deletes named ones, `read_sensor_inputs` reads `policy.yaml`, `config.yaml` and the baseline fresh, and the `sensor-inputs-changed` watcher; the app runs the structure sensor alone and never a registered sensor's command), the app socket (`socket.rs`: `app.sock` in the app's config folder, mode 0600, one JSON line per request and per response, answering `windows` and `window` from the state each window publishes through `publish_window_state`, and `drive`, which emits `window-drive` to one window and waits up to 3 seconds for its `answer_window_drive`), and the saved views (`views.rs`: list, write, rename, current view, the view's link, git-rename and commit-scan lookups, `view_author` (the `git config user.name` of the window's folder, or `Me`, written as the author of a note made in the app), and the `.recognizer/views/` watcher), the recent folders (`recent.rs`: `recent.json` in the app's config folder, the last ten canonical folders opened any way, most recent first, written through a temp file and rename, the pure `labels` that name each entry by folder (adding the parent when two collide), and the pure `open_target` that decides whether Open assigns the chosen folder to the focused window or opens a new one; `lib.rs` rebuilds File > Open Recent from it), and links (`link.rs` parses and validates `recognizer://open?repo=...&view=...`; `lib.rs` `handle_link` routes one through `windows.rs` `route_for` to the window already holding the folder or a new one, parks the view with `take_pending_view` and emits `view-link`; a refused link shows a dialog; a link never scans, describes or writes; the `view_link` command builds the link Copy link copies). `showExplorer` reaches them through the `ViewsPort` (`views-port.ts`, `views-source.ts`; `views-fake.ts` in tests) the `EditorPort` (`editor-port.ts`, `editor-source.ts`; `editor-fake.ts` in tests), the `ResponsibilitiesPort` (`responsibilities-port.ts`, `responsibilities-source.ts`; `responsibilities-fake.ts` in tests) and the `SensorsPort` (`sensor-run.ts`, `sensors-source.ts`; `sensors-fake.ts` in tests), the `WindowPort` (`window-port.ts`, `window-source.ts`; `window-fake.ts` in tests), which publishes what the window shows and delivers the `drive` commands an agent sends (`onDrive`; `window-drive.ts` plans each one and the explorer applies it as one marked history entry, and `agent-line.ts` times the footer line that offers Undo).
- A command never takes a path from the frontend: Rust reads the folder from the window's assignment. Every window is built by `open_window` and labelled `w-<n>`, and `app/src-tauri/capabilities/default.json` grants the `app-access` permission set to `w-*`; `capabilities/settings.json` grants only `settings-access` to the `settings` window, which holds no folder and receives no menu action.
- Filesystem access goes through `fs_safe`. The `fs_safe` tests are required: they guard the path-confinement boundary, so they are never removed or weakened.
- The app updates only through Homebrew. A release publishes `recognizer-toolchain.tar.gz` (the CLI, every scanner and the claude describer) and `recognizer.app.tar.gz`, named by slug, to the releases repo and renders the formula and cask into `kenmclennan/homebrew-tap`; the `RELEASES_TOKEN` secret name is fixed across apps and must reach the tap. The footer's `tools-notice` shows when the app and the installed `recognizer` command differ in version.
- `npm run check` is the `check/` gate (lint, build, tests), the same steps CI runs; `npm run check:app` is the app's gate (typecheck, tests, lint, format check, `cargo test`, `cargo fmt --check`, `cargo clippy -D warnings`, build); `npm run install-app` builds the bundle into `~/Applications`.

## Rules

- **The scan document is the contract.** Every scanner emits exactly the schema; nothing language-specific leaks into the document, the policy or the viewer. Every scanner is tested against the shared fixtures.
- **Recognizer knows no architecture.** Every architectural meaning - component names, which dependencies are permitted, any preset - lives in a repository's policy. A named architecture is a template under `policies/`, copied into a repository and edited there. Hexagonal vocabulary appears only in fixtures, examples and templates. Warnings are principle violations, reported by `recognizer check` as candidates with evidence, never verdicts; each names its principle, its evidence and a stable fix-pattern id, and the coaching text an agent reads lives outside recognizer.
- **Recognizer never measures.** Metrics that need something run (tests, mutation, duplication, git history) arrive as overlays, produced by tools a repository registers in `.recognizer/config.yaml`; recognizer runs them and owns the overlay format and the registration, never a metric's meaning.
- **Derived, never authored.** Nothing on the real diagram is drawn by hand. A proposed structure is a separate artifact, always labelled as not in the code.
- **No allow list.** The policy cannot mark a violating edge as acceptable. Existing violations live in a baseline that may only shrink.
- **Missing data is unknown, never healthy.**
- **Prior art is for approach only.** Robert C. Martin's [uml-viewer](https://github.com/unclebob/uml-viewer) states no licence: copy or port none of its code. Its published rules (what counts as an edge, what to skip, how interfaces are marked) may be followed.
- **Scanned repositories own their `.recognizer/` folder.** Policy, tooling configuration (`config.yaml`), saved views, module responsibilities (`responsibilities.json`), proposals and baselines are committed there; scans and overlays go in `.recognizer/cache/`, which is gitignored.

## Worktrees

A fresh worktree has no `node_modules`. Run `npm ci` at the repository root before typecheck, tests or any `npm run` script; the root install covers every workspace. `npm run check` and `npm run check:app` start with `scripts/require-install.mjs`, which exits 1 with "run npm ci at the repository root" when `node_modules` is missing, older than `package-lock.json` or lacks a workspace. Run app tools through their npm scripts, whose `pre*` hooks rebuild `check/dist`; a direct `tsc` or `vitest` call needs `npm run build -w recognizer` first.

## Gate risks

- A test that needs a temp folder makes it with `makeTempDir` from `scripts/temp-dirs.mjs` (look tests use `look-page.ts`), so it is removed after the file; every suite runs under `scripts/assert-clean-tmpdir.mjs`, which fails on anything left in `TMPDIR`.
- Biome formats and lints code (`npm run lint -w @recognizer/app`, `lint:fix` to apply). Prettier is for Markdown only; never run it over code or the whole repository.
- The `*-look.test.ts` files drive a headless Chrome and take about a minute each. While iterating, run only the file you are changing (`npm run test -w @recognizer/app -- src/<name>.test.ts`); run the full suite before you finish.
- The Rust scanner's real-content test (`scanners/rust/tests/real_content.rs`) pins the app crate's own shape from `fixtures/rust/recognizer-baseline.json`: adding, removing or re-wiring a Rust module under `app/src-tauri` changes its module, file or edge counts and fails the scanner-rust workflow, which `check:app` does not run. After any such change run `cargo test --locked` in `scanners/rust` and update the baseline and the test's counts in the same commit.
- The full `npm run check:app` takes about 5-6 minutes. Run it once, at the end, from the repo root, with the longest timeout; a timeout is not a failure, so do not re-run it.

## CI

Every pull-request and push workflow (`app`, `check`, `markdown`, `describer-claude` and the four `scanner-*` workflows) runs on GitHub-hosted `macos-15`; the repository is public, so those minutes are free. A hosted runner has only what the image and the workflow's own setup steps provide (Node from `actions/setup-node`, `uv` from `astral-sh/setup-uv`): no `recognizer-scan-*` binary is on the PATH, so a test that runs a real scan must build or install the scanner it needs inside the workflow, or it fails only on CI. Only `release.yml` runs on the self-hosted runner on Ken's Mac (`runs-on: [self-hosted, macOS, ARM64]`), which has the local toolchain. No workflow uses `Swatinem/rust-cache`: on the self-hosted runner its cleanup prunes `~/.cargo/bin` and deletes `rustup`, which takes `cargo` and `rustc` with it.
