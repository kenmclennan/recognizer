# Recognizer

<!-- markdownlint-configure-file { "MD013": { "line_length": 600, "code_block_line_length": 600, "heading_line_length": 600 } } -->

Scans codebases into a language-neutral structure model and shows it in a native viewer. [README.md](README.md) says what it is for.

## Design

The design of record is [docs/design.md](docs/design.md). It is temporary: it holds the design while it is decided and built, and is deleted once the code and these docs carry it. Build against it; do not restate it here.

- Its **Decided** section is settled. Do not reopen a decision without Ken.
- Its **Open** section is decided with Ken one question at a time, in the order listed, each recorded under Decided before anything is built on it.
- Its **First build items** section is the build order once the open decisions it names are settled.

The words the code, docs and interface use are defined in [docs/glossary.md](docs/glossary.md); add a term there before using it.

This repo is lightcycle project `kenmclennan/recognizer`, shortcode `REC`; work is filed and built through lightcycle.

## Layout

One repository, a directory per part:

- `schema/` - the JSON Schemas and their example files: the scan document, the saved view file, `config.yaml`, `responsibilities.json`, the overlay file, the findings document and the run log record. An example folder beside a schema (`findings-examples/`, `log-examples/`) is validated by a test.
- `scripts/` - the toolchain archive builder and its lockfile closure, the archive check, the Homebrew renderer, the install guard both gates start with, and the temp-directory guards every suite runs under, each with its tests. The archive holds the CLI, the four scanners (the Rust one a prebuilt arm64 binary, the Kotlin one with a vendored wheelhouse) and the claude describer.
- `check/` - the `recognizer` CLI ([check/README.md](check/README.md)). Every command is one entry in the table in `commands.ts`, which dispatches it and generates `help` and the agent guide's command section, so a command exists nowhere else. A module the app also uses is exported from the library (`check/src/index.ts`), never copied.
  - Pure logic (the structure sensor, the view model, the scan phases, the run log) takes no IO, and the one seam to the running app is `Io.request`. A findings or overlay file is written through a temp file and rename, and validated on a precompiled validator because the app's CSP forbids eval. `.recognizer/cache/log/` keeps the last fifty records.
- `packaging/homebrew/` - the formula and cask templates the release renders into the tap
- `THIRD-PARTY-NOTICES.md` - generated by `app/scripts/third-party-notices.mjs` from `package-lock.json` (npm production packages) and the app's and the Rust scanner's Cargo manifests (the Rust crates, via `cargo metadata`; `rust-notices.mjs` fails on a crate outside the accepted licence list); shipped in the app bundle and the toolchain archive
- `policies/` - starter policies a scanned repository copies into `.recognizer/policy.yaml`
- `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/` - one standalone CLI per language (`recognizer-scan-rust` is Rust on `syn`, one module per `.rs` file, with its own `cargo test` workflow); the Kotlin scanner is Python on py-tree-sitter, one module per package directory, and its real-content test needs `RECOGNIZER_KOTLIN_PETCLINIC` (the pinned petclinic checkout; CI sets it and `RECOGNIZER_REQUIRE_REAL_CONTENT=1`)
- `sensors/` - the shipped sensors, one Python package (`recognizer-sensors`, hatchling and uv as `scanners/kotlin/`, py-tree-sitter grammars pinned in `pyproject.toml`), shipped in the toolchain archive. `recognizer-sensors <name> [--repository P] [--commit C] [--output F] [--settings JSON]` writes one findings file and exits 2 on an unknown name.
  - A sensor is a package under `src/recognizer_sensors/` registered in `registry.py`, whose `run` returns an `Outcome` (findings, and an overlay the CLI writes first); a measurer registers in `MEASURERS` there. The names in `registry.py`, `fixtures/sensors/shipped.json` and `fixtures/sensors/measurers.json` are read by `check/src/shipped-sensors.ts`, so they move together.
  - A sensor's defaults live in its own settings and its tests in `sensors/tests/`, with one end-to-end run per sensor in `check/test/sensors.integration.test.ts` over `fixtures/<sensor>/sample`. A sensor that reads another's overlay is listed after it in `config.yaml`.
- `describers/claude/` - the reference describer: `recognizer-describe-claude <request-file>` sends the request `recognizer describe` writes to `claude -p` with the fixed prompt in `prompt.md` and prints one line; its version is derived from the prompt file and registered in `.recognizer/config.yaml`
- `app/` - the Tauri viewer, built from `kenmclennan/tauri-starter` ([app/README.md](app/README.md))
- `fixtures/` - small sample codebases per language, each with its expected scan; `fixtures/window-socket/` holds the request and response pairs the Rust socket tests and the CLI tests share. `fixtures/links/syntax.json` is shared the same way by `check/src/link.ts` and `app/src-tauri/src/link.rs`.

`app/` is the npm workspace `@recognizer/app`: Vite, TypeScript and plain DOM in `app/src/`, and the Rust crate `recognizer_app` in `app/src-tauri/`. It imports `check` as a library (`recognizer`, built to `check/dist` by the `pre*` scripts). Its rules:

- Logic goes in pure modules with unit tests: a module is pure when it takes no DOM, no Tauri call and no timer it was not handed. `*-view.ts` and `*-source.ts` stay thin, the ELK layout runs in the `layout.worker.ts` web worker, and `main.ts` is the composition root. The list of pure modules is `app/src/` itself, not this file.
- The frontend reaches Rust only through a port: `<name>-port.ts` declares it, `<name>-source.ts` implements it over Tauri, `<name>-fake.ts` stands in for tests, and `showExplorer` receives them. A new Rust command needs a port method, a permission file under `app/src-tauri/permissions/` and an entry in `app.toml`, or the window refuses it at runtime while the look tests, which stub the port, pass.
- A look test's `HARNESS` is a template string that `look-page.ts` bundles with esbuild and runs in Chrome, so tsc never reads it: the `Loaded` value (the `base` object in `scan-panel-look.test.ts` and its siblings), the `scanHost` literal and the `registered()` wiring there are plain JavaScript. A new required field on `Loaded`, `ScanHost` or `registered()`'s result must be added by hand to every harness that builds one, or the look tests fail at run time and only the full app gate shows it.
- Rust is the narrow boundary: dialogs, the editor, settings, git, the filesystem, child processes and the socket. Everything else is TypeScript.
- `scan-ticks.json`, `recent.json`, `config.json` and `app.sock` live in the app's config folder, never inside a repository; the socket is mode 0600, one JSON line per request and per response.
- `stop_scan` kills the scan's process group, and so does closing the window; nothing a scan spawns may leave that group.
- The app runs the structure sensor itself, and a registered sensor or measurer only as a phase of `run_scan`, each name positional and checked by `sensor_name_ok` before anything spawns.
- A `recognizer://` link never scans, describes or writes; a refused link shows a dialog.
- Note bubbles are held per window in the explorer, not in the published window state.
- A git ref reaches git only after `valid_ref` in `views.rs` accepts it, and `fixtures/views/refs.json` is the ref syntax shared with `check/src/git-range.ts`; a change view's staleness (`view-staleness.ts`) and marks (`change-marks.ts`) are pure and take git facts handed in; a stale view is deleted only on the user's click.
- A command never takes a path from the frontend: Rust reads the folder from the window's assignment. Every window is built by `open_window` and labelled `w-<n>`, and `app/src-tauri/capabilities/default.json` grants the `app-access` permission set to `w-*`; `capabilities/settings.json` grants only `settings-access` to the `settings` window, which holds no folder and receives no menu action.
- Filesystem access goes through `fs_safe`. The `fs_safe` tests are required: they guard the path-confinement boundary, so they are never removed or weakened.
- The app updates only through Homebrew. A release publishes `recognizer-toolchain.tar.gz` (the CLI, every scanner and the claude describer) and `recognizer.app.tar.gz`, named by slug, to the releases repo and renders the formula and cask into `kenmclennan/homebrew-tap`; the `RELEASES_TOKEN` secret name is fixed across apps and must reach the tap. The footer's `tools-notice` shows when the app and the installed `recognizer` command differ in version.
- `npm run check` is the `check/` gate (lint, build, tests), the same steps CI runs; `npm run check:app` is the app's gate (typecheck, tests, lint, format check, `cargo test`, `cargo fmt --check`, `cargo clippy -D warnings`, build); `npm run install-app` builds the bundle into `~/Applications`.

## Rules

- **The scan document is the contract.** Every scanner emits exactly the schema; nothing language-specific leaks into the document, the policy or the viewer. Every scanner is tested against the shared fixtures.
- **Recognizer knows no architecture.** Every architectural meaning - component names, which dependencies are permitted, any preset - lives in a repository's policy. A named architecture is a template under `policies/`, copied into a repository and edited there. Hexagonal vocabulary appears only in fixtures, examples and templates. Warnings are principle violations, reported by `recognizer check` as candidates with evidence, never verdicts; each names its principle, its evidence and a stable fix-pattern id, and the coaching text an agent reads lives outside recognizer.
- **Recognizer never measures.** Metrics that need something run (tests, mutation, duplication, git history) arrive as overlays, produced by tools a repository registers in `.recognizer/config.yaml`; recognizer runs them and owns the overlay format and the registration, never a metric's meaning.
- **Derived, never authored.** Nothing on the real diagram is drawn by hand. A proposed structure is a separate artifact, always labelled as not in the code.
- **No allow list.** The policy cannot mark a violating edge as acceptable. Existing violations live in a baseline that may only shrink.
- **Missing data is unknown, never healthy.**
- **Prior art is for approach only.** Robert C. Martin's [uml-viewer](https://github.com/unclebob/uml-viewer) states no licence: copy or port none of its code. Its published rules (what counts as an edge, what to skip, how interfaces are marked) may be followed.
- **Scanned repositories own their `.recognizer/` folder.** Policy, tooling configuration (`config.yaml`), saved views, module responsibilities (`responsibilities.json`), proposals and baselines are committed there; scans, overlays, findings and run logs go in `.recognizer/cache/` (`log/` holds the run records), which is gitignored.

## Worktrees

A fresh worktree has no `node_modules`. Run `npm ci` at the repository root before typecheck, tests or any `npm run` script; the root install covers every workspace. `npm run check` and `npm run check:app` start with `scripts/require-install.mjs`, which exits 1 with "run npm ci at the repository root" when `node_modules` is missing, older than `package-lock.json` or lacks a workspace. Run app tools through their npm scripts, whose `pre*` hooks rebuild `check/dist`; a direct `tsc` or `vitest` call needs `npm run build -w recognizer` first.

## Gate risks

- A test that needs a temp folder makes it with `makeTempDir` from `scripts/temp-dirs.mjs` (look tests use `look-page.ts`), so it is removed after the file; every suite runs under `scripts/assert-clean-tmpdir.mjs`, which fails on anything left in `TMPDIR`.
- Biome formats and lints code (`npm run lint -w @recognizer/app`, `lint:fix` to apply). Prettier is for Markdown only; never run it over code or the whole repository.
- The `*-look.test.ts` files drive a headless Chrome and take about a minute each. While iterating, run only the file you are changing (`npm run test -w @recognizer/app -- src/<name>.test.ts`); run the full suite before you finish.
- The Rust scanner's real-content test (`scanners/rust/tests/real_content.rs`) pins the app crate's own shape from `fixtures/rust/recognizer-baseline.json`: adding, removing or re-wiring a Rust module under `app/src-tauri` changes its module, file or edge counts and fails `check:app` (its `check:rust` step runs `cargo test --locked` in `scanners/rust`, as does the app workflow) and the scanner-rust workflow. After any such change run `cargo test --locked` in `scanners/rust` and update the baseline and the test's counts in the same commit.
- Window geometry and native dialog presentation cannot be seen from the pool: a look test runs in headless Chrome, not in the Tauri window, so it cannot prove a window's size, a sheet's placement or a clipped button. A test about size asserts the inner size the Rust builder sets, never a figure derived from the outer size or a title bar; everything else visible only in the running app is the driver's check at review, named as such in the brief, and a worker says so in its closing note rather than treating the look test as proof.
- The full `npm run check:app` takes about 5-6 minutes. Run it once, at the end, from the repo root, with the longest timeout; a timeout is not a failure, so do not re-run it.

## CI

- Every pull-request and push workflow runs on a GitHub-hosted runner; the repository is public, so those minutes are free.
- `app` and the `toolchain` job of `check` (which builds the macOS arm64 archive) run on `macos-15`. `check`'s `test` job, `markdown`, `describer-claude`, `sensors` and the four `scanner-*` workflows run on `ubuntu-latest`, so a test in them must not assume a Mac path or tool.
- A hosted runner has only what the image and the workflow's own setup steps provide (Node from `actions/setup-node`, `uv` from `astral-sh/setup-uv`): no `recognizer-scan-*` binary is on the PATH, so a test that runs a real scan must build or install the scanner it needs inside the workflow, or it fails only on CI.
- Only `release.yml` runs on the self-hosted runner on Ken's Mac (`runs-on: [self-hosted, macOS, ARM64]`), which has the local toolchain.
- No workflow uses `Swatinem/rust-cache`: on the self-hosted runner its cleanup prunes `~/.cargo/bin` and deletes `rustup`, which takes `cargo` and `rustc` with it.

## Code style

- No code comments and no docstrings; behaviour is legible from names and tests.
- Blank lines group related statements; whitespace around multi-line statements.
- Markdown: hyphens not emdashes, one line per paragraph, formatted with `prettier --prose-wrap=never` and linted with markdownlint (line length is off, `.markdownlint.json`).
- This file states conventions and the facts a module's own code and tests cannot carry. A change never adds itself here: no module, command, setting or flag is listed, and a line stays under 600 characters (markdownlint checks it). Update this file only when a convention changes.
