# Recognizer

<!-- markdownlint-configure-file { "MD013": { "line_length": 600, "code_block_line_length": 600, "heading_line_length": 600 } } -->

Scans codebases into a language-neutral structure model and shows it in a native viewer. [README.md](README.md) says what it is for.

## Design

The design of record is [docs/design.md](docs/design.md). It is temporary: it holds the design while it is decided and built, and is deleted once the code and these docs carry it. Build against it; do not restate it here. [docs/plugins.md](docs/plugins.md) is a second temporary design document, for the plugin model of scanners, sensors and describers: until it is built, `design.md` describes what is installed and `plugins.md` where it is going.

- Its **Decided** section is settled. Do not reopen a decision without Ken.
- Its **Open** section is decided with Ken one question at a time, in the order listed, each recorded under Decided before anything is built on it.
- Its **First build items** section is the build order once the open decisions it names are settled.

The words the code, docs and interface use are defined in [docs/glossary.md](docs/glossary.md); add a term there before using it.

This repo is lightcycle project `kenmclennan/recognizer`, shortcode `REC`; work is filed and built through lightcycle.

## Layout

One repository, a directory per part:

- `schema/` - the JSON Schemas and their example files: the scan document, the saved view file, `config.yaml`, the config key schema each key owner publishes, `responsibilities.json`, the overlay file, the findings document, the run log record, the scan run marker, the describe answer the app writes during a scan, and the suite record. Each schema's example folder (`examples/` for the scan document, `<name>-examples/` for the rest) is validated by a test.
- `scripts/` - the toolchain archive builder and its lockfile closure, the archive check, the Homebrew renderer, the install guard both gates start with, the temp-directory guards every suite runs under, the pool-load timeout scaling (`pool-scale.mjs`) and the `schema-behind` check, each with its tests.
  - The archive holds the CLI, the five scanners, the sensors and the claude describer: the Rust scanner a prebuilt arm64 binary, the Python packages (the Python, Kotlin and C# scanners and the sensors) from a vendored wheelhouse, with the Kotlin and C# grammar wheels built from their pinned git commits.
- `check/` - the `recognizer` CLI ([check/README.md](check/README.md)). Every command is one entry in the table in `commands.ts`, which dispatches it and generates `help` and the agent guide's command section, so a command exists nowhere else. A module the app also uses is exported from the library (`check/src/index.ts`), never copied.
  - Pure logic (the structure sensor, the view model, the scan phases, the run log) takes no IO, and the one seam to the running app is `Io.request`. A findings or overlay file is written through a temp file and rename, and validated on a precompiled validator because the app's CSP forbids eval. `.recognizer/cache/log/` keeps the last fifty records.
  - The structure sensor's duplication check (`check/src/duplication/`) parses source with `web-tree-sitter` and the grammars vendored in `check/grammars/`, whose provenance is `check/grammars/PROVENANCE.json`.
- `packaging/homebrew/` - the cask template the release renders into the tap
- `THIRD-PARTY-NOTICES.md` - generated by `app/scripts/third-party-notices.mjs` from `package-lock.json` (npm production packages) and the app's and the Rust scanner's Cargo manifests (the Rust crates, via `cargo metadata`; `rust-notices.mjs` fails on a crate outside the accepted licence list); shipped in the app bundle and the toolchain archive
- `policies/` - starter policies a scanned repository copies into `.recognizer/policy.yaml`
- `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/csharp/`, `scanners/rust/` - one standalone CLI per language (`recognizer-scan-rust` is Rust on `syn`, one module per `.rs` file, with its own `cargo test` workflow); the Kotlin and C# scanners are Python on py-tree-sitter, one module per `.kt` or `.cs` file, and their real-content tests need `RECOGNIZER_KOTLIN_PETCLINIC` and `RECOGNIZER_CSHARP_ESHOP` (the pinned checkouts; CI sets them and `RECOGNIZER_REQUIRE_REAL_CONTENT=1`)
- `sensors/` - the shipped sensors, one Python package (`recognizer-sensors`, hatchling and uv as `scanners/kotlin/`, py-tree-sitter grammars pinned in `pyproject.toml`), shipped in the toolchain archive. `recognizer-sense-<name> run --repository P --commit C --output F [--settings JSON]` (or `recognizer-sensors <name> run ...`) writes one findings file; a first argument that is not a verb (`manifest`, `check`, `run`, `guide`) exits 2.
  - A sensor is a package under `src/recognizer_sensors/` registered in `registry.py`, whose `run` returns an `Outcome` (findings, and an overlay the CLI writes first); a sensor that runs the repository's tests sets `runs_tests` there and gets its coverage through `testrun/`.
  - The names in `registry.py` and `fixtures/sensors/shipped.json`, the list in `fixtures/sensors/list.json` (display name, description, `runs_tests`, `listed`, metrics) and the copy of both in `check/src/shipped-sensors.ts` are held equal by `sensors/tests/test_cli.py` and `check/test/shipped-sensors.test.ts`, so they move together.
  - A sensor's defaults live in its own settings and its tests in `sensors/tests/`, with one end-to-end run per sensor in `check/test/sensors.integration.test.ts` over `fixtures/<sensor>/sample`. A sensor that reads another's overlay is listed after it in `config.yaml`.
- `describers/claude/` - the reference describer: `recognizer-describe-claude run --model <name> <request-file>` sends the request `recognizer describe` writes to `claude -p` with the fixed prompt in `prompt.md` and prints one line; its version is derived from the prompt file and registered in `.recognizer/config.yaml`
- `app/` - the Tauri viewer, built from `kenmclennan/tauri-starter` ([app/README.md](app/README.md))
- `docs/` - the temporary design documents (`design.md`, `plugins.md`), the glossary, and `duplication-sensor-review.md`, a past investigation kept as history
- `.recognizer/` - this repository's own Recognizer config, which registers the in-tree claude describer
- `.github/actions/` - the composite actions the workflows share: `install-uv` (uv from PyPI at one pinned version) and `cancel-on-failure`
- `fixtures/` - small sample codebases per language, each with its expected scan; `fixtures/window-socket/` holds the request and response pairs the Rust socket tests and the CLI tests share. `fixtures/links/syntax.json` is shared the same way by `check/src/link.ts` and `app/src-tauri/src/link.rs`.
- `validation/` - one `report.md` per sensor (crap, mutation, thresholds, structure) with its verdict, and the scripts that compare the sensor with reference tools; the labelled corpora the reports rest on are `fixtures/<sensor>/corpus/`, each with an `expected.json` whose every value is derived by hand, checked in CI by `sensors/tests/test_corpus.py` and `check/test/structure-corpus.test.ts`. A case with a `known_defect` is expected to fail until its fix lands. `validation/**` is in no CI path filter because the reference tools are not CI dependencies
  - `validation/corpus/` is the measurement corpus: the real repositories in `manifest.json`, which `snapshot.mjs` fetches at their pinned commits to measure a findings rule across many repositories.

`app/` is the npm workspace `@recognizer/app`: Vite, TypeScript and plain DOM in `app/src/`, and the Rust crate `recognizer_app` in `app/src-tauri/`. It imports `check` as a library (`recognizer`, built to `check/dist` by the `pre*` scripts). Its rules:

- Logic goes in pure modules with unit tests: a module is pure when it takes no DOM, no Tauri call and no timer it was not handed. `*-view.ts` and `*-source.ts` stay thin, the ELK layout runs in the `layout.worker.ts` web worker, and `main.ts` is the composition root. The list of pure modules is `app/src/` itself, not this file.
- The frontend reaches Rust only through a port: `<name>-port.ts` declares it, `<name>-source.ts` implements it over Tauri, `<name>-fake.ts` stands in for tests, and `showExplorer` receives them. A new Rust command needs a port method, a permission file under `app/src-tauri/permissions/` and an entry in `app.toml`, or the window refuses it at runtime while the look tests, which stub the port, pass.
- Rust is the narrow boundary: dialogs, the editor, settings, git, the filesystem, child processes and the socket. Everything else is TypeScript.
- `scan-ticks.json`, `recent.json`, `recent-views.json`, `config.json` and `app.sock` live in the app's config folder (`~/Library/Application Support/com.kenmclennan.recognizer`, the Tauri identifier), never inside a repository; the socket is mode 0600, one JSON line per request and per response. `RECOGNIZER_APP_SOCKET` overrides the socket path and `RECOGNIZER_APP_CONFIG_DIR` the folder the CLI reads `config.json` from.
- `stop_scan` sends SIGTERM to the scan's process group, and so does closing the window, then SIGKILL 15 seconds later if the scan is still alive; the CLI relays the TERM to each live plugin, waits up to 10 seconds for them, then kills the rest. Nothing a scan spawns may leave that group. The one exception is a Mutation test run, which starts its own session so a timeout can kill the runner's children; the sensor's `SIGTERM` handler ends those sessions itself, so Stop still reaches them.
- The app runs the structure sensor itself, and a registered sensor only as a phase of `run_scan`, each name positional and checked by `sensor_name_ok` before anything spawns.
- A `recognizer://` link never scans, describes or writes; a refused link shows a dialog.
- Note bubbles are held per window in the explorer, not in the published window state.
- A git ref reaches git only after `valid_ref` in `views.rs` accepts it, and `fixtures/views/refs.json` is the ref syntax shared with `check/src/git-range.ts`; a change view's staleness (`view-staleness.ts`) and marks (`change-marks.ts`) are pure and take git facts handed in; a stale view is deleted only on the user's click.
- A command never takes a path from the frontend: Rust reads the folder from the window's assignment. Every window is built by `open_window` and labelled `w-<n>`, and `app/src-tauri/capabilities/default.json` grants the `app-access` permission set to `w-*`; the `app-access` set is the only one, and the Settings modal opens inside a window, never as a window of its own. Repository config is written only by `write_repository_config`, which stages the edits in a temp folder through `recognizer config`.
- Filesystem access goes through `fs_safe`. The `fs_safe` tests are required: they guard the path-confinement boundary, so they are never removed or weakened.
- The app updates only through Homebrew. A release publishes `recognizer-toolchain.tar.gz` (the CLI, every scanner, the sensors and the claude describer; also copied into the app bundle) and `recognizer.app.tar.gz`, named by slug, to the releases repo and renders the cask into `kenmclennan/homebrew-tap`; the `RELEASES_TOKEN` secret name is fixed across apps and must reach the tap. The cask removes a retired formula's links in a `preflight_steps` stanza and links `toolchain/commands` onto `PATH`; the app runs that folder by absolute path.
- `npm run check` is the `check/` gate (lint, build, tests), the same steps CI runs; `npm run check:app` is the app's gate (typecheck, tests, lint, format check, `cargo test`, `cargo fmt --check`, `cargo clippy -D warnings`, build); `npm run install-app` builds the bundle into `~/Applications` without the toolchain inside it, so that bundle's scans refuse as an incomplete installation. A packaged app runs only its bundled toolchain; `npm run app` runs the tools from `RECOGNIZER_TOOLCHAIN` (a built toolchain folder) when it is set, else from the login shell's `PATH`.

## Rules

- **The scan document is the contract.** Every scanner emits exactly the schema; nothing language-specific leaks into the document, the policy or the viewer. Every scanner is tested against the shared fixtures.
- **Recognizer knows no architecture.** Every architectural meaning - component names, which dependencies are permitted, any preset - lives in a repository's policy. A named architecture is a template under `policies/`, copied into a repository and edited there. Hexagonal vocabulary appears only in fixtures, examples and templates. Warnings are principle violations, reported by `recognizer check` as candidates with evidence, never verdicts; each names its principle, its evidence and a stable fix-pattern id, and the coaching text an agent reads lives outside recognizer.
- **A change to a sensor's rules is measured per repository over `validation/corpus` before the spec PR, not on one repository.**
- **Recognizer never measures.** Metrics that need something run (tests, mutation, git history) arrive as overlays, written by the sensors recognizer ships or by a sensor a repository registers; recognizer owns the overlay format, never a metric's meaning. The structure sensor derives duplication from source text, which needs no run.
- **Derived, never authored.** Nothing on the real diagram is drawn by hand. A proposed structure is a separate artifact, always labelled as not in the code.
- **No allow list.** The policy cannot mark a violating edge as acceptable. Existing violations live in a baseline that may only shrink.
- **Missing data is unknown, never healthy.**
- **Nothing costly starts unasked.** A process that spends money (describer calls), noticeable time or machine resources (sensors, test and coverage runs, Mutation) starts only from an explicit user action, never on its own: not on window open, a file change or a timer. Automatic work is limited to the minimal checks needed to load and show what is out of date.
- **Prior art is for approach only.** Robert C. Martin's [uml-viewer](https://github.com/unclebob/uml-viewer) states no licence: copy or port none of its code. Its published rules (what counts as an edge, what to skip, how interfaces are marked) may be followed.
- **Scanned repositories own their `.recognizer/` folder.** Policy, tooling configuration (`config.yaml`), saved views, module responsibilities (`responsibilities.json`) and baselines are committed there; scans, overlays, findings and run logs go in `.recognizer/cache/` (`log/` holds the run records), which is gitignored.

## Worktrees

A fresh worktree has no `node_modules`. Run `npm ci` at the repository root before typecheck, tests or any `npm run` script; it covers every workspace. `npm run check` and `npm run check:app` start with `scripts/require-install.mjs`, which exits 1 with "run npm ci at the repository root" when `node_modules` is missing, stale or lacks a workspace. Run app tools and the `describers/claude` tests through their npm scripts, whose `pre*` hooks rebuild `check/dist`; a direct `tsc` or `vitest` call, and any test that spawns `check/dist/bin.js`, needs `npm run build -w recognizer` first.

The look tests need Playwright's WebKit (`npx -w @recognizer/app playwright install webkit`, as CI runs it) and skip without it.

## Stack-specific gate and review risks

- A test that needs a temp folder makes it with `makeTempDir` from `scripts/temp-dirs.mjs` (look tests use `look-page.ts`), so it is removed after the file; every suite runs under `scripts/assert-clean-tmpdir.mjs`, which fails on anything left in `TMPDIR`.
- A removed-test check counts tests per file by this identity: vitest (`app/src`, `check/test`, `scripts`, `scanners/typescript/test`, `describers/claude/test`) by the full title path, the `describe` titles joined with the `it` or `test` title; Rust (`app/src-tauri/src`, `scanners/rust/tests`, any other `#[test]` file) by the test function's path, the module path plus the function name; pytest (`sensors/tests`, `scanners/python/tests`, `scanners/kotlin/tests`, `scanners/csharp/tests`) by the pytest nodeid, the file path plus the test function, and the class when there is one.
- Biome formats and lints code (`npm run lint -w @recognizer/app`, `lint:fix` to apply). Prettier is for Markdown only; never run it over code or the whole repository.
- The `*-look.test.ts` files drive a headless Playwright WebKit and take about a minute each. While iterating, run only the file you are changing (`npm run test -w @recognizer/app -- src/<name>.test.ts`); run the full suite before you finish.
- The Rust scanner's real-content test (`scanners/rust/tests/real_content.rs`) pins the app crate's own shape from `fixtures/rust/recognizer-baseline.json`: adding, removing or re-wiring a Rust module under `app/src-tauri` changes its module, file or edge counts and fails `check:app` (its `check:rust` step runs `cargo test --locked` in `scanners/rust`, as does the app workflow) and the scanner-rust workflow. After any such change run `cargo test --locked` in `scanners/rust` and update the baseline and the test's counts in the same commit.
- Window geometry and native dialog presentation cannot be seen from the pool: a look test runs in headless Playwright WebKit, not in the Tauri window, so it cannot prove a window's size, a sheet's placement or a clipped button. A test about size asserts the inner size the Rust builder sets, never a figure derived from the outer size or a title bar; everything else visible only in the running app is the driver's check at review, named as such in the brief, and a worker says so in its closing note rather than treating the look test as proof.
- A look test that measures a width or height can pass on one machine and fail on another, because the headless browser's fonts and scrollbars differ between machines. Assert relationships measured on the same page, such as "fits within its container" or "same height as its sibling", never a fixed pixel width or height. CI's app job runs on the self-hosted macOS runner, so a green CI run is the proof a size assertion needs, and the closing note says whether CI or only a local run passed it. The shared `look-page.ts` hides scrollbars, so a test page never has a scrollbar gutter.
- `npm run check:app` does not run the two graph-layout test files (`layout-worker-build.test.ts`, `lightcycle-shaped-graph.test.ts`, which take many minutes under load): CI runs them in the app workflow's own `layout` job, and `npm run test:layout -w @recognizer/app` runs them locally. A worker need not run them unless it touches the layout worker or graph layout.
- The full `npm run check:app` took 13.5 minutes measured under pool load (the vitest part 250 s), without the graph-layout tests. Run it once, at the end, from the repo root, with the longest timeout; a timeout is not a failure, so do not re-run it. Other workers run it at the same time, so write its output to a log named for your worktree (`/tmp/check-app-$(basename "$PWD").log`), never a shared fixed path.
- Before pushing, run lint and typecheck for every workspace you touched, even when you skip the full `npm run check:app`. For a TypeScript workspace, run `npm run lint -w <workspace>`, then `npm run typecheck -w @recognizer/app` for the app, or `npm run build -w <workspace>` (its `tsc` step) for any other workspace. For a Python package (`scanners/python`, `scanners/kotlin`, `sensors`), run `uv run ruff check .`, `uv run ruff format --check .` and `uv run --python 3.11 pytest`, so fixtures and code are proven on the minimum Python CI runs.
- The `sensors` pytest suite takes 30 to 110 minutes on a pool worker under load, against about 5 minutes on CI, which runs it in full on every push. A writer changing `sensors` runs the test files that cover the modules it changed and their callers (`uv run --python 3.11 pytest tests/test_<area>*.py`), not the whole suite, and the closing note names the files run. A suite run is a foreground command with the longest timeout, never a backgrounded run polled with `sleep`.
- A test that fails on its own vitest test or hook timeout under load is re-run once on its own, and the closing note reports both results. A gate step the run never reached is never reported as passed.
- A test or hook that passes its own timeout, or waits on its own `setTimeout`, wraps the value in `scaledTimeout` from `scripts/pool-scale.mjs`, so it scales with the pool's load like vitest's defaults do.
- Output from a command run through the login shell (`$SHELL -ilc`) carries tty warnings on Ubuntu CI ("can't access tty") that macOS does not print. A test or sensor that parses such output reads it from a line it marked itself (for example a `RESULT=` prefix), never the whole stream. Passing on a Mac proves nothing here; only the `ubuntu-latest` jobs show the failure.

## CI

- Every pull-request and push workflow job not named below runs on a GitHub-hosted runner; the repository is public, so those minutes are free.
- `app` (its `check` and `layout` jobs), the `toolchain` job of `check` (which builds the macOS arm64 archive) and `release.yml` run on the self-hosted runner on Ken's Mac (`runs-on: [self-hosted, macOS, ARM64]`), which has the local toolchain and a TMPDIR shared between runs. `check`'s `test` job, `markdown`, `describer-claude`, `sensors`, `schema-behind` and the five `scanner-*` workflows run on `ubuntu-latest`, so a test in them must not assume a Mac path or tool.
- A hosted runner has only what the image and the workflow's own setup steps provide (Node from `actions/setup-node`, `uv` from the repository's own `.github/actions/install-uv`): no `recognizer-scan-*` binary is on the PATH, so a test that runs a real scan must build or install the scanner it needs inside the workflow, or it fails only on CI.
- A failing `schema-behind` check means the branch is on an older scan schema than main: rebase onto main.
- No workflow uses `Swatinem/rust-cache`: on the self-hosted runner its cleanup prunes `~/.cargo/bin` and deletes `rustup`, which takes `cargo` and `rustc` with it.

## Code style

- No code comments and no docstrings; behaviour is legible from names and tests.
- Blank lines group related statements; whitespace around multi-line statements.
- Markdown: hyphens not emdashes, one line per paragraph, formatted with `prettier --prose-wrap=never` and linted with markdownlint run from the repo root (line length is off, `.markdownlint.json`).
- This file states conventions and the facts a module's own code and tests cannot carry. A change never adds itself here: no module, command, setting or flag is listed, and a line stays under 600 characters (markdownlint checks it). Update this file only when a convention changes.
