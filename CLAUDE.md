# Recognizer

Scans codebases into a language-neutral structure model and shows it in a native viewer. [README.md](README.md) says what it is for.

## Design

The design of record is [docs/design.md](docs/design.md). It is temporary: it holds the design while it is decided and built, and is deleted once the code and these docs carry it. Build against it; do not restate it here.

- Its **Decided** section is settled. Do not reopen a decision without Ken.
- Its **Open** section is decided with Ken one question at a time, in the order listed, each recorded under Decided before anything is built on it.
- Its **First build items** section is the build order once the open decisions it names are settled.

The words the code, docs and interface use are defined in [docs/glossary.md](docs/glossary.md); add a term there before using it.

This repo is lightcycle project `kenmclennan/recognizer`, shortcode `REC`; work is filed and built through lightcycle.

## Layout

One repository, a directory per part:

- `schema/` - the JSON Schemas and example files for the scan document, the saved view file, `config.yaml`, `responsibilities.json` and the overlay file (`overlay.schema.json`)
- `check/` - the `recognizer` CLI, dispatched and documented from one command table (`commands.ts`, `help.ts`): `check` reports violations, baseline growth, graph metrics and warnings, for the repository's current scan (scanning first when stale; `check [<module>...]` narrows the report) or, with `--scan`, for a scan file; `find`, `show` and `modules` read the scan (`read-commands.ts`; `findings.ts` holds `findingsByModule` and is exported from the library, `signatures.ts` the plain-text signatures); `scan` detects languages, runs each scanner and writes the cache; `uses`, `used-by`, `callers` and `path` answer questions from a fresh scan (`freshness.ts`); `views` builds, shows and checks the saved view files at `.recognizer/views/<name>.json` (`views.ts` validates and resolves them and is exported from the library, `views-command.ts` is the CLI); `measure` runs the overlays a repository registers in `.recognizer/config.yaml` and writes `.recognizer/cache/overlays/<name>.json` (`measure-command.ts`; `overlays.ts` holds `validateOverlay` and is exported from the library), and `describe` runs the describer a repository registers in `.recognizer/config.yaml` (`config.ts`) for every module whose line in `.recognizer/responsibilities.json` is missing or out of date, and `describe --check` reads the lines without running it (`describe-command.ts`; `responsibilities.ts` holds the file's types, `validateResponsibilities` and `lineStatus` and is exported from the library). The neighbour, caller and path logic the app also uses lives in `neighbours.ts`, `callers.ts` and `paths.ts` and is exported from the library ([check/README.md](check/README.md))
- `scripts/` - the toolchain archive builder (`build-toolchain.mjs`), the lockfile closure it vendors (`toolchain-closure.mjs`), the archive check (`verify-toolchain.mjs`) and the Homebrew renderer (`render-homebrew.mjs`), with their tests
- `packaging/homebrew/` - the formula and cask templates the release renders into the tap
- `THIRD-PARTY-NOTICES.md` - generated by `app/scripts/third-party-notices.mjs` from `package-lock.json` (npm production packages) and `app/src-tauri/Cargo.lock` (the Rust crates, via `cargo metadata`; `rust-notices.mjs` fails on a crate outside the accepted licence list); shipped in the app bundle and the toolchain archive
- `policies/` - starter policies a scanned repository copies into `.recognizer/policy.yaml`
- `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/` - one standalone CLI per language (`recognizer-scan-rust` is Rust on `syn`, one module per `.rs` file, with its own `cargo test` workflow); the Kotlin scanner is Python on py-tree-sitter, one module per package directory, and its real-content test needs `RECOGNIZER_KOTLIN_PETCLINIC` (the pinned petclinic checkout; CI sets it and `RECOGNIZER_REQUIRE_REAL_CONTENT=1`)
- `describers/claude/` - the reference describer: `recognizer-describe-claude <request-file>` sends the request `recognizer describe` writes to `claude -p` with the fixed prompt in `prompt.md` and prints one line; its version is derived from the prompt file and registered in `.recognizer/config.yaml`
- `app/` - the Tauri viewer, built from `kenmclennan/tauri-starter` ([app/README.md](app/README.md))
- `fixtures/` - small sample codebases per language, each with its expected scan

`schema/`, `check/`, `policies/`, `scanners/python/`, `scanners/typescript/`, `scanners/kotlin/`, `scanners/rust/`, `describers/claude/`, `app/` and `fixtures/` exist.

`app/` is the npm workspace `@recognizer/app`: Vite, TypeScript and plain DOM in `app/src/`, and the Rust crate `recognizer_app` in `app/src-tauri/`. It imports `check` as a library (`recognizer`, built to `check/dist` by the `pre*` scripts). Its rules:

- Logic goes in pure modules with unit tests (`scan-loading`, `tree-model`, `tree-filter`, `health`, `open-modules`, `canvas-state`, `canvas-graph`, `canvas-layout`, `canvas-scene`, `canvas-keys`, `bar-hover`, `edge-evidence`, `inspector-model`, `card-code`, `show-private`, `editor-open`, `picker-model`, `row-model`, `panel-widths`, `view-steps`, `view-file`, `stale-report`, `view-history`, `current-view`, `viewport`, `wheel-device`, `layout-source`, `tools-notice`, `footer-scan`, `rescanner`, `trail-model`, `responsibility-model`, `busy-gate`); views and sources (`*-view.ts`, `*-source.ts`) stay thin, the ELK layout runs in the `layout.worker.ts` web worker, and `main.ts` is the composition root. Rust stays the narrow boundary for the dialog, the app's settings (`settings.rs`: the `editor` and `recognizer_path` keys of `config.json`, read and written for the Settings window `settings.html`, which `settings-view.ts` builds), launching the editor (`editor.rs`: system default, an app's name or a shell command), the changed-since rule (`changes.rs`: the baseline built from the cached scans' recorded files, hashes and selection, the comparison and the 2-second poller behind `changes-changed`), running `recognizer scan`, asking the installed command for its version (`recognizer_version`, behind the footer's out-of-step notice), reading the cache and launch arguments, the module responsibility lines (`responsibilities.rs`: `read_responsibilities` reads `.recognizer/responsibilities.json` and `config.yaml` with the SHA-256 of each module's source, `describe_module` runs `recognizer describe <module> --json` for one module, and the `responsibilities-changed` watcher), and the saved views (`views.rs`: list, write, rename, current view, git-rename and commit-scan lookups, and the `.recognizer/views/` watcher). `showExplorer` reaches them through the `ViewsPort` (`views-port.ts`, `views-source.ts`; `views-fake.ts` in tests) the `EditorPort` (`editor-port.ts`, `editor-source.ts`; `editor-fake.ts` in tests) and the `ResponsibilitiesPort` (`responsibilities-port.ts`, `responsibilities-source.ts`; `responsibilities-fake.ts` in tests).
- A command never takes a path from the frontend: Rust reads the folder from the window's assignment. Every window is built by `open_window` and labelled `w-<n>`, and `app/src-tauri/capabilities/default.json` grants the `app-access` permission set to `w-*`; `capabilities/settings.json` grants only `settings-access` to the `settings` window, which holds no folder and receives no menu action.
- Filesystem access goes through `fs_safe`. The `fs_safe` tests are required: they guard the path-confinement boundary, so they are never removed or weakened.
- The app updates only through Homebrew. A release publishes `recognizer-toolchain.tar.gz` (the CLI and every scanner) and `recognizer.app.tar.gz`, named by slug, to the releases repo and renders the formula and cask into `kenmclennan/homebrew-tap`; the `RELEASES_TOKEN` secret name is fixed across apps and must reach the tap. The footer's `tools-notice` shows when the app and the installed `recognizer` command differ in version.
- `npm run check` is the `check/` gate (lint, build, tests), the same steps CI runs; `npm run check:app` is the app's gate (typecheck, tests, lint, format check, `cargo test`, `cargo fmt --check`, `cargo clippy -D warnings`, build); `npm run install-app` builds the bundle into `~/Applications`.

## Rules

- **The scan document is the contract.** Every scanner emits exactly the schema; nothing language-specific leaks into the document, the policy or the viewer. Every scanner is tested against the shared fixtures.
- **Recognizer knows no architecture.** Every architectural meaning - component names, which dependencies are permitted, any preset - lives in a repository's policy. A named architecture is a template under `policies/`, copied into a repository and edited there. Hexagonal vocabulary appears only in fixtures, examples and templates. Warnings are principle violations, reported by `recognizer check` as candidates with evidence, never verdicts; each names its principle, its evidence and a stable fix-pattern id, and the coaching text an agent reads lives outside recognizer.
- **Recognizer never measures.** Metrics that need something run (tests, mutation, duplication, git history) arrive as overlays, produced by tools a repository registers in `.recognizer/config.yaml`; recognizer runs them and owns the overlay format and the registration, never a metric's meaning.
- **Derived, never authored.** Nothing on the real diagram is drawn by hand. A proposed structure is a separate artifact, always labelled as not in the code.
- **No allow list.** The policy cannot mark a violating edge as acceptable. Existing violations live in a baseline that may only shrink.
- **Missing data is unknown, never healthy.**
- **Prior art is for approach only.** Robert C. Martin's [uml-viewer](https://github.com/unclebob/uml-viewer) states no licence: copy or port none of its code. Its published rules (what counts as an edge, what to skip, how interfaces are marked) may be followed.
- **Scanned repositories own their `.recognizer/` folder.** Policy, tooling configuration (`config.yaml`), saved views, module responsibilities (`responsibilities.json`), proposals and baselines are committed there; scans and overlays go in `.recognizer/cache/`, which is gitignored.

## Worktrees

A fresh worktree has no `node_modules`. Run `npm ci` at the repository root before typecheck, tests or any `npm run` script; the root install covers every workspace. Run app tools through their npm scripts, whose `pre*` hooks rebuild `check/dist`; a direct `tsc` or `vitest` call needs `npm run build -w recognizer` first.

## Gate risks

- Biome formats and lints code (`npm run lint -w @recognizer/app`, `lint:fix` to apply). Prettier is for Markdown only; never run it over code or the whole repository.
- The `*-look.test.ts` files drive a headless Chrome and take about a minute each. While iterating, run only the file you are changing (`npm run test -w @recognizer/app -- src/<name>.test.ts`); run the full suite before you finish.
- The full `npm run check:app` takes about 5-6 minutes. Run it once, at the end, from the repo root, with the longest timeout; a timeout is not a failure, so do not re-run it.

## CI

Every workflow runs on a self-hosted runner on Ken's Mac (`runs-on: [self-hosted, macOS, ARM64]`), registered to this repo only, because GitHub-hosted minutes for private repos ran out. It has the local toolchain, so no workflow installs system libraries. No workflow uses `Swatinem/rust-cache`: on a self-hosted runner its cleanup prunes `~/.cargo/bin` and deletes `rustup`, which takes `cargo` and `rustc` with it.

## Code style

- No code comments and no docstrings; behaviour is legible from names and tests.
- Blank lines group related statements; whitespace around multi-line statements.
- Markdown: hyphens not emdashes, one line per paragraph, formatted with `prettier --prose-wrap=never` and linted with markdownlint (line length is off, `.markdownlint.json`).
- Keep this file current as the code changes, in the same change.
